# FC-030.1E.1 — Host Startup Contract and Failure Vocabulary

## Status

Implemented; awaiting local verification before closure/freeze.

FC-030.1A through D remain frozen. E.1 introduces startup orchestration contracts only. API/Edge startup wiring and SQL startup execution remain outside this slice.

## Goal

Freeze the provider-aware host readiness boundary and the SQL-specific startup failure vocabulary that FC-030.1E.2 through E.4 will compose around the already-frozen migration engine and runtime compatibility verifier.

## Provider-neutral host contract

Hosts depend on exactly one readiness operation:

```csharp
public interface IPersistenceStartupGate
{
    ValueTask EnsureReadyAsync(CancellationToken cancellationToken);
}
```

The interface lives in `FactoryConnect.Persistence` so API and Edge can call the same provider-aware boundary without referencing SQL-specific migration or compatibility implementation types.

E.1 does not register an implementation and does not wire either host.

## SQL startup failure vocabulary

The SQL-specific failure vocabulary is closed and ordered:

```text
MigrationOperationalFailure
VerificationOperationalFailure
DatabaseIncompatible
```

The startup exception preserves mechanism authority rather than flattening it:

```text
MigrationOperationalFailure
    CompatibilityResult = null
    InnerException = exact C operational exception

VerificationOperationalFailure
    CompatibilityResult = null
    InnerException = exact D operational exception

DatabaseIncompatible
    CompatibilityResult = exact non-Compatible D result
    InnerException = null
```

A `Compatible` D result cannot construct `DatabaseIncompatible`.

E-authored exception messages are deterministic and do not interpolate provider exception text, connection configuration, or other secrets.

## Cancellation invariant

`OperationCanceledException` is not part of the startup failure taxonomy.

The frozen rule is deliberately unconditional:

```text
Any OperationCanceledException emitted by C or D
    -> propagate unchanged
    -> never wrap as SqlPersistenceStartupException
```

This rule does not depend on whether the supplied startup `CancellationToken` is currently signalled. E.2 must therefore catch and rethrow every `OperationCanceledException` before any generic operational-failure translation.

The operational-failure factories defensively reject cancellation wrapping, and `SqlPersistenceStartupCancellationPolicy.MustPropagate` is the single E-layer predicate used to freeze this distinction.

```text
OperationCanceledException
    -> propagation path
    -> no SqlPersistenceStartupException translation
    -> gate never succeeds
    -> host activation does not proceed

all other operational exceptions
    -> translated by stage to MigrationOperationalFailure or VerificationOperationalFailure
```

This avoids an undefined branch where an unrelated `OperationCanceledException` could otherwise fall into a generic catch and be replaced by an `ArgumentException` from the defensive factory.

## Lock-timeout options boundary

E.1 introduces one SQL startup lock-timeout value:

```text
SqlPersistenceStartupOptions.LockTimeout
```

Construction delegates validation to the frozen `SqlMigrationLockTimeout.ToMilliseconds` authority. E does not copy timeout conversion rules.

Therefore E inherits exactly:

- non-negative timeout requirement;
- zero-wait support;
- positive fractional millisecond ceiling behavior;
- SQL Server `Int32` millisecond maximum; and
- rejection beyond that maximum.

The exact configured `TimeSpan` is retained and will be passed to both C Exclusive migration and D Shared verification in E.2.

No configuration key/default is frozen in E.1; provider composition/configuration binding belongs to E.2 after repository convention review.

## Logging contract

E.1 freezes the allowed E-authored structured field vocabulary:

```text
HostName
PersistenceProvider
StartupStage
FailureKind
CompatibilityClassification
DiagnosticCode
DecisionStage
Artifact
Expected
Actual
Detail
```

Startup stages are closed to:

```text
Migration
Verification
```

E.2+ may attach operational exceptions through the logger exception channel, but E-authored message templates must not interpolate connection strings, passwords, tokens, secrets, raw configuration dumps, or provider exception text.

D diagnostics remain the compatibility evidence; E does not create another diagnostic model.

## Contract tests

`SqlPersistenceStartupContractTests` freezes:

1. one cancellation-aware `IPersistenceStartupGate.EnsureReadyAsync` method;
2. exact failure-kind vocabulary/order;
3. exact startup-stage vocabulary/order;
4. timeout delegation and retention;
5. zero-wait acceptance;
6. negative timeout rejection;
7. SQL `Int32` timeout limit rejection;
8. exact migration operational cause preservation;
9. exact verification operational cause preservation;
10. every `OperationCanceledException` is identified for unconditional propagation, including when the supplied startup token is not cancelled;
11. cancellation non-wrapping for both operational stages;
12. exact non-compatible D result preservation;
13. rejection of `Compatible` as a startup incompatibility failure; and
14. closed secret-safe structured logging field vocabulary.

## Hard boundary

E.1 does not:

- register `IPersistenceStartupGate`;
- execute the migration engine;
- execute runtime compatibility verification;
- wire API startup;
- wire Edge startup;
- introduce migration 005;
- change migrations 001–004;
- change C exception or transaction semantics;
- change D classification, diagnostic, lock, or read-only semantics;
- add SQL reporting persistence; or
- change non-SQL provider behavior.
