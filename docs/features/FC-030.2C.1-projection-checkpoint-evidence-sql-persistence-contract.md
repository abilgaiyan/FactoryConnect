# 1. Governing invariant

> **For each operational metric projection processor, a successful commit atomically replaces the complete published projection set, including projection rows, manifest membership, and evidence, and advances the corresponding checkpoint. Any unsuccessful commit leaves the previously published complete set and checkpoint unchanged. Equal-revision processing is replay validation/idempotency, not partial replacement.**

The atomic publication boundary is:

```text
projection replacement
+ manifest replacement
+ evidence persistence
+ checkpoint advancement
= one atomic commit boundary
```

Readers may observe the old complete published set or the new complete published set. They MUST NOT observe an intermediate set.

# 3. Frozen decision table

| Concern | Frozen decision |
|---|---|
| Processor lookup | Resolve by canonical processor-key SQL authority frozen in FC-030.2A. |
| Processor creation | A missing processor may be created by the first valid commit. A plain checkpoint read MUST NOT create it. |
| Processor binding | Aggregation processor and metric-input stream bindings are immutable for the processor lifetime. Existing unequal binding is a conflict with zero mutation. |
| Checkpoint absence | `null` means no committed projection revision exists for the processor. |
| Initial commit | `ExpectedCheckpoint = null` is valid only while no durable checkpoint exists. |
| Advancing revision | Proposed source position strictly greater than the expected/current position is a mutation candidate. |
| Equal revision | Replay validation/idempotency only. It MUST NOT become a second partial replacement. |
| Lower revision | Reject as source-revision regression. |
| Stale expected checkpoint | Compare-and-swap conflict; no durable mutation. |
| Manifest meaning | `BatchManifest` is the exact complete published projection-key set at the checkpoint, not a changed-key delta. |
| Shrinking manifest | Keys absent from the replacement manifest cease to be published/query-visible atomically. |
| Empty manifest | A valid commit may replace a previously nonempty set with the empty published set and advance the checkpoint. |
| Projection insert | An absent exact evaluation key is inserted with its complete durable state and evidence. |
| Projection replacement | The same exact evaluation key at an advancing revision receives the complete replacement durable state. |
| Unchanged projection | Physical rewrite is optional; externally visible provider-neutral state MUST remain equivalent. |
| Evaluation-key lookup | Hash is lookup/index authority; exact canonical binary equality is logical identity authority. |
| Hash collision | Same hash with unequal codec/canonical bytes is a persisted-identity collision and MUST fail; the existing row MUST NOT be updated. |
| Evidence replacement | Evidence is a complete snapshot. Replacement deletes/replaces old evidence and writes the complete new evidence collection inside the same transaction. |
| Component evidence | Persist with the frozen component subtype discriminator and ordinal within component operand evidence. |
| Dependency evidence | Persist with the frozen dependency subtype discriminator and ordinal within dependency evidence. |
| Operand uniqueness | Provider-neutral ordinal operand-name uniqueness applies across component and dependency evidence. SQL projections/order keys are physical enforcement aids, not alternate string semantics. |
| Evidence ordinals | Writer emits exact contiguous `0..N-1` per kind; reader revalidates contiguity. |
| Reader publication | Nonmanifest rows MUST NOT be returned as published projections. |
| Atomicity | Processor/binding effects, rows, evidence, manifest, and checkpoint publication participate in one transaction. |
| Failure | Any pre-commit failure rolls back the entire attempted publication. |
| Concurrency | Commits for the same processor are serialized around processor/checkpoint CAS authority. Distinct processors remain logically independent. |
| Ambiguous commit | Retry reconciles durable state against expected and proposed state before deciding success/conflict/retry. |
| Cancellation | Before confirmed commit: rollback/cancel. After confirmed commit: state is committed and MUST NOT be represented as rolled back. |
| Provider failures | Unexpected SQL failures preserve the underlying provider exception; Core/worker behavior MUST NOT depend on raw SQL error numbers. |

# 4. Processor identity and immutable binding

Conceptual behavior:

```text
processor missing
    + valid source processor/stream
    → create on first commit

processor exists
    + exact same source binding
    → reuse

processor exists
    + different aggregation processor
      or different source stream
    → immutable-binding conflict
    → rollback / no mutation
```

The canonical processor key and its frozen SQL comparison projection remain the processor lookup/CAS authority defined by FC-030.2A. SQL persistence MUST revalidate the stored binding after resolution rather than treating lookup-key equality as proof of the complete binding.

Checkpoint reads are observational. They MUST NOT manufacture durable processor identity merely because a runtime asks whether a checkpoint exists.

---

# 5. Checkpoint, source revision, and replay

Checkpoint state is the durable publication position for one projection processor.

```text
no checkpoint
    + ExpectedCheckpoint = null
    + valid proposed revision
    → initial commit candidate

current = N
    + expected = N
    + proposed > N
    → advancing commit candidate

current = N
    + expected < N
    → stale writer conflict

current = N
    + proposed < N
    → source revision regression

current = proposed = N
    → replay validation only
```

Equal-position replay succeeds only when the durable checkpoint, exact manifest, and every published projection/evidence reconstruction are provider-neutral equivalent to the proposed state. Manifest or projection mismatch at the same source revision is an inconsistency/corruption signal, not permission to rewrite history.

All projections and evidence in one commit MUST be coherent with the commit source identity/revision under the existing provider-neutral contract.

---

# 6. Exact manifest and complete-set replacement

`OperationalMetricProjectionCheckpoint.BatchManifest` owns the complete currently published projection-key set for the processor at the checkpoint revision.

Example:

```text
old manifest = { A, B, C }
new manifest = { A, C }

successful commit:
published set = { A, C }

B is no longer published or query-visible.
```

Migration 005 models current publication rather than historical manifest versions. SQL implementation may physically delete obsolete current projection/evidence rows. It MUST NOT rely on stale nonmanifest rows remaining reader-visible.

A replacement from a nonempty manifest to an empty manifest is valid and MUST publish an empty set atomically with checkpoint advancement.

# 7. Evaluation-key identity and collision handling

Migration 005 persists the frozen evaluation-key identity material:

```text
EvaluationKeyCodecVersion
EvaluationKeyHash
EvaluationKeyBinary
```

The hash is SHA-256 over the canonical V1 evaluation-key bytes under the frozen codec contract.

Lookup and identity verification are deliberately two-stage:

```text
lookup by processor + EvaluationKeyHash
        ↓
verify supported EvaluationKeyCodecVersion
        ↓
compare exact EvaluationKeyBinary bytes

same canonical bytes
    → same logical evaluation key

different canonical bytes
    → hash collision / incompatible persisted identity
    → fail operation
    → never mutate the hash owner as though it were the requested key
```

A SQL unique-key violation alone is not sufficient collision classification. When required, implementation MUST reread the authoritative hash owner and distinguish same exact identity/concurrency from same hash/different canonical bytes.

---

# 8. Projection and evidence replacement

Projection persistence is snapshot replacement, not field-level patching.

For an advancing commit:

```text
absent exact key
    → insert complete projection + evidence + manifest membership

existing exact key
    → replace complete durable projection state and complete evidence

old manifest key absent from new manifest
    → remove from current published state
```

Evidence replacement is conceptually:

```text
delete/replace old evidence for projection
        ↓
write complete new evidence collection
```

and occurs inside the same publication transaction.

Subtype mapping follows the frozen migration-005 discriminator vocabulary:

```text
ComponentEvidence
    EvidenceKind = 1
    EvidenceOrdinal = index within OperandEvidence

DependencyEvidence
    EvidenceKind = 2
    EvidenceOrdinal = index within DependencyEvidence
```

Writer validation MUST preserve exact ordinal sequence and provider-neutral operand uniqueness. Dependency snapshot bytes/hash and canonical projections remain subject to the frozen codec and physical-authority contracts.

# 9. Transaction isolation, locking, and concurrent writers

The observable lock ordering is frozen as:

```text
ProjectionProcessor
    ↓
Checkpoint
    ↓
Projection identity rows
    ↓
Manifest
    ↓
Evidence
```

The implementation may choose the precise SQL Server locking statements/hints needed to realize these semantics, but MUST preserve the frozen physical lookup/CAS authorities and observable concurrency behavior.

Same-processor writers MUST serialize such that two writers starting from the same expected checkpoint cannot both publish divergent successor states. Exactly one may win the advancing publication; the other must reconcile or fail as stale/conflicting without partial mutation.

The checkpoint row is the natural CAS serialization point once it exists. The initial no-processor/no-checkpoint path MUST also serialize creation at the canonical processor-key slot so duplicate initial publishers cannot independently create competing processor state.

Distinct processors MUST remain logically independent; correctness MUST NOT require a database-wide projection publication lock.

---

# 10. Atomic writer sequence

The conceptual transaction is:

```text
BEGIN TRANSACTION

1. Resolve/lock projection processor key slot
2. Create processor if absent and commit permits creation
3. Verify immutable aggregation-processor + input-stream binding
4. Read/lock current checkpoint
5. Compare expected/current/proposed revision state
6. Resolve every incoming evaluation key by hash
7. Confirm exact codec version + EvaluationKeyBinary equality for hash owners
8. Materialize complete replacement projection rows
9. Materialize complete replacement evidence
10. Replace exact manifest membership
11. Remove state no longer in the current published set as required
12. Advance checkpoint
13. COMMIT
```

Checkpoint advancement is logically the publication marker, but it is not a separate transaction. No reader-visible intermediate state may be committed between these steps.

---

# 11. Rollback guarantee

Any unsuccessful transaction before confirmed commit MUST preserve the previous complete durable publication.

The guarantee covers:

```text
processor creation/binding effects
checkpoint
projection rows
manifest membership
component evidence
dependency evidence
```

Failure injection after processor resolution, projection mutation, evidence mutation, manifest mutation, or immediately before checkpoint advancement MUST prove that the previous complete published state and checkpoint remain unchanged.

---

# 12. Ambiguous commit reconciliation

The worker retries failed processing, while the runtime advances its in-memory checkpoint only after `CommitAsync` reports success. Therefore the provider MUST tolerate the case where SQL Server committed but the client did not receive a successful completion.

Example:

```text
SQL COMMIT succeeds
        ↓
connection/result fails before CommitAsync reports success
        ↓
worker retries
        ↓
runtime still supplies old ExpectedCheckpoint
```

On retry, durable state is reconciled:

```text
durable checkpoint == proposed checkpoint
+ durable manifest == proposed manifest
+ every published projection/evidence is provider-neutral equivalent
    → prior commit succeeded
    → idempotent success

durable checkpoint == expected checkpoint
    → previous attempt did not publish
    → commit may be attempted again

durable checkpoint is neither expected nor proposed
    → concurrent/stale writer conflict

same proposed revision but different durable manifest/state
    → replay mismatch / persisted inconsistency
```

A retry MUST NOT blindly translate a previously successful but ambiguously reported commit into a stale-write failure.

---

# 13. Cancellation and error boundaries

Cancellation semantics:

```text
cancellation before confirmed COMMIT
    → rollback
    → cancellation propagates

COMMIT confirmed
    → publication is durable
    → MUST NOT subsequently be represented as rolled back

connection/cancellation race around COMMIT
    → outcome may be ambiguous
    → reconciliation on retry determines durable truth
```

C.1 freezes semantic outcomes rather than introducing a large provider-neutral exception hierarchy:

```text
CheckpointConflict
ImmutableProcessorBindingConflict
PersistedIdentityCollision
PersistedProjectionCorruption / ReplayMismatch
Cancellation
ProviderFailure
```

Expected uniqueness/concurrency SQL errors MUST be interpreted against authoritative durable state where necessary. Unexpected SQL failures MUST preserve the underlying `SqlException` as provider evidence/inner failure. Provider-neutral runtime/worker behavior MUST NOT branch directly on SQL Server error numbers.

---

# 14. Reader reconstruction and corruption detection

SQL reconstruction MUST validate persisted canonical/denormalized redundancy. It MUST NOT silently normalize incompatible persisted state.

At minimum reconstruction/conformance must validate, where applicable:

```text
supported EvaluationKeyCodecVersion
SHA-256(EvaluationKeyBinary) == EvaluationKeyHash
decoded EvaluationKey == denormalized identity columns
projection source identity/revision is coherent
evidence subtype shape is valid
evidence ordinal sequence is contiguous and structurally valid
operand order-key projection matches OperandName
dependency snapshot hash matches dependency snapshot bytes
dependency snapshot decodes to the projected dependency
manifest membership defines the published set
```

Provider-neutral `OperationalMetricProjection` construction and equivalence remain authoritative for domain invariants including status/value/reason shape, source coherence, dependency identity, and duplicate operand rejection.

Malformed durable state is corruption/incompatibility. It is not equivalent to "not found".

# 15. In-memory conformance finding

The current `InMemoryOperationalMetricProjectionStore.CommitAsync` upserts projections from the new commit and advances the checkpoint, but does not remove projection rows that belonged to the previous manifest and are absent from the replacement manifest. Its query readers enumerate the backing projection dictionary directly.

Therefore a shrinking replacement can leave a stale projection query-visible even though the provider-neutral checkpoint manifest describes the new exact key set.

Classification:

```text
existing in-memory behavior
    = conformance defect to correct
    ≠ persistence contract authority
    ≠ permission for SQL to retain query-visible stale rows
```

SQL MUST implement the provider-neutral/runtime exact-set semantics frozen here. The Core/in-memory implementation should be corrected under an explicit conformance change; that correction MUST NOT redefine the SQL contract.
