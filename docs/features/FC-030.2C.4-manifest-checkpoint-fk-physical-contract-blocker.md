## 1. Contradiction discovered by real SQL

The frozen publication choreography requires:

```text
processor
→ checkpoint slot acquisition
→ projection acquisition
→ manifest acquisition
→ evidence acquisition
→ projection / manifest / evidence DML
→ exact-state revalidation
→ C.2 checkpoint advancement last
→ COMMIT
```

Migration 005 currently defines:

```text
FK_OperationalMetricProjectionManifest_Checkpoint
  OperationalMetricProjectionManifest.OperationalMetricProjectionProcessorRowId
  → OperationalMetricProjectionCheckpoint.OperationalMetricProjectionProcessorRowId
```

On an initial publication, the checkpoint slot is locked but there is no checkpoint row yet. C.2 intentionally creates the first checkpoint only after the publication body returns successfully. Therefore the first manifest membership cannot be inserted before checkpoint advancement, while checkpoint advancement is frozen to occur after publication DML and exact-state revalidation.

This is a physical-schema contradiction. It is not a C.4 mutation defect and is not resolved by reordering the writer.

## 3. Exact physical correction

The narrowly reopened FK decision is:

```text
REMOVE

FK_OperationalMetricProjectionManifest_Checkpoint
  OperationalMetricProjectionManifest
    .OperationalMetricProjectionProcessorRowId
  → OperationalMetricProjectionCheckpoint
    .OperationalMetricProjectionProcessorRowId

ADD

FK_OperationalMetricProjectionManifest_Processor
  OperationalMetricProjectionManifest
    .OperationalMetricProjectionProcessorRowId
  → OperationalMetricProjectionProcessor
    .OperationalMetricProjectionProcessorRowId
```

The existing composite manifest-to-projection FK remains unchanged:


The direct processor FK preserves explicit processor lifecycle authority without requiring checkpoint existence before publication.

No other Migration 005 column, index, key, FK, CHECK, computed column, collation, or table definition is reopened by this blocker.

## 6. Disposable-versus-durable release rule

Migration-history mutability is decided by durable application, not by branch/tag state alone.

```text
Disposable only
  local/test databases intended for recreation
  → an unreleased Migration 005 may be amended in place

Durable anywhere
  shared development
  CI persistence
  staging
  pilot
  customer
  production
  or any database expected to survive
  → Migration 005 history is immutable
  → a subsequent migration is required
```

Absence from `main`, absence of a formal release tag, or absence of a package/release artifact is insufficient evidence for in-place amendment.

In-place amendment requires affirmative evidence that Migration 005 has never been applied to any durable database.
