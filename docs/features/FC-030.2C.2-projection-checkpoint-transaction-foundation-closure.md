# FC-030.2C.2 — Projection Processor / Checkpoint Transaction Foundation Closure

## Status

**CLOSED / FROZEN**

FC-030.2C.2 implements and proves the SQL Server transaction foundation required by the frozen FC-030.2C.1 persistence contract.

This closure does not authorize migration-005 changes, schema-descriptor changes, projection-row persistence, manifest persistence, or evidence persistence.

## Frozen implementation boundary

FC-030.2C.2 owns:

```text
StringOrderKeyV2 processor-key encoding
observational checkpoint-header reads
source aggregation processor / metric-input stream binding resolution
Serializable projection commit transaction
processor key-slot locking with UPDLOCK,HOLDLOCK
initial processor creation inside the transaction
immutable source-binding validation
checkpoint key-slot locking with UPDLOCK,HOLDLOCK
checkpoint CAS classification
Advance versus ReconcileProposed transaction mode
checkpoint advancement after delegated publication work
rollback of initial processor/checkpoint effects on pre-commit failure
```

The public provider-neutral `IOperationalMetricProjectionStore` is intentionally not advertised by this slice because full projection / manifest / evidence semantics are completed by later C.3/C.4 work.

## Lock-order continuation boundary

C.2 freezes the first two lock stages:

```text
OperationalMetricProjectionProcessor key slot
    ↓
OperationalMetricProjectionCheckpoint key slot
```

C.3/C.4 must continue the frozen order:

```text
resolve complete current projection identity set directly by processor
    ↓
merge with incoming projection identity/hash slots
    ↓
sort ascending EvaluationKeyHash
    ↓
lock every projection identity/hash slot
    ↓
lock manifest rows
    ↓
lock evidence rows
```

No later implementation may acquire manifest or evidence locks before every required projection identity slot has been resolved and locked.

## StringOrderKeyV2 authority

The C.2 implementation uses the migration-005 frozen V2 ordering key:

```text
UTF-16 code unit -> 0x01 + UInt16BE
terminator        -> 0x00
maximum length    -> 256 UTF-16 code units
maximum bytes     -> 769
```

Known vectors include:

```text
""    -> 00
"A"   -> 01004100
"x "  -> 01007801002000
"x\0" -> 01007801000000
"😀"  -> 01D83D01DE0000
```

Processor-key encoding/length validation occurs before source-binding SQL so an overlength processor ID is rejected before SQL execution.

## Concurrency evidence note

The deterministic concurrency test holds the first transaction open after processor/checkpoint lock acquisition, starts the second writer, verifies that the second body does not enter and the second operation does not complete while the first transaction is held, then releases the first and observes:

```text
first writer  -> Advance
second writer -> ReconcileProposed
processor rows  = 1
checkpoint rows = 1
```

A possible future non-blocking test-hardening improvement is to expose a dedicated internal test observer immediately before `LockProcessorSlotAsync`, or inspect SQL Server blocked-request state, so the test can prove directly that the second SQL command has reached the blocked processor-key lookup rather than relying on the held-transaction/outcome proof. This is not a C.2 closure blocker.
