## Goal

Prove the production SQL startup path against real SQL Server:

```text
startup gate
    → C Exclusive migration/adoption
    → D Shared compatibility verification
    → Compatible only
    → host activation permitted
```

E.5 reuses the frozen `SqlServerPersistenceStartupGate`, `SqlServerMigrationEngine`, and `SqlServerRuntimeSchemaCompatibilityVerifier`.

## Determinism requirements

Every concurrency or timeout proof must use isolated databases, explicit SQL session ids, `sys.dm_tran_locks` observation, bounded completion timeouts, assertions that blocked tasks have not completed, deterministic transaction commit/rollback release, and cleanup that cannot replace the primary failure.

Elapsed time and `Task.Delay` are never authoritative evidence of lock ordering.

## E.5.3 — Verification-stage outcomes

The existing startup-gate internal stage seam may be used only to coordinate state between the real C engine and real D verifier or to prove the frozen E.1 exception boundary after real C completes.

Required cases:

### Database incompatibility

```text
real C succeeds
controlled structural drift is introduced before D
real D returns MigrationSchemaDrift
gate throws DatabaseIncompatible
```

The startup exception carries the exact immutable D result and diagnostics, has no inner exception, and prevents activation.

### Verification operational failure

```text
real C succeeds
external transaction obtains Exclusive FactoryConnect.SqlMigration applock
real D Shared lock acquisition times out
VerificationOperationalFailure
```

The exact D/provider cause is retained and activation remains zero.

### Cancellation boundary

E.5.3 follows the already-frozen E.1 rule exactly:

```text
OperationCanceledException emitted by C or D
    → propagate unchanged
    → never wrap

all other C/D operational exceptions
    → translate by stage
```

Real SQL Server/`Microsoft.Data.SqlClient` cancellation while the verifier is blocked inside `sp_getapplock` surfaces as `SqlException` (`Operation cancelled by user`) rather than `OperationCanceledException`. E.5 does not normalize that provider exception into OCE.

Therefore E.5.3 proves both sides independently:

```text
real D blocked on Shared APPLICATION lock
startup token cancelled
provider emits SqlException
    → VerificationOperationalFailure
    → exact provider exception preserved
    → activation = 0
```

and:

```text
real C completes
verification stage emits OperationCanceledException
    → exact OCE propagates unchanged through E
    → no SqlPersistenceStartupException wrapper
    → activation = 0
```

The blocked-D lock tests capture the exact verification session id and require `sys.dm_tran_locks` to show that session waiting on a transaction-owned Shared `APPLICATION` lock before timeout/cancellation is triggered.

Blocker cleanup is best-effort and primary-failure-aware: rollback, transaction disposal, and connection disposal are all attempted; cleanup failures are attached as secondary evidence when a primary startup failure exists and are raised only when no primary failure exists.

## E.5.4 — Concurrent SQL startup

Run two independent real startup gates against the same **empty database**, labelled API and Edge only for diagnostic clarity.

### Required fresh-install concurrency proof

The original E.5.4 requirement remains authoritative:

```text
empty database
external transaction holds Exclusive FactoryConnect.SqlMigration applock
API-labelled and Edge-labelled real C stages both start
SQL metadata confirms both startup sessions WAIT/X on the APPLICATION lock
ledger is still absent
FactoryConnect-owned application schema is still absent
release external applock deterministically
one startup acquires C lock and performs fresh installation
second startup subsequently acquires C lock and re-reads committed current state
both execute real D verification
both succeed
```

The fresh-install case proves:

```text
both startup calls succeed
each activation count = 1
each D verification count = 1
each D result = Compatible
one exact migration ledger exists
history contains canonical 001–004 exactly once
Current schema is exact
no duplicate initialization artifacts
no partial migration history
```

The external application-lock barrier exists only to make both empty-database startup sessions observable before either may initialize the database. It does not alter C semantics; after release, the real C engines compete normally for the same Exclusive migration lock.

### Additional prefix-002 lock-transition proof

The prefix-002 construction is retained as an additional stronger serialization proof, not as a replacement for the required empty-database case.

It seeds exact prefix 001–002 and holds a transaction-owned table lock on migration 003's target table. That barrier does not use the migration application-lock resource. It exists only to keep the designated winner inside the real C engine after C has acquired its Exclusive application lock.

Required sequence:

```text
seed exact 001–002 prefix
external schema blocker holds migration-003 target table
winning labelled gate enters real C
SQL metadata confirms winner has GRANT/X on APPLICATION migration lock
waiting labelled gate enters real C
SQL metadata confirms waiter has WAIT/X on same APPLICATION lock
both startup tasks remain incomplete
release schema blocker deterministically
winner completes 003–004 and commits
waiter acquires C lock and re-reads exact current committed state
both execute real D verification
both succeed
```

The theory proves both labelled winner directions:

```text
API wins first, Edge waits
Edge wins first, API waits
```

Both constructions use primary-failure-preserving best-effort cleanup. They also share one non-parallel xUnit collection so fixture-level scheduling does not add unrelated SQL Server load; each test still creates and proves its own internal concurrency.

The E.5.4 test bounds are finite and separated by purpose:

```text

completion deadlock guard   2 minutes
SQL lock observation        10 seconds
```

The 10-second observation bound remains the fast authority for expected SQL lock state. The wider completion bound only accommodates real migration and verification work after deterministic release.

## E.5.5 — Commit-boundary proof

Retain one deterministic lock/commit boundary test. The implemented construction begins from an exact current database, then opens an external transaction which:

```text
acquires Exclusive FactoryConnect.SqlMigration applock
transactionally drops required owned index IX_MetricInputFact_OrderedRead
keeps that schema mutation uncommitted
```

The startup gate then enters the real C engine on its own SQL session. SQL metadata must prove that exact startup session is `WAIT/X` on the transaction-owned `APPLICATION` lock while activation and D invocation remain zero.

After the external transaction commits, the startup session acquires C's Exclusive lock and re-reads the committed database. Because migration history is already exact current but live owned schema now differs from `Current`, frozen C precedence owns the rejection:

```text
real C emits FinalSchemaValidationException
startup gate translates it to MigrationOperationalFailure
CompatibilityResult = null
InnerException = exact C exception object
D invocation count = 0
activation count = 0
```

A separate read-only real D verification after the startup failure must classify the same committed state as `MigrationSchemaDrift`. This is evidence of the committed state only; it does not alter the startup result or bypass the frozen C-before-D sequence.

The test uses explicit SQL session id capture, `sys.dm_tran_locks` observation, finite bounds, deterministic commit release, and primary-failure-preserving cleanup.
