# FC-030.2 — SQL Operational Metric Projection Persistence

## Status

Architecture contract proposed for review. FC-030.1A through FC-030.1D are closed and frozen. No FC-030.2 production implementation or migration 005 should begin until this contract is accepted.

## Goal

Persist the existing provider-neutral operational metric projection model in SQL Server without changing metric evaluation, projection, reporting, checkpoint, replay, or ordering semantics.

FC-030.2 is the first slice permitted to extend the migration catalog beyond the frozen legacy 001–004 baseline. Its schema evolution is migration 005.

The durable SQL implementation must support the existing contracts:

```text
IOperationalMetricProjectionStore
    ReadCheckpointAsync
    ReadProjectionAsync
    CommitAsync

IOperationalMetricProjectionReportReader
    ReadWindowAsync
```

and must preserve the semantics already proven by the in-memory store and FC-027 through FC-029.

## Central invariant

An operational metric projection commit is one atomic publication of:

```text
expected current checkpoint
        ↓ compare-and-swap
new strictly advancing checkpoint
+ exact top-level batch manifest
+ immutable projection snapshot graph for the batch
+ current-head updates for exactly the batch projection keys
```

If the expected checkpoint does not exactly match current durable state, nothing is published.

Projection keys absent from a later batch are not deleted or rebound. They remain the current projection for their own evaluation identity until that identity is explicitly projected again.

## Existing semantic authorities remain unchanged

FC-030.2 must not redefine:

- `OperationalMetricEvaluationKey` identity;
- exact metric definition version identity;
- shift versus production-day period semantics;
- evaluation context identity;
- evaluation status/value/reason rules;
- projection evidence validation;
- source revision coherence;
- strict checkpoint advancement;
- exact batch-manifest equality;
- provider-neutral report filtering;
- provider-neutral report ordering; or
- reporting continuation semantics.

SQL is a persistence implementation of those authorities, not a second semantic model.

## Projection identity

The semantic current-projection identity is:

```text
ProjectionProcessorId
MachineId
PeriodId
DefinitionId = MetricKey + Version
EvaluationContextKey
```

`PeriodId` is exactly one of:

```text
Shift
    SiteId
    ShiftScheduleAssignmentId
    ShiftId
    StartsAtUtc
    EndsAtUtc

ProductionDay
    SiteId
    BusinessDate
```

`EvaluationContextKey` preserves the nullable exact identities currently carried by the domain contract:

```text
ProductionOrderId?
OperationId?
PartId?
ProductionLineId?
OperatorId?
```

No context field may be silently omitted from SQL identity merely because the current HTTP report filter does not expose every field.

## Why current rows alone are insufficient

`OperationalMetricDependencyProjectionEvidence` contains a full dependent `OperationalMetricProjection`, and that dependency must share the parent processor, machine, period, context, and source revision.

A later source revision may replace the current projection for that dependency key while a previously committed parent projection remains current for its own key. Therefore dependency evidence must not be reconstructed by following a mutable current-projection row.

Otherwise a parent projection could silently change historical evidence after a later dependency update.

The SQL model must therefore separate immutable projection snapshots from mutable current-head selection.

## Frozen persistence model

FC-030.2 uses five semantic table families.

```text
OperationalMetricProjectionCheckpoint
OperationalMetricProjectionCheckpointManifest
OperationalMetricProjectionSnapshot
OperationalMetricProjectionCurrent
OperationalMetricProjectionEvidence
```

`OperationalMetricProjectionEvidence` may be physically split into component-evidence and dependency-evidence tables when migration 005 is frozen. The semantic distinction is mandatory even if the exact physical table count changes during FC-030.2A review.

### 1. Current checkpoint

One current checkpoint exists per:

```text
ProjectionProcessorId
SourceAggregationProcessorId
SourceMetricInputStreamId
```

It persists the complete `MetricAggregationCheckpoint` identity, including source position.

The checkpoint is the compare-and-swap authority used by `CommitAsync`.

Initial commit requires no current checkpoint when `ExpectedCheckpoint` is null.

Subsequent commits require exact equality with `ExpectedCheckpoint` and a strictly greater proposed source position, matching the provider-neutral constructor contract.

### 2. Explicit checkpoint manifest

The current checkpoint has an explicit persisted manifest containing exactly the top-level `OperationalMetricEvaluationKey` values in that commit.

Manifest persistence is mandatory. It must not be reconstructed from:

- every snapshot at the same source revision, because nested dependency snapshots are not top-level batch members;
- every current head whose snapshot has the same source revision, because current-head history is not the batch-membership authority; or
- reporting query results, because reporting filters are not projection commit semantics.

Checkpoint-only commits persist an empty manifest.

### 3. Immutable projection snapshots

Every top-level committed projection and every nested dependency projection needed to reconstruct its evidence is persisted as an immutable snapshot node.

A snapshot identity must include enough information to distinguish the same semantic evaluation key at different source revisions. The semantic identity is:

```text
ProjectionProcessorId
OperationalMetricEvaluationKey
SourceAggregationProcessorId
SourceMetricInputStreamId
SourcePosition
```

A physical surrogate row id may be introduced for compact foreign keys, but it is storage identity only. A unique constraint over the complete semantic snapshot identity remains mandatory.

Each snapshot preserves at least:

```text
ProcessorId
complete OperationalMetricEvaluationKey
Status
Value?
Unit
ReasonCode?
ReasonOperandName?
complete SourceRevision
```

Snapshots are immutable after insertion. Re-persisting the same semantic snapshot identity is allowed only if its complete scalar/evidence representation is value-equivalent; conflicting representation is corruption and must fail rather than overwrite history.

### 4. Current projection heads

`OperationalMetricProjectionCurrent` maps:

```text
ProjectionProcessorId
OperationalMetricEvaluationKey
    -> immutable ProjectionSnapshot
```

A successful commit moves current heads for exactly the commit's top-level projection keys.

It does not delete, replace, or otherwise modify current heads for keys absent from the batch.

Nested dependency snapshots do not become current heads merely because they were persisted as evidence. A dependency projection becomes a current head only when it is itself a top-level projection in the commit manifest.

`ReadProjectionAsync` resolves the current head and reconstructs the immutable snapshot graph referenced by that head.

### 5. Projection evidence

Component evidence preserves, in deterministic operand-name order:

```text
OperandName
OperationalMetricAggregateSourceIdentity
SourceRevision
Dimension
Value
Unit
InputCount
FirstInputTimestamp
LastInputTimestamp
```

Dependency evidence preserves:

```text
OperandName
exact dependency DefinitionId
reference to immutable dependency ProjectionSnapshot
```

Dependency evidence must never reference `OperationalMetricProjectionCurrent`.

The SQL reader must reconstruct the same provider-neutral nested projection object graph and therefore re-run the existing domain constructors/validation boundary rather than returning a weaker SQL DTO as the public result.

## Atomic commit semantics

`SqlServerOperationalMetricProjectionStore.CommitAsync` must use one SQL transaction for the complete publication.

The governing flow is:

```text
begin transaction
    ↓
read current checkpoint for processor + source stream
    ↓
compare exactly with ExpectedCheckpoint
    ↓ mismatch
rollback / no mutation

match
    ↓
insert-or-verify immutable snapshot graph
    ↓
upsert current heads for top-level batch keys only
    ↓
replace persisted current checkpoint manifest with exact proposed manifest
    ↓
insert/update current checkpoint to proposed source revision
    ↓
commit
```

No partial publication is observable.

A transaction failure at any point must leave checkpoint, manifest, current heads, snapshots, and evidence in their previously committed state.

## Snapshot graph insertion and deduplication

A projection graph can contain the same dependency snapshot through multiple parent operands or parent projections. SQL persistence may deduplicate immutable snapshot nodes by complete semantic snapshot identity.

Deduplication must be deterministic and must not weaken equality checks.

The store must reject:

- conflicting scalar values for the same semantic snapshot identity;
- conflicting evidence for the same semantic snapshot identity;
- dependency references whose reconstructed domain object would violate existing projection invariants; or
- duplicate evidence operand names.

FC-030.2 must not rely only on application-side prevalidation for durable integrity where a practical SQL uniqueness/foreign-key constraint can encode structural identity.

## Reporting reads operate on current heads only

Reporting queries represent current durable reporting state, not historical snapshot history.

`ReadWindowAsync` and later SQL-backed `IOperationalMetricQueryReader` paths must start from current heads and project `OperationalMetricProjectionSummary` semantics.

Historical immutable snapshots exist to preserve exact evidence/revision identity; they are not independently returned by current reporting queries unless a future contract explicitly adds historical reporting.

The SQL report reader must preserve the existing filters:

```text
source selection: MachineId + ProjectionProcessorId
period scope: Shift OR ProductionDay
period range
exact MetricKey + Version selection
optional context filters
optional status selection
order: PeriodAscending / PeriodDescending
page size / continuation
```

The complete deterministic ordering authority remains `OperationalMetricReportOrdering`.

For equal primary period values, SQL ordering must preserve all existing tie breakers, including:

```text
MachineId
complete period identity
context identity
MetricKey ordinal
Version ordinal
```

String comparisons used for semantic identity/order must use an ordinal-compatible binary SQL collation. SQL default database collation must not redefine provider-neutral ordering.

## Reporting index direction

Migration 005 should provide indexes for the real read paths rather than attempting to optimize every possible identity combination.

At minimum, physical index design must support:

- current-head lookup by processor + evaluation key;
- shift-window reporting by selected processor/machine and `StartsAtUtc`;
- production-day reporting by selected processor/machine and `BusinessDate`;
- exact metric definition filtering;
- context/status filtering without changing semantics; and
- deterministic page seek/order keys.

Exact column order, include columns, and filtered-index choices are frozen in FC-030.2A after the physical table/column contract is written and measured against the existing report-query vocabulary.

## Continuation semantics

FC-030.2 does not create a new continuation-token format.

The SQL reader must honor the existing provider-neutral query/ordering contract and the current reporting continuation authority used by FC-028. If a SQL-specific seek key is needed internally, it must encode exactly the same last-item ordering identity and query compatibility semantics rather than exposing a provider-specific public token contract.

## Migration 005

FC-030.2 introduces exactly one new repository migration:

```text
005_<frozen-name>.sql
```

The exact name is frozen in FC-030.2A together with the physical schema.

Migration 005 is engine-owned and therefore must obey the standard migration lexical/transaction policy. It must not contain embedded `BEGIN/COMMIT/ROLLBACK/SAVE TRAN` control.

When 005 is added:

```text
repository catalog length              4 -> 5
LegacyPost004MigrationHistory          remains exactly 001..004
LegacyPost004SchemaDescriptor          remains unchanged
CurrentSchemaDescriptor                evolves to exact post-005 schema
OwnedObjectRecognitionSet              includes new migration-managed tables
```

### Compatibility behavior after migration 005 exists

```text
ledger 001..004 + post-004 schema
    -> MigrationPending

ledger 001..005 + exact post-005 Current schema
    -> Compatible

ledger absent + exact legacy post-004 schema
    -> LegacyAdoptionRequired

migration engine on exact legacy post-004 schema
    -> adopt frozen 001..004
    -> execute 005
    -> record 005
    -> validate Current
    -> commit atomically
```

Synthetic future-history tests that previously used migration id 5 must move to 6 or later once 005 is real. Tests that intentionally prove the frozen legacy 001–004 authority must remain exactly four migrations.

## Restart and replay semantics

SQL persistence must preserve the existing revision-driven behavior:

- after a successful commit, restart reads the persisted checkpoint and does not reprocess the same source revision;
- a later revision can replace the current head for the same evaluation key;
- a later revision can affect a different set of period/evaluation keys without deleting earlier current heads;
- checkpoint-only revisions remain valid;
- stale concurrent writers fail the expected-checkpoint comparison without partial publication; and
- replay of an already committed logical snapshot must not create conflicting historical evidence.

FC-030.2 does not redefine metric calculation replay semantics; it persists the existing projection runtime boundary.

## Construction slices

### FC-030.2A — Physical schema and migration-005 authority

Freeze:

- exact migration 005 name;
- exact table/column vocabulary;
- SQL types, lengths, precision, scale, nullability, and BIN2 collations;
- semantic unique keys;
- PK/FK/UQ/check constraints;
- indexes and deterministic reporting seek/order support;
- `CurrentSchemaDescriptor` post-005 update;
- owned-object recognition update;
- catalog/checksum evolution tests; and
- migration/runtime compatibility transition tests around 001–004 versus 001–005.

No store implementation yet.

### FC-030.2B — SQL projection commit/checkpoint store

Implement:

- exact expected-checkpoint compare-and-swap;
- strictly advancing source revision;
- checkpoint-only commit;
- explicit manifest persistence;
- immutable snapshot graph insertion;
- top-level current-head publication;
- atomic rollback on failure; and
- processor/source-stream isolation.

### FC-030.2C — Full projection detail reconstruction

Implement:

- current-head `ReadProjectionAsync`;
- scalar result reconstruction;
- component evidence reconstruction;
- immutable dependency graph reconstruction;
- exact source-revision reconstruction;
- deterministic evidence ordering; and
- provider-neutral constructor validation on read.

### FC-030.2D — SQL reporting window and query conformance

Implement:

- current-head reporting reads;
- shift and production-day ranges;
- source, exact metric version, context, and status filters;
- ascending/descending deterministic order;
- continuation/page behavior consistent with existing reporting contracts; and
- SQL-backed provider conformance against the in-memory authority.

### FC-030.2E — Restart, replay, concurrency, and real-SQL closure

Prove with real SQL Server:

- restart from persisted projection checkpoint;
- same-key replacement on newer revision;
- different-period-set revisions preserve untouched heads;
- checkpoint-only revision;
- stale writer rollback;
- transaction failure rollback;
- dependency evidence remains bound to the original immutable snapshot after later dependency updates;
- multiple processors remain isolated;
- current reporting never leaks non-current historical snapshots; and
- whole migration/runtime compatibility remains exact with 005.

## Hard boundary

FC-030.2 must not:

- change operational metric formulas or built-in definitions;
- change provider-neutral evaluation/projection/reporting contracts merely for SQL convenience;
- add historical-reporting APIs;
- persist a dependency as a mutable current-head reference;
- treat a batch manifest as a global replacement set;
- delete current projections absent from a later batch;
- introduce migration 006;
- introduce broader production-entry, roster, downtime-reason, incentive, or unrelated reporting schemas;
- wire automatic runtime migration side effects into API/Edge startup; or
- reopen FC-030.1 migration/compatibility semantics.
