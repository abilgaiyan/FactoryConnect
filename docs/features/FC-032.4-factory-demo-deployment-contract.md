## Governing invariant

> Migration, Edge, and API target the same explicitly provisioned FactoryConnect application database. FactoryConnect.Migrations is the sole DDL authority; Edge and API only verify database compatibility before starting.

No runtime host may improvise schema repair, invoke migrations implicitly, or fall back to InMemory when production SQL compatibility fails.

## D1 — Database provisioning boundary

FactoryConnect does not provision the SQL Server instance as an infrastructure concern.

The deployment operator / site IT provides the SQL Server instance, FactoryConnect application database, service/login identity, connectivity, permissions, and backup/recovery infrastructure.

FactoryConnect.Migrations establishes or advances the FactoryConnect-owned schema inside that configured application database.

The production connection string used by Migration, Edge, and API must address the FactoryConnect application database, not master.

**Status: FROZEN.**

## D2 — Shared production SQL authority

Migration, Edge, and API must target the same FactoryConnect application database.

Production persistence selection:

~~~text
Persistence__Provider=SqlServer
~~~

Shared SQL provider configuration:

~~~text
PersistenceProviders__SqlServer__ConnectionString=<FactoryConnect application database connection string>
PersistenceProviders__SqlServer__Startup__LockTimeout=00:00:30
~~~

FactoryConnect.Migrations binds PersistenceProviders:SqlServer. Edge and API additionally select Persistence:Provider=SqlServer.

Checked-in InMemory defaults are examples/development defaults only. They are not a production fallback.

**Status: FROZEN.**

## D3 — Isolated artifact layout

~~~text
FactoryConnect\
├── migrations\
├── edge\
├── api\
├── dashboard\
└── config\
~~~

Each artifact is independently published and runnable from its own directory. No executable may require the source repository, another artifact's working directory, or generated files from another publish directory.

Production configuration should remain outside artifact directories where practical.

Dashboard frontend assets are generated during build/publish. Node/npm are build-machine dependencies, not factory-server runtime dependencies after a successful publish.

**Status: FROZEN.**

## D4 — Permanent machine identity

Each physical pilot machine receives one permanent MachineId GUID.

The same GUID is reused by:

- MTConnect:Machines[n]:MachineId;
- observation/activity stream ownership;
- ProductionProcessing:Machines[n]:MachineId;
- API MTConnect/current-state inventory;
- Dashboard:Sources[n]:MachineId;
- SQL/reporting/current-state evidence.

Changing a MachineId after commissioning merely to align existing configuration or data is prohibited.

**Status: FROZEN.**

## D5 — Shared site schedule

~~~text
Pilot
7 machines
2 production lines
3 shared shifts
~~~

Per-machine production context belongs under ProductionProcessing:Machines[].

Shared shift authority belongs under ProductionProcessing:ShiftSchedules[].

Legacy machine-local Shift configuration is not valid production configuration.

A shared schedule may be site-scoped or line-scoped. Every configured machine must have an applicable schedule.

The checked-in 06:00 / 14:00 / 22:00 / 06:00 times are examples, not Gajra deployment authority. Exact local boundaries are site-confirmation inputs.

The timezone identifier is a target-inspection input. Runtime composition validates it with TimeZoneInfo.FindSystemTimeZoneById(...).

**Status: FROZEN.**

## D6 — Network and address authority

Hostnames, IP addresses, numeric ports, bindings, SQL endpoints, and MTConnect endpoints are explicit deployment-manifest inputs. Repository localhost values are not production authority.

| Flow | Initiator | Target | Authority |
|---|---|---|---|
| Migration → SQL | Migrations | SQL Server | production SQL connection string |
| Edge → SQL | Edge | SQL Server | same FactoryConnect application DB |
| API → SQL | API | SQL Server | same FactoryConnect application DB |
| Edge → MTConnect | Edge | machine/agent | MTConnect:Machines[n]:BaseUri |
| Dashboard → API | Dashboard | API | Dashboard:ReportingApiBaseAddress |
| Browser → Dashboard | factory LAN client | Dashboard | deployment binding / site infrastructure |

A direct browser-to-API route is not required for the initial pilot. Dashboard is the same-origin presentation/gateway host.

In Production the Dashboard API base address must not use loopback.

Firewall policy, TLS termination, OS service supervision, restart policy, log collection, and host hardening remain deployment/infrastructure responsibilities.

**Status: FROZEN.**

## D7 — Operational startup order

~~~text
SQL Server
    ↓
FactoryConnect application database
    ↓
FactoryConnect.Migrations
    ↓
FactoryConnect.Edge
    ↓
FactoryConnect.Api
    ↓
FactoryConnect.Dashboard
~~~

Migration before Edge/API is a hard compatibility dependency.

Edge before API is the operational commissioning order so acquisition/processing is live before reporting is exposed. API does not technically require the Edge process merely to pass its SQL startup gate.

Dashboard starts last because its useful upstream is API.

**Status: FROZEN.**

## D8 — Explicit migration operation

Migration is an explicit operator action.

~~~text
Exit 0  completed successfully
Exit 1  failed
Exit 2  canceled
~~~

Example operator invocation:

~~~powershell
$env:PersistenceProviders__SqlServer__ConnectionString = "<FactoryConnect application database connection string>"
$env:PersistenceProviders__SqlServer__Startup__LockTimeout = "00:00:30"
.\FactoryConnect.Migrations.exe

if ($LASTEXITCODE -ne 0) {
    throw "STOP: FactoryConnect migration failed."
}
~~~

Expected success message:

~~~text
FactoryConnect SQL migration completed successfully. Database schema is repository-current.
~~~

Edge/API startup may proceed only after successful migration.

**Status: FROZEN.**

## D9 — Verification, stop, and recovery policy

Deployment verification is fail-closed.

### Mandatory stop conditions

~~~text
STOP if migration fails or reports incompatible schema state.
STOP if Edge or API reports SQL startup/compatibility failure.
STOP if any configured MachineId differs across Edge/API/Dashboard authorities.
STOP if site timezone or shift-boundary resolution is not proven on target.
STOP if any configured machine lacks an applicable shared shift schedule.
STOP if an MTConnect endpoint does not represent the intended physical machine/device.
STOP if Dashboard Production configuration points at localhost or another loopback API endpoint.
~~~

### Allowed recovery

- correct deployment configuration;
- correct network, DNS, firewall, or SQL connectivity;
- correct SQL permissions/service identity;
- correct MTConnect endpoint/device key;
- use the site's approved database backup/restore process when actual database recovery is required;
- rerun the explicit migration executable after the underlying cause is understood and corrected;
- redeploy the same validated artifact set when artifact corruption or placement is the cause.

### Prohibited improvised recovery

- runtime auto-migration;
- manual CREATE, ALTER, or DROP merely to make startup pass;
- deleting migration-ledger rows;
- editing migration checksums;
- switching production persistence to InMemory;
- destructive rollback without an approved recovery design;
- replacing MachineId values to fit existing records;
- changing production timezone to UTC merely to bypass target-timezone validation;
- running older binaries against a newer database without explicit compatibility evidence.

**Status: FROZEN.**

## D10 — Configuration and secrets boundary

### Public deployment settings

Hostnames, ports, machine display names, MachineId, site/line identifiers, shift times, and MTConnect BaseUri / DeviceKey when allowed by site policy.

### Protected operational settings

SQL connection string, database credentials/service identity, and certificate/private-key material if later introduced.

Protected settings must use protected environment/service configuration or an equivalent site-approved secret mechanism when available. They should not be stored in ordinary checked-in JSON.

### Repository defaults

Repository defaults remain examples/development defaults only and never become production authority merely by being copied.

**Status: FROZEN.**

## Publish profiles

All deployable projects currently inherit net10.0. The repository does not freeze a global RuntimeIdentifier or self-contained mode.

The selected profile must be recorded in the release manifest.

### Profile A — all four self-contained win-x64

~~~powershell
dotnet publish src\FactoryConnect.Migrations\FactoryConnect.Migrations.csproj -c Release -r win-x64 --self-contained true -o .\release\FactoryConnect\migrations
dotnet publish src\FactoryConnect.Edge\FactoryConnect.Edge.csproj -c Release -r win-x64 --self-contained true -o .\release\FactoryConnect\edge
dotnet publish src\FactoryConnect.Api\FactoryConnect.Api.csproj -c Release -r win-x64 --self-contained true -o .\release\FactoryConnect\api
dotnet publish src\FactoryConnect.Dashboard\FactoryConnect.Dashboard.csproj -c Release -r win-x64 --self-contained true -o .\release\FactoryConnect\dashboard
~~~

### Profile B — explicitly mixed runtime requirements

A mixed profile is permitted only when the release manifest says so explicitly, for example:

~~~text
Migrations     win-x64 self-contained
Edge           win-x64 self-contained
API            win-x64 self-contained
Dashboard      framework-dependent net10.0
~~~

Framework-dependent Dashboard publish:

~~~powershell
dotnet publish src\FactoryConnect.Dashboard\FactoryConnect.Dashboard.csproj -c Release -o .\release\FactoryConnect\dashboard
~~~

A release package must not silently mix runtime assumptions.
