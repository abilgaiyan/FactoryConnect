# FC-030.1E.3 — API Startup Integration

## Status

Implemented on the feature branch; awaiting local verification and architecture review before closure/freeze.

FC-030.1E.1 and E.2 are closed/frozen. Edge startup integration remains outside this slice and belongs to E.4.

## Goal

Make API host activation depend on the provider-neutral persistence startup gate already frozen by E.1/E.2:

```text
WebApplicationBuilder
    → existing provider registration/finalization
    → builder.Build()
    → IPersistenceStartupGate.EnsureReadyAsync(...)
    → only after success: app.RunAsync()
```

The API host does not know whether the selected provider is SQL Server or InMemory and contains no migration, compatibility, provider-name, or SQL-specific logic.

## Central invariant

No API listener may become operational before the selected persistence startup gate succeeds.

Therefore a SQL migration failure, verification operational failure, non-compatible database result, or cancellation represented by the E.2 startup gate prevents all API surfaces from becoming externally reachable, including:

```text
/health
/openapi/*
/api/reporting/v1/*
```

Endpoint mapping may exist on the constructed `WebApplication`, but mapping is not activation. `RunAsync` is the activation boundary and is not invoked until gate success.

## Host integration

`Program.cs` retains the existing service composition and endpoint registrations.

The only lifecycle change is:

```text
var app = builder.Build();

map middleware/endpoints

ApiPersistenceStartup.RunAsync(
    app.Services,
    () => app.RunAsync(),
    startupCancellationToken)
```

`ApiPersistenceStartup` is an internal API-host sequencing helper. It:

1. resolves `IPersistenceStartupGate` from the built service provider;
2. awaits `EnsureReadyAsync`;
3. invokes the host-run delegate only after gate success;
4. does not catch or translate startup-gate failures; and
5. therefore preserves E.1/E.2 failure and cancellation semantics unchanged.

It contains no SQL-specific behavior.

## Cancellation

E.3 does not reinterpret cancellation.

Any `OperationCanceledException` emitted by the startup gate propagates unchanged and the host-run delegate is not invoked.

The current API executable supplies `CancellationToken.None` at this pre-host activation boundary. E.3 therefore proves propagation semantics when a token/cancellation exception reaches the helper but does not introduce an independent console-lifetime cancellation mechanism before ASP.NET Core host activation.

No E-layer exception wrapping is added by the API host.

## Tests

`ApiPersistenceStartupTests` proves:

1. successful readiness executes in exact `gate → host` order;
2. gate failure propagates unchanged and host activation is not invoked;
3. gate cancellation propagates unchanged and host activation is not invoked;
4. the default InMemory API still starts and `/health` remains reachable after gate success; and
5. replacing the resolved startup gate with a failing gate prevents `WebApplicationFactory<Program>` from creating an API client, proving host creation/activation cannot complete after readiness failure.

The E.3 tests do not require a real SQL Server instance. SQL migration/verification execution and cross-host serialization remain E.5 responsibilities.

## Hard boundary

E.3 does not:

- implement or duplicate SQL migration logic;
- implement or duplicate runtime compatibility verification;
- inspect `Persistence:Provider` in host code;
- introduce a second startup failure taxonomy;
- alter SQL configuration binding;
- alter E.2 configuration snapshot identity;
- modify Edge startup;
- introduce migration 005;
- introduce operational-metric/reporting SQL persistence; or
- change endpoint contracts.
