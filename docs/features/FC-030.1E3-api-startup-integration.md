## Goal

Make API host activation depend on the provider-neutral persistence startup gate already frozen by E.1/E.2:

```text
WebApplicationBuilder
    → existing provider registration/finalization
    → builder.Build()
    → establish pre-activation process-shutdown cancellation
    → IPersistenceStartupGate.EnsureReadyAsync(...)
    → dispose pre-activation shutdown registrations
    → only after success: app.RunAsync()
```

The API host does not know whether the selected provider is SQL Server or InMemory and contains no migration, compatibility, provider-name, or SQL-specific logic.

## Central invariant

No API listener may become operational before the selected persistence startup gate succeeds.

Therefore a SQL migration failure, verification operational failure, non-compatible database result, or cancellation represented by the E.2 startup gate prevents all API surfaces from becoming externally reachable, including:

```text
/health
/openapi/*
/api/reporting/v1/*
```

Endpoint mapping may exist on the constructed `WebApplication`, but mapping is not activation. `RunAsync` is the activation boundary and is not invoked until gate success.

## Host integration

`Program.cs` retains the existing service composition and endpoint registrations.

The lifecycle change is:

```text
var app = builder.Build();

map middleware/endpoints

ApiPersistenceStartup.RunAsync(
    app.Services,
    () => app.RunAsync())
```

`ApiPersistenceStartup` is an internal API-host sequencing helper. It:

1. resolves the pre-activation cancellation-registration factory;
2. establishes the process-shutdown cancellation token;
3. resolves `IPersistenceStartupGate` from the built service provider;
4. awaits `EnsureReadyAsync` with that token;
5. disposes the pre-activation shutdown registration in a `finally` block;
6. invokes the host-run delegate only after gate success; and
7. does not catch or translate startup-gate failures.

It contains no SQL-specific behavior.

## Pre-activation cancellation ownership

Before ASP.NET Core host activation, the normal host lifetime has not yet taken ownership of process shutdown signals. E.3 therefore establishes a narrow pre-activation cancellation window.

`ApiStartupCancellationRegistration` observes:

```text
Console.CancelKeyPress
    → request startup cancellation
    → suppress immediate process termination long enough for cancellation to propagate

SIGTERM when supported
    → request startup cancellation
    → suppress immediate signal termination long enough for cancellation to propagate
```

The registration exists only while the persistence startup gate is executing.

```text
gate succeeds or fails
    → dispose Console/SIGTERM registrations
    → ASP.NET Core normal lifetime owns shutdown after RunAsync begins
```

This prevents duplicate long-lived signal ownership and does not interfere with normal ASP.NET Core lifetime handling after activation.

Any `OperationCanceledException` emitted by C, D, or the startup gate propagates unchanged. The API layer does not wrap cancellation.

## Tests

`ApiPersistenceStartupTests` proves:

1. successful readiness executes in exact `gate → host` order;
2. pre-activation cancellation registration is disposed before host activation;
3. gate failure propagates unchanged and host activation is not invoked;
4. gate cancellation propagates unchanged and host activation is not invoked;
5. a cancelled pre-activation token reaches the startup gate and prevents host activation;
6. the default InMemory API still starts and `/health` remains reachable after gate success;
7. replacing the resolved startup gate with a failing gate prevents `WebApplicationFactory<Program>` from creating an API client; and
8. replacing the real pre-activation cancellation factory with an already-cancelled registration proves the real `Program` path delivers a cancelled token to the gate, propagates cancellation, and prevents API client/listener creation.

The E.3 tests do not require a real SQL Server instance. SQL migration/verification execution and cross-host serialization remain E.5 responsibilities.

## Hard boundary

E.3 does not:

- implement or duplicate SQL migration logic;
- implement or duplicate runtime compatibility verification;
- inspect `Persistence:Provider` in host code;
- introduce a second startup failure taxonomy;
- alter SQL configuration binding;
- alter E.2 configuration snapshot identity;
- modify Edge startup;
- introduce migration 005;
- introduce operational-metric/reporting SQL persistence; or
- change endpoint contracts.
