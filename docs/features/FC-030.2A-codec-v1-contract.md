# 1. Primitive canonical encodings

Unless a field below explicitly states otherwise, every multi-byte integer is encoded **big-endian**.

```text
UInt8       1 byte
UInt16      2 bytes, unsigned big-endian
UInt32      4 bytes, unsigned big-endian
UInt64      8 bytes, unsigned big-endian
Int32       4 bytes, two's-complement big-endian
Int64       8 bytes, two's-complement big-endian
Boolean     one byte: 0x00 false, 0x01 true; all other values invalid
```

## 1.1 Strings

Canonical string encoding is:

```text
UInt32 byteLength
byteLength bytes of strict UTF-8
```

Rules:

- UTF-8 has no BOM.
- Invalid UTF-8 is rejected.
- No Unicode normalization is performed.
- The exact .NET string code-point sequence is preserved.
- Length is the UTF-8 byte length, not character count.
- Fields whose domain contract forbids empty strings reject `byteLength = 0`.
- No NUL termination or padding is present.

## 1.2 Optional values

Canonical optional encoding is:

```text
0x00                    absent
0x01 + encoded value    present
```

Any tag other than `0x00` or `0x01` is invalid. A present string is still subject to the field's non-empty domain rule.

## 1.3 Guid V1 bytes

A Guid is encoded as exactly 16 bytes in **big-endian field order**:

```text
UInt32 A
UInt16 B
UInt16 C
8 remaining bytes unchanged and in their Guid field order
```

For canonical Guid text `00112233-4455-6677-8899-aabbccddeeff`, the V1 bytes are exactly:

```text
00 11 22 33 44 55 66 77 88 99 AA BB CC DD EE FF
```

On the target .NET runtime, `guid.TryWriteBytes(destination, bigEndian: true, out _)` is the preferred implementation when available. An implementation that does not call that API MUST produce exactly the same 16 bytes.

## 1.4 DateOnly

`DateOnly` is encoded as:

```text
Int32 DayNumber
```

where `DayNumber` is the exact .NET `DateOnly.DayNumber` value.

## 1.5 UTC DateTimeOffset

Only offset-zero timestamps are valid in these codecs.

A UTC `DateTimeOffset` is encoded as:

```text
Int64 utcTicks
```

where `utcTicks` is the number of 100-nanosecond ticks since `0001-01-01T00:00:00.0000000Z`, equivalent to the UTC `DateTime` ticks represented by the value.

A value whose offset is not `+00:00` is rejected before encoding and rejected when reconstructing persisted state.

## 1.6 UInt64 positions/revisions

Source positions and revisions are encoded as an 8-byte `UInt64`, big-endian. SQL persists the same logical value as `decimal(20,0)` with the existing `1..18446744073709551615` check where the domain requires a positive position/revision.

## 1.7 Decimal values

Operational metric/component decimal values are encoded inside dependency snapshots as their repository-canonical decimal **text**, then as a canonical string under section 1.1.

No binary decimal representation is introduced by FC-030.2A. The same canonical decimal formatting/parser authority already used by FactoryConnect durable aggregation persistence must be reused.

# 2. MachineOrderKey V1

`MachineOrderKey` is permanently defined by migration 005 as **V1**. There is no unstored, floating codec version.

For a `MachineId` Guid:

```text
MachineOrderKeyV1 = Guid V1 bytes from section 1.3
```

Therefore lexicographic SQL `binary(16)` comparison is equivalent to the field-by-field comparison used by `.NET Guid.CompareTo`:

```text
A as UInt32
then B as UInt16
then C as UInt16
then each of the remaining 8 bytes as unsigned bytes
```

## 2.1 SQL authority

`MachineOrderKey` MUST NOT be an independently trusted writer-supplied value.

Migration 005 shall define it as a deterministic persisted computed column from `MachineId`:

```sql
MachineOrderKey AS
    CONVERT(
        binary(16),
        REPLACE(CONVERT(char(36), MachineId), '-', ''),
        2)
    PERSISTED
```

The expression converts the canonical textual Guid hex sequence to display/field-order bytes, yielding exactly section 1.3.

If SQL Server metadata/conformance proves this exact expression cannot be persisted/indexed on the supported SQL Server target, implementation MUST stop and return to architecture review; it MUST NOT fall back silently to trusting writer bytes.

## 2.2 V1 conformance

The executable matrix must prove bytewise SQL ordering equals `.NET Guid.CompareTo` for:

- differences in each byte of field A;
- the A/B boundary;
- differences in each byte of field B;
- the B/C boundary;
- differences in each byte of field C;
- the C/tail boundary;
- each of the final eight bytes;
- high-bit transitions (`0x7F -> 0x80` and `0xFF`);
- `Guid.Empty`;
- the maximum all-`FF` Guid;
- pairs intentionally demonstrating legacy little-endian `Guid.ToByteArray()` order would disagree;
- a deterministic randomized corpus of at least 10,000 Guid pairs.

For every pair `x,y`:

```text
sign(x.CompareTo(y))
==
sign(SQL_BINARY_COMPARE(MachineOrderKeyV1(x), MachineOrderKeyV1(y)))
```

# 3. EvaluationKeyBinary V1

## 3.1 Envelope

The exact V1 prefix is:

```text
ASCII "FCEK"        4 bytes: 46 43 45 4B
TypeMarker          UInt8 = 0x01
CodecVersion        UInt16 = 0x0001
```

The codec version is therefore included **inside the hashed bytes**.

`EvaluationKeyHash` is:

```text
SHA-256(exact complete EvaluationKeyBinary bytes)
```

The projection table shall also persist:

```text
EvaluationKeyCodecVersion smallint NOT NULL
```

For migration 005 it MUST equal `1`, and it MUST equal the embedded `0x0001` version decoded from `EvaluationKeyBinary`.

## 3.2 Exact V1 field order

After the envelope, fields occur exactly in this order:

```text
1. MachineId
   Guid V1 bytes

2. PeriodKind
   UInt8
   0x01 = Shift
   0x02 = ProductionDay

3. PeriodSiteId
   canonical non-empty string

4. Period payload
   when Shift:
     ShiftScheduleAssignmentId    canonical non-empty string
     ShiftId                      canonical non-empty string
     ShiftStartsAtUtc             UTC DateTimeOffset encoding
     ShiftEndsAtUtc               UTC DateTimeOffset encoding
   when ProductionDay:
     ProductionBusinessDate       DateOnly encoding

5. ProductionOrderId
   canonical optional non-empty string

6. OperationId
   canonical optional non-empty string

7. PartId
   canonical optional non-empty string

8. OperatorId
   canonical optional non-empty string

9. MetricKey
   canonical non-empty string

10. DefinitionVersion
    canonical non-empty string
```

No field names, separators, padding, alignment bytes, or trailing checksum are present.

Unknown `PeriodKind` is rejected. Shift requires `EndsAtUtc > StartsAtUtc`. ProductionDay has no Shift payload bytes at all.

## 3.3 Decoder rules

A V1 decoder MUST:

1. require the exact `FCEK` magic;
2. require `TypeMarker = 0x01`;
3. require a supported embedded version;
4. dispatch to the reader for that exact version;
5. reject malformed primitive encodings;
6. reject invalid UTF-8;
7. reject invalid/empty domain identities;
8. reject an invalid period shape or interval;
9. consume the complete input;
10. reject any trailing byte.

Unknown versions are deterministic failures, never interpreted as V1.

## 3.4 Persisted-row mutual validation

Before any projection row may participate in reporting, projection reads, replay validation, or checkpoint manifest equality, the SQL provider must validate:

```text
SHA-256(EvaluationKeyBinary) == EvaluationKeyHash
embedded codec version == EvaluationKeyCodecVersion == 1
decoded MachineId == structured MachineId
decoded MachineId GuidV1 bytes == computed MachineOrderKey
decoded period == all structured period columns exactly
decoded context == all presence/value columns exactly
decoded MetricKey == structured MetricKey
decoded DefinitionVersion == structured DefinitionVersion
```

A mismatch is persisted-data corruption and fails the operation deterministically; it MUST NOT be normalized into “row missing”.

For reporting, integrity validation scope is every projection row belonging to the selected projection processor identities **before** date/context/status/seek filters are allowed to determine the returned page. This prevents corrupt structured ordering/filter columns from hiding a row before validation.

The provider may optimize this rule only if a later architecture change proves an equivalent database-enforced integrity mechanism. Migration 005 does not weaken it.

# 4. DependencySnapshotBinary V1

## 4.1 Envelope and hash authority

The exact V1 prefix is:

```text
ASCII "FCDS"        4 bytes: 46 43 44 53
TypeMarker          UInt8 = 0x02
CodecVersion        UInt16 = 0x0001
```

`DependencySnapshotCodecVersion` SQL column MUST equal `1` for V1.

The version is included inside the binary and therefore inside the hash:

```text
DependencySnapshotHash = SHA-256(exact complete DependencySnapshotBinary bytes)
```

## 4.2 Common substructures

### Projection processor identity

Encode the exact provider-neutral `OperationalMetricProjectionProcessorId` value as one canonical non-empty string.

### Metric input stream identity

Encode:

```text
MachineId       Guid V1 bytes
StreamKey       canonical non-empty string
```

### Aggregation source revision

Encode:

```text
MetricAggregationProcessorId  canonical non-empty string
MetricInputStreamId            stream identity above
Position                       UInt64
```

### Metric definition identity

Encode:

```text
MetricKey       canonical non-empty string
Version         canonical non-empty string
```

### Period identity

Use exactly the period payload defined in EvaluationKey V1 section 3.2: `PeriodKind`, `PeriodSiteId`, followed by the matching Shift or ProductionDay payload.

### Canonical blob

A nested canonical binary blob is encoded as:

```text
UInt32 byteLength
byteLength exact bytes
```

The length prefix is part of the parent hash authority.

## 4.3 Exact projection snapshot field order

After the `FCDS` envelope, encode exactly one complete `OperationalMetricProjection` in this order:

```text
1. ProjectionProcessorId
   canonical non-empty string

2. EvaluationKey
   canonical blob containing exact EvaluationKeyBinary V1 bytes

3. Status
   UInt8
   0x00 = Calculated
   0x01 = Unavailable
   0x02 = InsufficientEvidence

4. Value
   optional canonical decimal-text string

5. Unit
   canonical non-empty string

6. ReasonCode
   optional UInt8
   numeric value must be a currently supported provider-neutral reason enum value

7. ReasonOperandName
   optional canonical non-empty string

8. SourceRevision
   aggregation source revision substructure

9. ComponentEvidenceCount
   UInt32

10. ComponentEvidence[0..count-1]
    encoded in exact provider-neutral list order

11. DependencyEvidenceCount
    UInt32

12. DependencyEvidence[0..count-1]
    encoded in exact provider-neutral list order
```

Status/value/reason shape MUST satisfy the same durable projection invariant as the structured projection row:

```text
Calculated
  value present
  reason code absent
  reason operand absent

Unavailable / InsufficientEvidence
  value absent
  reason code present
```

Any invalid combination is rejected during decoding.

## 4.4 Component evidence V1

Each component evidence item is encoded exactly as:

```text
1. OperandName
   canonical non-empty string

2. SourceMachineId
   Guid V1 bytes

3. SourcePeriod
   canonical period identity substructure

4. ComponentKey
   canonical non-empty string

5. SourceRevision
   aggregation source revision substructure

6. MetricDimension
   UInt8, exact currently supported provider-neutral enum numeric value

7. Value
   canonical decimal-text string

8. Unit
   canonical non-empty string

9. InputCount
   UInt64, must be > 0

10. FirstInputTimestamp
    UTC DateTimeOffset encoding

11. LastInputTimestamp
    UTC DateTimeOffset encoding
```

`LastInputTimestamp` must be `>= FirstInputTimestamp`.

## 4.5 Dependency evidence V1

Each dependency evidence item is encoded exactly as:

```text
1. OperandName
   canonical non-empty string

2. DependencyDefinitionId
   metric definition identity substructure

3. NestedProjectionSnapshot
   canonical blob containing one complete FCDS snapshot
```

The nested snapshot must decode to a projection whose `EvaluationKey.DefinitionId` exactly equals `DependencyDefinitionId`.

Nested snapshot bytes include their own `FCDS` magic/type/version and are therefore independently canonical and hashable; no nested hash is added inside the parent payload.

## 4.6 Collection semantics

Component and dependency collections preserve provider-neutral list order exactly.

During every projection-snapshot decode:

- `OperandName` must be unique across both component and dependency evidence collections;
- duplicate component operands are rejected;
- duplicate dependency operands are rejected;
- cross-kind duplicate operands are rejected;
- no sorting is performed by the codec;
- count is the exact encoded count and every declared item must be present.

## 4.7 V1 safety limits

V1 freezes these decoder/writer bounds:

```text
maximum DependencySnapshotBinary payload         16 MiB (16,777,216 bytes)
maximum recursive dependency depth               64 projection snapshots
maximum component evidence items per projection  65,535
maximum dependency evidence items per projection 65,535
maximum total evidence nodes in one root decode   262,144
```

Depth counts the root projection as depth `1`. A nested dependency at root depth 64 is forbidden.

These bounds are checked before allocation whenever the encoded length/count makes that possible. Exceeding a bound is deterministic corruption/unsupported-state failure; partial decoding is forbidden.

If a future valid provider-neutral definition genuinely requires exceeding these frozen V1 limits, that requires a new reviewed codec version rather than silently changing V1.

## 4.8 Complete-input consumption

Every V1 decoder invocation is length-bounded by its containing blob.

A successful decode requires the reader position to equal the exact end of that bounded blob. Any extra byte, including zero padding, is rejected.

This rule applies independently to:

- root `DependencySnapshotBinary`;
- embedded `EvaluationKeyBinary` blob;
- every nested `FCDS` projection snapshot blob.

# 5. Version evolution policy

V1 is immutable once FC-030.2A freezes.

Future version policy is:

```text
writer
  emits exactly one configured current version

reader
  must continue to read every previously released version that can remain in durable storage

unknown version
  rejected deterministically

existing V1 bytes
  never reinterpreted under newer rules

hash
  always covers magic + type marker + embedded codec version + complete payload

SQL version column
  must equal the embedded version
```

A future V2 may change encoding only through a separately reviewed compatibility/migration decision. Introducing V2 does not permit removing V1 read support while V1 rows can still exist.

# 6. Validation order

## 6.1 Evaluation key row

Validation order is frozen:

```text
1. physical binary length/nonempty checks
2. SHA-256 recomputation and EvaluationKeyHash equality
3. magic + type marker
4. embedded version known and equals SQL EvaluationKeyCodecVersion
5. strict V1 decode with bounds/domain checks
6. complete-input consumption
7. decoded key versus structured projection columns
8. decoded MachineId versus computed MachineOrderKey
9. only then may the row enter filtering/order/seek/reconstruction
```

## 6.2 Dependency evidence row

Validation order is frozen:

```text
1. dependency physical shape + payload size bound
2. SHA-256 recomputation and DependencySnapshotHash equality
3. magic + type marker
4. embedded version known and equals DependencySnapshotCodecVersion
5. strict version-specific recursive decode with all bounds
6. complete-input consumption at every nesting level
7. provider-neutral projection invariants and duplicate-operand checks
8. structured DependencyMetricKey/DefinitionVersion header versus decoded definition
9. only then reconstruct OperationalMetricDependencyProjectionEvidence
```

Hash failure is reported before parsing untrusted payload structure. Unknown-version failure is reported only after the stored hash and envelope are valid.

# 7. Deterministic corruption behavior

A malformed persisted row MUST fail the current provider operation before returning a partial page, partial projection, replay success, or checkpoint equality result.

For FC-030.2 implementation, codec/integrity failures surface as `InvalidDataException` (or a provider-internal subtype of it) with deterministic artifact/row context. They are never converted to:

```text
missing projection
empty evidence
continuation exhausted
filter mismatch
checkpoint conflict
```

No reader repairs, rewrites, or normalizes corrupt durable state.
