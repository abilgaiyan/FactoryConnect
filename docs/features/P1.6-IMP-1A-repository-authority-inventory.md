## Concrete source references

- [Runtime](../../src/FactoryConnect.Core/ProductionContextProcessingRuntime.cs): resolves shifts/planned intervals for activity batches; derives facts; submits grouped outputs/inputs and next observation checkpoint.
- [Deriver](../../src/FactoryConnect.Core/Metrics/DurableMetricInputFactDeriver.cs): scheduled-duration fact for every eligibility interval; planned-duration only when true; state-duration by state, no state-specific key for Unknown; copies source references and eligibility into facts.
- [SQL context writer](../../src/FactoryConnect.Persistence.SqlServer/SqlServerProductionContextProcessingStore.cs): owns Serializable transaction, appends metric inputs, inserts immutable-by-identity output payloads with conflicting-content checks, advances checkpoint.
- [Output schema 004](../../src/FactoryConnect.Persistence.SqlServer/Sql/004_ProductionContextMetricInputHandoff.sql): output identity/payload records and latest checkpoint; no output-to-batch ledger in these table definitions.
- [Metric-input writer](../../src/FactoryConnect.Persistence.SqlServer/SqlServerMetricInputTransactionWriter.cs): allocates positions and compares existing complete fact payloads; source IDs are stored as fields.
- [Revision writer](../../src/FactoryConnect.Persistence.SqlServer/SqlServerMetricAggregationRevisionPublication.cs) and [schema 011](../../src/FactoryConnect.Persistence.SqlServer/Sql/011_DurableMetricAggregationRevisionLedger.sql): exact revision and affected period records.
- [Historical contribution reader](../../src/FactoryConnect.Persistence.SqlServer/SqlContainmentHistoricalContributionReader.cs): exact-cut registration/revision/membership verification in caller Serializable transaction.
- [Schedule interface](../../src/FactoryConnect.Abstractions/IPlannedProductionScheduleReader.cs) and [coverage model](../../src/FactoryConnect.Abstractions/OperationalMetricCoverageAssessment.cs).

Atomic co-commit is useful evidence of writer behavior, but the inspected output insert stores only identity and payload, not the complete batch manifest/expected-next checkpoint relation. Do not promote this runtime property into a persisted historical membership receipt without independent proof.

## Candidate historical binding path (not yet verified)

For an incorporated fact: aggregation processor + revision -> contribution at metric-input position -> fact eligibility/context IDs -> exact output payloads -> contextualized source observation processor/stream/position/instance/sequence.
Validate every join for machine, source identity, payload/hash, endpoints, period and classification. Matching IDs alone do not establish schedule completeness or absence of other outputs.

For non-running: inspect incorporated state-duration and scheduled-duration facts as candidate output references. The deriver emits scheduled-duration even for Unknown; these inputs may establish retained linkage but never establish non-running merely because running is absent.
For output authority with no incorporated metric fact, a dedicated historical membership receipt or equivalent independently retained publication evidence remains required by C1. Latest checkpoints and matching timestamps cannot supply that missing relation.
Do not conclude all non-running evidence lacks facts; the actual fact inventory must be inspected by key/state and source interval.

For schedule: assignment IDs and activity-derived planned facts identify candidate selections, but do not preserve complete planned/break/override content or approved empty selection in the inspected commit contract. Search deployed release/config archives only as candidate historical artifacts; a current or unbound copy cannot be admitted automatically.

## Proposed prospective binding specification for review

Reserve an immutable producer-publication receipt binding producer/observation stream, expected/next checkpoint, ordered contextualized/eligibility output identities and payload digests, exact metric fact IDs/assigned positions, historical schedule selection identity and classification/continuity versions.
The producer transaction must persist this receipt with outputs and inputs. Duplicate/retry content conflicts are rejected. New aggregation revisions must durably bind the exact admitted producer receipt/output subset used for authority, including source-only boundary/non-running evidence.
A producer batch can span multiple metric-input positions; aggregation cuts may split that batch. Do not admit its entire output set just because one fact is incorporated. Require explicit subset/dependency membership and closure rules for a cut; this is still an open detailed specification.
No migration/API/codec is selected here. This prospective relation cannot be backfilled as if it existed historically. Recovery/admission of old external artifacts requires separate provenance and versioning review.
