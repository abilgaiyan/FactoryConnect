## Goal

FC-030.1C introduces the deployment-side mechanism that converts a repository migration catalog plus a real SQL Server database into one serialized, transactionally committed migration history.

The governing execution flow is:

```text
open deployment connection
        ↓
begin Serializable transaction
        ↓
acquire Exclusive transaction-owned sp_getapplock
        ↓
resolve ledger object identity and object kind
        ↓
no object              non-table object              user table
    │                        │                           │
    │                        └─ MigrationLedgerSchemaInvalid
    │                                                    │
    │                                                    └─ validate exact ledger structure
    ↓
classify unledgered FactoryConnect-owned application schema
        ↓
Uninitialized         LegacyAdoptable         Partial/Incompatible
     │                      │                         │
     │                      │                         └─ reject, no mutation
     │                      │
     │                      └─ create ledger + record canonical 001–004
     │                         without rerunning historical DDL
     │
     └─ create ledger + execute 001→004 + record each canonical identity
        ↓
for an existing exact ledger: validate exact catalog prefix
        ↓
execute only pending catalog suffix
        ↓
validate candidate history against repository catalog
        ↓
validate live migration-managed schema against Current descriptor
        ↓
commit
```

All classification and mutation occurs after the migration lock is acquired.

## 1. Migration infrastructure is separate from migration-managed schema

FC-030.1B froze `LegacyPost004` and `Current` as the 13-table migration-managed application schema produced by migrations 001–004.

FC-030.1C does **not** add the migration ledger to those descriptors and does not add it to `SqlRepositorySchemaAuthority.OwnedObjects`.

```text
migration-managed application schema
    → SqlRepositorySchemaDescriptors.LegacyPost004
    → SqlRepositorySchemaDescriptors.Current
    → SqlRepositorySchemaAuthority.OwnedObjects

migration infrastructure
    → dedicated migration-ledger identity/schema contract
    → dedicated ledger object-kind resolver
    → dedicated ledger metadata reader/validator
```

The ledger is FactoryConnect-owned infrastructure, but it is not a historical migration artifact and must not make an otherwise exact post-004 application schema cease to equal the immutable legacy adoption descriptor.

Future application-schema migrations update `Current`; they do not redefine the ledger contract unless a separately reviewed infrastructure change explicitly does so.

## 2. Physical migration ledger contract

FC-030.1C freezes one ledger table:

```text
dbo.FactoryConnectMigrationHistory
```

Required columns:

```text
MigrationId        int                 NOT NULL
Name               nvarchar(128)       NOT NULL COLLATE Latin1_General_100_BIN2
CanonicalChecksum  char(64)            NOT NULL COLLATE Latin1_General_100_BIN2
AppliedAtUtc       datetimeoffset(7)    NOT NULL
```

Required key:

```text
PK_FactoryConnectMigrationHistory
PRIMARY KEY CLUSTERED (MigrationId ASC)
```

No default constraint is required for `AppliedAtUtc`; the migration engine writes it explicitly.

### Exact infrastructure shape

The ledger schema is exact FactoryConnect infrastructure state. Exactness includes the complete owned table shape, not only the four required columns.

For FC-030.1C the valid ledger table has exactly:

```text
the four required columns
PK_FactoryConnectMigrationHistory
no additional columns
no additional primary/unique constraints
no foreign keys
no check constraints beyond any explicitly frozen later in C.1
no ordinary indexes
no triggers
```

A same-name user table with any unexpected or mismatched owned artifact is `MigrationLedgerSchemaInvalid`. The engine never repairs, drops, or recreates an incompatible ledger.

The ledger reader orders history by `MigrationId ASC`; physical row order is never relied upon.

### Row semantics

Migration identity is exactly:

```text
MigrationId
Name
CanonicalChecksum
```

`AppliedAtUtc` is operational metadata and does not participate in migration identity.

The engine writes `AppliedAtUtc` from an injectable UTC time source. Every engine-written value must have UTC offset zero.

Existing rows with a non-zero `AppliedAtUtc` offset are invalid ledger history for FC-030.1C. The reader validates offset zero rather than silently normalizing an existing value.

`CanonicalChecksum` is exact 64-character hexadecimal text stored under `Latin1_General_100_BIN2`. Comparison is ordinal/BIN2 exact, including letter casing. The engine does not uppercase, lowercase, trim, or otherwise normalize ledger checksum text.

Every history insert is parameterized. Migration identity and timestamp values must never be interpolated into SQL text.

## 3. Ledger presence and object-kind resolution

Ledger presence must distinguish absence from an incompatible object occupying the ledger identity.

The resolver must not use only:

```sql
OBJECT_ID(..., N'U')
```

because that collapses a view, synonym, or other object kind into apparent absence.

Frozen decision:

```text
No object exists at dbo.FactoryConnectMigrationHistory
    → ledger absent

An object exists at that identity but is not a user table
    → MigrationLedgerSchemaInvalid

A user table exists at that identity
    → read and validate exact ledger structure
```

The implementation may use `sys.schemas` + `sys.objects`, `OBJECT_ID` without a type filter followed by object-type inspection, or an equivalent SQL Server catalog query, provided these three states remain distinguishable.

After acquiring the migration lock:

```text
ledger absent
    → classify unledgered application schema using FC-030.1B

ledger identity occupied by non-user-table object
    → MigrationLedgerSchemaInvalid

ledger user table + exact ledger schema
    → read exact ordered history

ledger user table + incompatible ledger schema
    → MigrationLedgerSchemaInvalid
```

Required real-SQL proofs include at least one view occupying the ledger identity and one synonym occupying the ledger identity. Both must be rejected explicitly as `MigrationLedgerSchemaInvalid`; neither may enter the unledgered classification path.

A ledger must never be silently dropped, recreated, or repaired.

## 4. Migration lock contract

Migration serialization uses SQL Server `sp_getapplock` with the frozen resource:

```text
FactoryConnect.SqlMigration
```

Required lock semantics:

```text
@LockMode     = 'Exclusive'
@LockOwner    = 'Transaction'
@DbPrincipal  = 'public'
```

The lock is acquired after the `Serializable` transaction begins and before ledger/schema classification.

The engine must inspect the `sp_getapplock` return code. Negative return codes are `MigrationLockAcquisitionFailure` and must not be interpreted as success or compatibility.

### Lock timeout

Deployment options expose a finite non-negative `TimeSpan` lock timeout.

Frozen conversion rules:

```text
TimeSpan < 0                     → reject options
TimeSpan == Timeout.InfiniteTimeSpan (-1 ms) → not supported / reject options
TimeSpan > Int32.MaxValue ms     → reject options
sub-millisecond positive value   → round up to 1 ms
whole/fractional milliseconds    → ceiling to the next integer millisecond
0                                → SQL Server zero-wait timeout
```

Infinite waiting is deliberately not supported by FC-030.1C. A deployment must have an explicit bounded lock wait.

Conversion is checked and deterministic; it must not truncate a positive sub-millisecond timeout to zero, overflow, or reinterpret an invalid value.

Transaction ownership means successful commit or rollback releases the lock. No separate unlock is part of the normal engine path.

## 5. Transaction boundary

One invocation owns one outer SQL transaction:

```text
IsolationLevel.Serializable
```

The transaction encloses:

```text
lock acquisition
ledger creation when needed
legacy adoption rows when needed
all pending migration SQL
all corresponding history inserts
final history validation
final Current-schema validation
```

Therefore one executor invocation has one commit point.

For a fresh installation of the current 001–004 catalog:

```text
create ledger
execute 001
insert row 001
execute 002
insert row 002
execute 003
insert row 003
execute 004
insert row 004
validate history
validate Current
commit
```

If any later step fails, none of the schema effects or history rows created by that invocation may remain committed.

For an already committed prefix, the prefix predates the current invocation and must survive rollback of the current invocation.

## 6. Fresh FactoryConnect installation

A database is fresh-installable only when:

```text
ledger absent
AND
FC-030.1B classification == Uninitialized
```

Unrelated customer/admin objects remain tolerated.

The engine then:

```text
creates exact ledger table
executes every repository migration in catalog order
submits each descriptor's exact CanonicalSql representation
inserts its exact frozen MigrationId/Name/Sha256Checksum with parameterized SQL
writes AppliedAtUtc from the injectable UTC time source
validates final history
validates live Current schema
commits
```

The executor must not rediscover or reread migration resource bytes independently of `SqlMigrationCatalog`; execution consumes the canonical representation already frozen by FC-030.1A.

## 7. Exact post-004 legacy adoption

A database may be adopted only when:

```text
ledger absent
AND
FC-030.1B classification == LegacyAdoptable
```

Adoption does not execute migrations 001–004.

Instead, under the already-held migration lock and outer transaction:

```text
create exact ledger table
insert canonical history row 001
insert canonical history row 002
insert canonical history row 003
insert canonical history row 004
validate history
validate Current schema
commit
```

The rows use the exact identities and checksums supplied by the repository catalog and parameterized history insertion.

Adoption must fail rather than infer history when the repository catalog is not exactly the historical 001–004 baseline expected by the current FC-030.1 implementation.

Before migration 005 exists this means the adoptable historical prefix is exactly all catalog entries 001–004.

When future migrations exist, adoption remains conceptually:

```text
exact LegacyPost004
→ record 001–004
→ execute pending 005+
```

but no 005+ path is introduced in FC-030.1C itself.

## 8. Partial/incompatible unledgered databases

When:

```text
ledger absent
AND
classification == PartialOrIncompatibleLegacy
```

FC-030.1C rejects without creating the ledger and without executing migration SQL.

No repair, best-effort completion, object deletion, or schema reconciliation is permitted.

## 9. Existing ledger and exact-prefix execution

When an exact ledger exists, FC-030.1C reads ordered history and determines the pending repository suffix needed for deployment execution.

Before executing pending migration SQL, committed rows must form an exact prefix of the current repository catalog by exact:

```text
MigrationId
Name
CanonicalChecksum
```

Invalid cases are rejected before DDL:

```text
duplicate/reordered/impossible history
identity mismatch
checksum mismatch including casing-only checksum difference
ledger contains a migration not represented by current catalog
history contains a gap rather than an exact catalog prefix
non-zero AppliedAtUtc offset
```

FC-030.1D later exposes the richer runtime compatibility taxonomy (`MigrationPending`, `DatabaseNewerThanSupported`, and so on). FC-030.1C needs deployment-side failures sufficient to prevent unsafe mutation; it must not collapse bad history into "pending" and continue.

### Valid-prefix behavior

A valid committed prefix is a supported deployment state. Only the pending suffix executes.

For the current catalog the required real-SQL prefix matrix is:

```text
exact empty ledger + no FC application schema
    → execute 001, 002, 003, 004

exact history/schema through 001
    → execute 002, 003, 004

exact history/schema through 002
    → execute 003, 004

exact history/schema through 003
    → execute 004

exact history/schema through 004
    → execute nothing; validate Current; success
```

Each prefix fixture must represent the genuine committed application-schema state produced by that prefix, not a synthetic history row placed over post-004 schema.

The through-002 case is mandatory because it proves grandfathered migration 003 can execute as the first pending migration of an already committed installation.

### Failure from a committed prefix

A committed prefix predates the current invocation. Therefore if pending-suffix execution fails:

```text
committed prefix remains durable
no pending migration from the failed invocation advances history
no partial schema from the failed pending migration remains committed
later pending migrations do not execute
```

A valid prefix plus structural drift that causes a pending migration to fail must preserve the committed prefix and reject without advancing history.

If history already equals the complete current catalog, the executor performs no migration SQL, validates `Current`, and commits successfully.

## 10. Grandfathered migration 003 and execution exception contract

`003_BindMetricInputFactMachine.sql` contains its own:

```sql
BEGIN TRANSACTION;
...
COMMIT TRANSACTION;
```

and on failure:

```sql
IF @@TRANCOUNT > 0
    ROLLBACK TRANSACTION;
THROW;
```

This exact historical SQL remains immutable.

### Success

Under the engine-owned outer transaction:

```text
outer transaction begins       @@TRANCOUNT = 1
003 BEGIN TRANSACTION           @@TRANCOUNT = 2
003 COMMIT TRANSACTION          @@TRANCOUNT = 1
engine remains transaction owner
003 history row is inserted
later migration work continues
outer commit makes all work durable
```

A real SQL Server test must prove successful 003 execution does not prematurely commit the outer migration invocation, including the valid-through-002 prefix path.

### Failure

SQL Server `ROLLBACK TRANSACTION` without a savepoint rolls back the entire transaction, not only the nested transaction level. Therefore failing 003 may invalidate/complete the engine's outer `SqlTransaction` before control returns to the executor.

FC-030.1C freezes one externally observable execution-failure contract:

```text
MigrationExecutionException
    MigrationId
    MigrationName
    InnerException = original provider/SQL exception
```

The executor does **not** rethrow a raw `SqlException` as its public deployment failure. It wraps the original provider exception exactly once at the migration boundary so migration identity is always available.

The original provider exception object is retained unchanged as `InnerException`; its own stack trace and provider-specific diagnostic data remain available there.

Cleanup is best-effort only:

```text
catch original provider/SQL migration exception
    ↓
construct the canonical MigrationExecutionException
    ↓
attempt rollback only if transaction state permits
    ↓
if rollback/transaction cleanup also fails
    → cleanup failure must not replace MigrationExecutionException
    → original provider exception remains its InnerException
    ↓
throw MigrationExecutionException
```

A cleanup failure may be attached as secondary diagnostic information if the implementation has a deterministic non-destructive mechanism, but it must never become the primary thrown exception and must never replace `InnerException`.

The engine must not attempt a history insert or a later migration after the migration command fails.

Required observable result for fresh-install 003 failure:

```text
MigrationExecutionException identifies 003
InnerException is the original 003 provider/SQL failure
no committed ledger table/history from the failed fresh invocation
no partial 003 schema
no later migration effects
subsequent invocation can retry from a clean committed state
```

Required observable result for failure when 001–002 were already committed before invocation:

```text
MigrationExecutionException identifies 003
committed 001–002 ledger/schema remain durable
no committed 003 row
no partial 003 schema
no 004 effects
subsequent invocation can retry from the committed 001–002 prefix
```

The failure proofs use real SQL Server behavior, not a mocked transaction abstraction.

## 11. Canonical execution invariant

FC-030.1A froze:

> the exact canonical bytes/text hashed by SHA-256 are the representation later submitted for execution.

FC-030.1C executes:

```text
SqlMigrationDescriptor.CanonicalSql
```

and inserts exact:

```text
SqlMigrationDescriptor.Sha256Checksum
```

No migration-specific file read, newline conversion, BOM handling, checksum casing conversion, or SQL transformation is allowed in the execution engine.

Migration 003 receives no textual rewrite to compensate for its embedded transaction behavior.

## 12. Final validation before commit

A successful mutating or no-op deployment invocation finishes by validating:

```text
exact ledger infrastructure shape
AND
ordered ledger history == repository catalog
AND
live migration-managed schema == SqlRepositorySchemaDescriptors.Current
```

The structural application-schema validation uses the existing FC-030.1B metadata reader/comparator.

The ledger is validated against the dedicated FC-030.1C infrastructure contract.

A final validation failure rolls back the current invocation and is not converted into successful migration completion.

## 13. Concurrency

Two deployment processes may enter concurrently, but only one may classify/mutate at a time.

Required proof:

```text
migrator A begins Serializable transaction
migrator A acquires Exclusive transaction-owned app lock
migrator B begins and waits on same resource
migrator A installs/adopts and commits
migrator B acquires lock afterward
migrator B re-reads committed ledger/schema state
migrator B performs no duplicate migration/adoption
both return success
```

The proof asserts one canonical history sequence and no duplicate rows or partial schema.

The second migrator must never rely on state observed before its lock acquisition.

## 14. Failure taxonomy owned by FC-030.1C

Public/runtime compatibility taxonomy remains FC-030.1D. FC-030.1C keeps deployment failures structurally distinguishable for tests and diagnostics:

```text
MigrationLockAcquisitionFailure
MigrationLedgerSchemaInvalid
MigrationHistoryInvalid
UnledgeredSchemaIncompatible
MigrationExecutionException
FinalSchemaValidationFailure
```

Exact type names other than the now-frozen `MigrationExecutionException` may be refined during construction, but failures requiring different operator action must not collapse into one generic migration error.

`MigrationExecutionException` is the sole migration-SQL execution wrapper and always exposes migration identity plus the original provider exception as `InnerException`.
