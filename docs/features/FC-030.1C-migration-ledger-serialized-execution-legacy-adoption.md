# FC-030.1C — Migration Ledger, Serialized Execution, and Legacy Adoption

## Status

**Architecture / construction contract frozen for implementation.**

Prerequisites:

```text
FC-030.1A  Repository Catalog & Canonical SQL       CLOSED / FROZEN
FC-030.1B  Schema Descriptor & Classification       CLOSED / FROZEN
FC-030.1C  Migration Ledger & Execution             ACTIVE
```

Hard boundary:

```text
NO migration 005
NO operational-metric SQL schema
NO reporting persistence schema
NO runtime-host migration side effects
NO runtime compatibility verifier implementation (FC-030.1D)
```

## Goal

FC-030.1C introduces the deployment-side mechanism that converts a repository migration catalog plus a real SQL Server database into one serialized, transactionally committed migration history.

The governing execution flow is:

```text
open deployment connection
        ↓
begin Serializable transaction
        ↓
acquire Exclusive transaction-owned sp_getapplock
        ↓
determine ledger presence and validate ledger shape
        ↓
if no ledger: read/classify FactoryConnect-owned schema
        ↓
Uninitialized         LegacyAdoptable         Partial/Incompatible
     │                      │                         │
     │                      │                         └─ reject, no mutation
     │                      │
     │                      └─ create ledger + record canonical 001–004
     │                         without rerunning historical DDL
     │
     └─ create ledger + execute 001→004 + record each canonical identity
        ↓
validate committed-candidate history against repository catalog
        ↓
validate live migration-managed schema against Current descriptor
        ↓
commit
```

All classification and mutation occurs after the migration lock is acquired.

## 1. Migration infrastructure is separate from migration-managed schema

FC-030.1B froze `LegacyPost004` and `Current` as the 13-table migration-managed application schema produced by migrations 001–004.

FC-030.1C does **not** add the migration ledger to those descriptors and does not add it to `SqlRepositorySchemaAuthority.OwnedObjects`.

This distinction is intentional:

```text
migration-managed application schema
    → SqlRepositorySchemaDescriptors.LegacyPost004
    → SqlRepositorySchemaDescriptors.Current
    → SqlRepositorySchemaAuthority.OwnedObjects

migration infrastructure
    → dedicated migration-ledger identity/schema contract
    → dedicated ledger reader/validator
```

The ledger is FactoryConnect-owned infrastructure, but it is not a historical migration artifact and must not make an otherwise exact post-004 application schema cease to equal the immutable legacy adoption descriptor.

Future application-schema migrations update `Current`; they do not redefine the ledger contract unless a separately reviewed infrastructure change explicitly does so.

## 2. Physical migration ledger contract

FC-030.1C freezes one ledger table:

```text
dbo.FactoryConnectMigrationHistory
```

Required columns:

```text
MigrationId        int                 NOT NULL
Name               nvarchar(128)       NOT NULL COLLATE Latin1_General_100_BIN2
CanonicalChecksum  char(64)            NOT NULL COLLATE Latin1_General_100_BIN2
AppliedAtUtc       datetimeoffset(7)    NOT NULL
```

Required key:

```text
PK_FactoryConnectMigrationHistory
PRIMARY KEY CLUSTERED (MigrationId ASC)
```

No default constraint is required for `AppliedAtUtc`; the migration engine writes it explicitly.

The ledger schema is exact infrastructure state. A table with the same name but incompatible columns/key/collation is not an adoptable or fresh ledger and must be rejected without attempting repair.

The ledger reader must order history by `MigrationId ASC`; physical row order is never relied upon.

`AppliedAtUtc` is operational metadata and does not participate in migration identity. Migration identity is:

```text
MigrationId
Name
CanonicalChecksum
```

## 3. Ledger presence and state

Ledger presence is resolved through SQL Server object identity, not string assumptions:

```sql
OBJECT_ID(
    QUOTENAME(N'dbo') + N'.' + QUOTENAME(N'FactoryConnectMigrationHistory'),
    N'U')
```

After acquiring the migration lock:

```text
ledger absent
    → classify unledgered application schema using FC-030.1B

ledger present + exact ledger schema
    → read exact ordered history

ledger present + incompatible ledger schema
    → explicit migration-infrastructure failure
```

A ledger must never be silently dropped, recreated, or repaired.

## 4. Migration lock contract

Migration serialization uses SQL Server `sp_getapplock` with the frozen resource:

```text
FactoryConnect.SqlMigration
```

Required lock semantics:

```text
@LockMode  = 'Exclusive'
@LockOwner = 'Transaction'
@DbPrincipal = 'public'
```

The lock is acquired after the `Serializable` transaction begins and before ledger/schema classification.

The engine must inspect the `sp_getapplock` return code. Negative return codes are migration-lock failures and must not be interpreted as success or compatibility.

The executor accepts an explicit lock timeout from its deployment-side options. Conversion to SQL Server milliseconds must reject values that cannot be represented safely; it must not silently overflow or reinterpret an invalid timeout.

Transaction ownership means successful commit or rollback releases the lock. No separate unlock is part of the normal engine path.

## 5. Transaction boundary

One invocation owns one outer SQL transaction:

```text
IsolationLevel.Serializable
```

The transaction encloses:

```text
lock acquisition
ledger creation when needed
legacy adoption rows when needed
all pending migration SQL
all corresponding history inserts
final history validation
final Current-schema validation
```

Therefore an invocation has one commit point.

For fresh installation of the current 001–004 catalog:

```text
create ledger
execute 001
insert row 001
execute 002
insert row 002
execute 003
insert row 003
execute 004
insert row 004
validate history
validate Current
commit
```

If any later step fails, none of the schema effects or history rows from that invocation may remain committed.

## 6. Fresh FactoryConnect installation

A database is fresh-installable only when:

```text
ledger absent
AND
FC-030.1B classification == Uninitialized
```

Unrelated customer/admin objects remain tolerated.

The engine then:

```text
creates exact ledger table
executes every repository migration in catalog order
submits each descriptor's exact CanonicalSql representation
inserts its exact frozen MigrationId/Name/Sha256Checksum
validates final history
validates live Current schema
commits
```

The executor must not rediscover or reread migration resource bytes independently of `SqlMigrationCatalog`; execution consumes the canonical representation already frozen by FC-030.1A.

## 7. Exact post-004 legacy adoption

A database may be adopted only when:

```text
ledger absent
AND
FC-030.1B classification == LegacyAdoptable
```

Adoption does not execute migrations 001–004.

Instead, under the already-held migration lock and outer transaction:

```text
create exact ledger table
insert canonical history row 001
insert canonical history row 002
insert canonical history row 003
insert canonical history row 004
validate history
validate Current schema
commit
```

The rows use the exact identities and checksums supplied by the repository catalog.

Adoption must fail rather than infer history when the repository catalog is not exactly the historical 001–004 baseline expected by the current FC-030.1 implementation.

Before migration 005 exists this means the adoptable historical prefix is exactly all catalog entries 001–004.

When future migrations exist, adoption remains conceptually:

```text
exact LegacyPost004
→ record 001–004
→ execute pending 005+
```

but no 005+ path is introduced in FC-030.1C itself.

## 8. Partial/incompatible unledgered databases

When:

```text
ledger absent
AND
classification == PartialOrIncompatibleLegacy
```

FC-030.1C must reject without creating the ledger and without executing any migration SQL.

No repair, best-effort completion, object deletion, or schema reconciliation is permitted.

## 9. Existing ledger behavior

When an exact ledger exists, FC-030.1C reads its ordered history and determines the pending repository suffix needed for deployment execution.

Before executing any pending migration, existing committed rows must form an exact prefix of the current repository catalog by:

```text
MigrationId
Name
CanonicalChecksum
```

Invalid cases are rejected before DDL:

```text
duplicate/reordered/impossible history
identity mismatch
checksum mismatch
ledger contains migration not represented by current catalog
history contains a gap rather than an exact catalog prefix
```

FC-030.1D later exposes the richer runtime compatibility taxonomy (`MigrationPending`, `DatabaseNewerThanSupported`, and so on). FC-030.1C needs only deployment-side explicit failures sufficient to prevent unsafe mutation; it must not collapse a bad existing history into "pending" and continue.

If history already equals the complete current catalog, the executor performs no migration SQL, validates `Current`, and commits successfully.

## 10. Grandfathered migration 003

`003_BindMetricInputFactMachine.sql` contains its own:

```sql
BEGIN TRANSACTION;
...
COMMIT TRANSACTION;
```

and on failure:

```sql
IF @@TRANCOUNT > 0
    ROLLBACK TRANSACTION;
THROW;
```

This exact historical SQL remains immutable.

### Success

Under the engine-owned outer transaction:

```text
outer transaction begins       @@TRANCOUNT = 1
003 BEGIN TRANSACTION           @@TRANCOUNT = 2
003 COMMIT TRANSACTION          @@TRANCOUNT = 1
engine remains transaction owner
003 history row is inserted
later migration work continues
outer commit makes all work durable
```

A real SQL Server test must prove successful 003 execution does not prematurely commit the outer migration invocation.

### Failure

SQL Server `ROLLBACK TRANSACTION` without a savepoint rolls back the entire transaction, not only the nested transaction level. Therefore a failing 003 may invalidate/complete the engine's outer `SqlTransaction` before control returns to the executor.

The executor must preserve the migration SQL exception as the primary failure.

Cleanup behavior is best-effort only:

```text
catch original migration exception
    ↓
attempt rollback only if appropriate
    ↓
if rollback/transaction cleanup also fails
    → do not replace original migration exception
    ↓
rethrow original failure preserving stack/identity
```

The engine must not attempt a history insert or later migration after the 003 command fails.

Required observable result:

```text
no committed ledger table/history from the failed fresh invocation
no partial 003 schema
no later migration effects
original 003 failure remains primary
subsequent invocation can retry from a clean committed state
```

The failure proof must use real SQL Server behavior, not a mocked transaction abstraction.

## 11. Canonical execution invariant

FC-030.1A froze:

> the exact canonical bytes/text hashed by SHA-256 are the representation later submitted for execution.

FC-030.1C therefore executes:

```text
SqlMigrationDescriptor.CanonicalSql
```

and inserts:

```text
SqlMigrationDescriptor.Sha256Checksum
```

No migration-specific file read, newline conversion, BOM handling, or SQL transformation is allowed in the execution engine.

Migration 003 receives no textual rewrite to compensate for its embedded transaction behavior.

## 12. Final validation before commit

A successful mutating or no-op deployment invocation must finish by validating both:

```text
ordered ledger history == repository catalog
AND
live migration-managed schema == SqlRepositorySchemaDescriptors.Current
```

The structural validation uses the existing FC-030.1B metadata reader/comparator.

The ledger itself is validated against the dedicated FC-030.1C ledger-schema contract.

A final validation failure rolls back the invocation and is not converted into successful migration completion.

## 13. Concurrency

Two deployment processes may enter concurrently, but only one may classify/mutate at a time.

Required proof:

```text
migrator A begins Serializable transaction
migrator A acquires Exclusive transaction-owned app lock
migrator B begins and waits on same resource
migrator A installs/adopts and commits
migrator B acquires lock afterward
migrator B re-reads committed ledger/schema state
migrator B performs no duplicate migration/adoption
both return success
```

The proof must assert one canonical history sequence and no duplicate rows or partial schema.

The second migrator must never rely on state observed before its lock acquisition.

## 14. Failure taxonomy owned by FC-030.1C

Public/runtime compatibility taxonomy remains FC-030.1D. FC-030.1C should nevertheless keep deployment failures structurally distinguishable for tests and diagnostics, including at least:

```text
MigrationLockAcquisitionFailure
MigrationLedgerSchemaInvalid
MigrationHistoryInvalid
UnledgeredSchemaIncompatible
MigrationExecutionFailure
FinalSchemaValidationFailure
```

Exact .NET type names may be refined during construction, but failures that imply different operator action must not be collapsed into one generic "migration failed" condition.

The original provider/SQL exception should be retained as inner/causal information for execution failures, and migration identity must be available in the migration-execution diagnostic.

## 16. Required executable acceptance matrix

At minimum FC-030.1C must prove with real SQL Server where database semantics are involved:

| Scenario | Expected result |
|---|---|
| No ledger + no FactoryConnect application schema + unrelated tables | Create ledger, execute canonical 001–004, exact history, exact Current, commit |
| No ledger + exact post-004 application schema | Create ledger, record canonical 001–004 without replaying DDL, commit |
| No ledger + partial/incompatible recognizable schema | Reject; no ledger created; no schema mutation |
| Ledger table present with incompatible infrastructure shape | Reject; no repair/DDL |
| Existing exact history 001–004 + exact Current | No migration re-execution; success |
| Existing history is not an exact catalog prefix | Reject before DDL |
| Existing history checksum differs | Reject before DDL |
| Fresh install executes descriptor SQL | Submitted SQL is descriptor `CanonicalSql`; inserted checksum is descriptor checksum |
| 003 succeeds inside outer transaction | Outer transaction remains active; final schema/history commit atomically |
| 003 fails | Original migration exception primary; no committed partial schema/history; no 004 |
| Invocation after failed 003 | Retry succeeds from committed pre-invocation state |
| Failure after an earlier migration/history insert in same invocation | Earlier schema/history work rolls back |
| Two concurrent migrators | One serialized migration sequence; second reclassifies after lock and does not duplicate work |
| App-lock return code is negative | Explicit lock-acquisition failure; no classification/mutation proceeds |
| Final Current descriptor does not match | Rollback and explicit final-schema failure |
