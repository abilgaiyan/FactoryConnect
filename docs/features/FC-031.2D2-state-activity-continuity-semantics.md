# FC-031.2D.2 — Preserve / Reset Instance-Transition Semantics

Status: DOCUMENTATION RECORD / REVIEW REQUIRED

Mode: Documentation-only authority inventory

Implementation authority: NOT AUTHORIZED

## 1. Scope

This record freezes the portable state/activity continuity calculation semantics for FC-031.2D.2.

It defines:

- coherent calculator starting-state classification;
- same-instance continuation;
- per-observation instance-transition detection;
- Preserve behavior;
- Reset behavior;
- state/activity output semantics at instance boundaries;
- batching invariance;
- `LastConsumedInstanceId` derivation;
- continuity-policy reference stability;
- no-input/no-advance behavior; and
- coherence requirements that later FC-031.2D.3 atomic publication must carry.

This record does not authorize:

- `MachineStateActivityProcessor` mutation;
- `MachineStateActivityProjection` or projection-store mutation;
- evaluation-authority provider implementation;
- atomic projection/output/authority publication implementation;
- FC-031.2D.4 failure or competing-CAS proof;
- FC-031.2D.5 provider composition;
- SQL persistence;
- current-state readers;
- API work; or
- dashboard work.

The separation remains:

```text
2D.2  continuity calculation semantics
2D.3  atomic projection / derived-output / authority publication
2D.4  failure, replay, and competing-CAS proof
2D.5  provider composition and whole-slice conformance
```

## 2. Existing FC-024 working context

The existing state/activity processor evaluates mapped observations using a working context containing:

```text
Signals
State
ActiveState
ActiveStartedAt
```

With no prior projection, the bootstrap values are:

```text
Signals          empty
State            Unknown
ActiveState      null
ActiveStartedAt  null
```

The existing FC-024 processor restores all four fields from an existing projection, applies each mapped signal, evaluates the resulting signal snapshot, emits a state change only when the evaluated state differs, and advances the projection through the greatest incorporated mapped durable position.

`InstanceId` is currently carried by durable derived-output envelopes but is not persisted in the FC-024 projection and does not currently participate in state evaluation. FC-031.2D.2 therefore makes instance identity an explicit continuity-calculation input through `EvaluationAuthority.LastConsumedInstanceId`.

## 3. Coherent starting-state classification

Before applying any newly incorporated mapped input, the continuity calculator MUST classify its restored state.

### 3.1 Fresh start

```text
MachineStateActivityProjection absent
EvaluationAuthority absent
```

This state is valid.

The calculator starts from:

```text
Signals          empty
State            Unknown
ActiveState      null
ActiveStartedAt  null
prior instance   absent
```

No prior `LastConsumedInstanceId` exists.

### 3.2 Established continuation

```text
MachineStateActivityProjection present
EvaluationAuthority present
```

Continuation is valid only when all of the following agree:

```text
Projection.ProcessorId
    == EvaluationAuthority.StateProcessorId

Projection.StreamId
    == EvaluationAuthority.ObservationStreamId

Projection.Position
    == EvaluationAuthority.EvaluatedThrough

Projection.State
    == EvaluationAuthority.MachineState
```

When valid:

- signal/state/activity working context is restored from the projection;
- `LastConsumedInstanceId` is restored from `EvaluationAuthority`; and
- same-instance or instance-transition calculation may continue.

### 3.3 Incoherent starting state

Any of the following is incoherent:

```text
projection present, authority absent
projection absent, authority present
processor identities differ
stream identities differ
projection position differs from EvaluatedThrough
projection state differs from EvaluationAuthority.MachineState
```

The calculator MUST fail before applying any mapped input.

An incoherent start MUST:

```text
emit no state-change output
emit no activity-period output
produce no new projection
produce no new EvaluationAuthority
mutate nothing
```

FC-031.2D.2 defines the semantic precondition only. Failure representation and atomic mutation guarantees remain later-slice concerns.

## 4. Legacy projection adoption is prohibited

A pre-FC-031 `MachineStateActivityProjection` without matching `EvaluationAuthority` is not implicitly adoptable by the continuity calculator.

The calculator MUST NOT:

- infer `LastConsumedInstanceId` from the next mapped observation;
- assume the next mapped observation belongs to the same instance;
- treat projection presence as implicit Preserve behavior;
- fabricate `EvaluationAuthority` for an existing legacy projection; or
- invent any migration/bootstrap interpretation not defined by this record.

Intentional adoption of a pre-FC-031 projection requires a separately authorized and explicitly defined bootstrap/migration rule.

## 5. Observation-order authority and boundary detection

Newly incorporated mapped observations are evaluated in strictly increasing durable-position order.

For each newly incorporated observation, the calculator compares that observation's `InstanceId` with the working `LastConsumedInstanceId` before applying the observation's mapped signal.

Conceptually:

```text
for each newly incorporated mapped input in durable-position order

    if prior evaluated input exists
       and input.InstanceId != working LastConsumedInstanceId
        apply the configured Preserve or Reset boundary

    apply mapped signal
    evaluate resulting snapshot
    derive outputs

    working LastConsumedInstanceId = input.InstanceId
    working EvaluatedThrough       = input.Position
```

Boundary classification occurs before signal application so Reset cannot accidentally evaluate new-instance input against prior-instance signal evidence.

## 6. Same-instance continuation

When the next mapped observation has the same `InstanceId` as the working `LastConsumedInstanceId`, ordinary FC-024 continuation semantics apply.

The calculator preserves:

```text
Signals
State
ActiveState
ActiveStartedAt
```

It then:

1. applies the mapped signal;
2. evaluates the complete working signal snapshot;
3. emits derived output only if the evaluated state differs from the working state; and
4. advances `EvaluatedThrough` and `LastConsumedInstanceId` to the incorporated observation.

An unchanged evaluated state does not restart the active period.

## 7. Preserve semantics

When `InstanceId` changes under `StateContinuityMode.Preserve`, the complete evaluator context survives the boundary:

```text
Signals          retained
State            retained
ActiveState      retained
ActiveStartedAt  retained
```

The first observation from the new instance is then applied normally to that retained context.

The instance boundary itself does not synthesize a state transition. A transition exists only if evaluation after applying the new-instance observation changes the working state.

### 7.1 Preserve cross-instance activity completion

If the retained context contains an open activity and new-instance evidence changes the state, completing that retained activity at the transition-causing observation's timestamp is intentional.

Preserve asserts trusted continuity across the instance boundary, so the existing FC-024 completion rule remains authoritative for this case.

### 7.2 Closing-observation envelope attribution

A durable output produced by the transition retains the existing FC-024 envelope convention:

```text
output.Position   = closing observation Position
output.InstanceId = closing observation InstanceId
output.Sequence   = closing observation Sequence
```

Therefore an activity may have begun while processing an earlier acquisition instance and be completed by evidence carried by a later instance; the durable completion envelope is attributed to the later observation that supplied the closing evidence.

## 8. Reset semantics

When `InstanceId` changes under `StateContinuityMode.Reset`, the boundary creates a fresh continuity epoch before the first new-instance observation is applied:

```text
Signals          := empty
State            := Unknown
ActiveState      := null
ActiveStartedAt  := null
```

Any prior open activity is abandoned. Reset MUST NOT manufacture an end timestamp and MUST NOT emit a completed activity period merely because the acquisition instance changed.

The first new-instance observation is then applied to the fresh signal context and evaluated normally.

### 8.1 Reset state/output rule

The exact baseline behavior is:

```text
baseline state = Unknown

first evaluation == Unknown
    → no transition
    → ActiveState remains null

first evaluation != Unknown
    → emit Unknown → evaluated state
    → ActiveState = evaluated state
    → ActiveStartedAt = observation timestamp
```

`ActiveState` is not a special subset of machine states. Under existing FC-024 semantics, every actual state transition establishes the newly evaluated state as `ActiveState` and establishes the transition-causing observation timestamp as `ActiveStartedAt`.

Normal later transitions retain existing FC-024 behavior, including a later transition to `Unknown`.

Reset itself does not emit a synthetic `old-state → Unknown` transition and does not complete the prior open activity.

## 9. Multiple instance transitions within one batch

Continuity mode is applied independently at every observed instance boundary, not once per invocation or once per batch.

For example:

```text
position 10  instance 100
position 11  instance 100
position 12  instance 101   ← boundary
position 13  instance 101
position 14  instance 102   ← boundary
position 15  instance 102
```

The boundary policy applies before position 12 and again before position 14.

Each observation is evaluated in durable-position order against the working state produced by all preceding incorporated observations and any boundary action that immediately precedes it.

## 10. Batching invariance

Batch boundaries have no semantic authority.

Given the same initial coherent state, continuity policy, and ordered mapped inputs, processing the inputs in one invocation or partitioning them across multiple invocations MUST produce the same logical state/activity result and final continuity state.

Durable-position ordering is authoritative for calculation order.

FC-031.2D.2 does not introduce a new timestamp-monotonicity requirement. Activity timestamps continue to follow existing FC-024 semantics: transition/activity timestamps come from the mapped observation whose evaluation causes the transition, while durable-position ordering determines evaluation order.

## 11. `LastConsumedInstanceId` derivation

For every successful logical evaluation result:

```text
EvaluationAuthority.LastConsumedInstanceId
    = InstanceId of the mapped durable observation
      at EvaluationAuthority.EvaluatedThrough
```

It is not derived from:

- latest acquisition contact;
- latest raw observation;
- the final supplied batch element unless that element was actually incorporated;
- a generic processing checkpoint; or
- inferred legacy state.

Only a mapped durable observation actually incorporated into evaluation can advance `LastConsumedInstanceId`.

## 12. Continuity-policy stability

One logical evaluation publication is calculated under exactly one resolved `CurrentStateContinuityPolicy`.

The policy's `CurrentStatePolicyReference` is stable for the whole logical calculation, including every instance boundary encountered while calculating that publication.

The resulting `EvaluationAuthority.AppliedContinuityPolicy` MUST equal the reference of the policy used to calculate the result.

A retry of the same logical publication MUST retain the same policy reference. A changed policy reference at the same `EvaluatedThrough` is not an exact replay under the frozen FC-031.2D.1 publication algebra.

How policy resolution is composed is outside FC-031.2D.2; this record freezes only the requirement that the resolved policy and reference remain stable for one logical publication.

## 13. No-input / no-advance semantics

When no newly incorporated mapped input advances evaluation:

```text
no instance-transition policy is applied
no evaluator state changes
no state-change output is derived
no activity-period output is derived
no new logical EvaluationAuthority is created
no authority revision churn is permitted
```

This includes an empty invocation and an invocation whose supplied durable positions are all already incorporated.

FC-031.2D.1 lost-ack recovery remains distinct: replay of an already-determined logical publication is recovery of that publication, not a new continuity calculation.

## 14. Derived-output semantics summary

### Same instance

```text
retain complete working context
apply observation
evaluate
emit transition/activity output only on actual state change
```

### Different instance + Preserve

```text
retain complete working context
apply first new-instance observation
evaluate
if state changes:
    emit normal state transition
    complete retained activity at closing observation timestamp when one is open
```

### Different instance + Reset

```text
clear signal evidence
abandon prior open activity
set baseline State = Unknown
set ActiveState = null
set ActiveStartedAt = null
apply first new-instance observation
evaluate
if result == Unknown:
    emit nothing
if result != Unknown:
    emit Unknown → result
    set ActiveState = result
    set ActiveStartedAt = observation timestamp
```

## 15. Coherence requirements carried into FC-031.2D.3

FC-031.2D.2 does not define the atomic publication mechanism, but it freezes the logical values that later FC-031.2D.3 publication must keep coherent.

For an accepted logical evaluation publication:

```text
Projection.ProcessorId
    == EvaluationAuthority.StateProcessorId

Projection.StreamId
    == EvaluationAuthority.ObservationStreamId

Projection.Position
    == EvaluationAuthority.EvaluatedThrough

Projection.State
    == EvaluationAuthority.MachineState

EvaluationAuthority.LastConsumedInstanceId
    == InstanceId of the incorporated mapped observation at EvaluatedThrough

EvaluationAuthority.AppliedContinuityPolicy
    == reference of the continuity policy used for the calculation
```

The following must all describe one transition calculation:

```text
Projection.Signals
Projection.State
Projection.ActiveState
Projection.ActiveStartedAt
derived state-change outputs
derived activity-period outputs
EvaluationAuthority semantic fields
```

FC-031.2D.1 already requires later integration to publish projection, derived outputs, and accepted evaluation authority within one provider-owned atomic publication boundary. The mechanism and failure behavior remain FC-031.2D.3 and FC-031.2D.4 concerns respectively.
