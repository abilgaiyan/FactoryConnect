# FC-031.2D.2 — Preserve / Reset Instance-Transition Semantics

Status: CLOSED / FROZEN

Mode: Documentation-only authority inventory

Implementation authority: NOT AUTHORIZED

## 1. Scope

This record freezes the portable state/activity continuity calculation semantics for FC-031.2D.2.

It defines:

- coherent calculator starting-state classification;
- prohibition on implicit legacy-projection adoption;
- same-instance continuation;
- per-observation instance-transition detection;
- Preserve behavior;
- Reset behavior;
- state/activity output semantics at instance boundaries;
- batching invariance;
- `LastConsumedInstanceId` derivation;
- continuity-policy reference stability;
- no-input/no-advance behavior; and
- coherence requirements that later FC-031.2D.3 atomic publication must carry.

This record does not authorize:

- `MachineStateActivityProcessor` mutation;
- `MachineStateActivityProjection` or projection-store mutation;
- evaluation-authority provider implementation;
- atomic projection/output/authority publication implementation;
- FC-031.2D.4 failure or competing-CAS proof;
- FC-031.2D.5 provider composition;
- SQL persistence;

- API work; or
- dashboard work.

The separation remains:

```text
2D.2  continuity calculation semantics
2D.3  atomic projection / derived-output / authority publication

2D.5  provider composition and whole-slice conformance
```

## 2. Existing FC-024 working context

The existing processor's working context is:

```text
Signals
State
ActiveState
ActiveStartedAt
```

With no prior projection:

```text
Signals          empty
State            Unknown
ActiveState      null
ActiveStartedAt  null
```

The FC-024 processor restores all four fields from an existing projection, applies each mapped signal, evaluates the resulting signal snapshot, emits a state change only when the evaluated state differs, and advances through the greatest incorporated mapped durable position.

`InstanceId` is currently carried by durable derived-output envelopes but is not persisted in the FC-024 projection and does not participate in state evaluation. FC-031.2D.2 therefore uses `EvaluationAuthority.LastConsumedInstanceId` as the prior authoritative instance identity.

## 3. Coherent starting-state classification

Before applying any newly incorporated mapped input, the continuity calculator MUST classify its restored state.

### 3.1 Fresh start

```text
MachineStateActivityProjection absent
EvaluationAuthority absent
```

This is valid. Start from:

```text
Signals          empty
State            Unknown
ActiveState      null
ActiveStartedAt  null
prior instance   absent
```

### 3.2 Established continuation

```text
MachineStateActivityProjection present
EvaluationAuthority present
```

Continuation is valid only when:

```text
Projection.ProcessorId
    == EvaluationAuthority.StateProcessorId

Projection.StreamId
    == EvaluationAuthority.ObservationStreamId

Projection.Position
    == EvaluationAuthority.EvaluatedThrough

Projection.State
    == EvaluationAuthority.MachineState
```

When valid:

- signal/state/activity context is restored from the projection;
- `LastConsumedInstanceId` is restored from `EvaluationAuthority`; and
- same-instance or instance-transition calculation may continue.

### 3.3 Incoherent starting state

Any of the following is incoherent:

```text
projection present, authority absent
projection absent, authority present
processor identities differ
stream identities differ
projection position differs from EvaluatedThrough
projection state differs from EvaluationAuthority.MachineState
```

The calculator MUST fail before applying any mapped input and MUST:

```text
emit no state-change output
emit no activity-period output
produce no new projection
produce no new EvaluationAuthority
mutate nothing
```

FC-031.2D.2 freezes this semantic precondition only. Failure representation and atomic mutation mechanics remain later-slice concerns.

## 4. Legacy projection adoption is prohibited

A pre-FC-031 `MachineStateActivityProjection` without matching `EvaluationAuthority` is not implicitly adoptable.

The calculator MUST NOT:

- infer `LastConsumedInstanceId` from the next mapped observation;
- assume the next observation belongs to the same instance;
- treat projection presence as implicit Preserve behavior;
- fabricate `EvaluationAuthority` for an existing projection; or
- invent an unspecified migration/bootstrap interpretation.

Intentional adoption of a pre-FC-031 projection requires a separately authorized and explicitly defined bootstrap/migration rule.

## 5. Observation-order authority and boundary detection

New mapped observations are evaluated in strictly increasing durable-position order.

For every newly incorporated observation, compare its `InstanceId` with the working `LastConsumedInstanceId` before applying the mapped signal:

```text
for each newly incorporated mapped input in durable-position order

    if prior evaluated input exists
       and input.InstanceId != working LastConsumedInstanceId
        apply Preserve or Reset boundary

    apply mapped signal
    evaluate resulting snapshot
    derive outputs

    working LastConsumedInstanceId = input.InstanceId
    working EvaluatedThrough       = input.Position
```

Boundary classification occurs before signal application so Reset cannot evaluate new-instance evidence against retained prior-instance signal evidence.

## 6. Same-instance continuation

When the next observation has the same `InstanceId` as the working `LastConsumedInstanceId`, ordinary FC-024 continuation applies.

Retain:

```text
Signals
State
ActiveState
ActiveStartedAt
```

Then:

1. apply the mapped signal;
2. evaluate the complete working snapshot;
3. emit derived output only if evaluated state differs from working state; and
4. advance `EvaluatedThrough` and `LastConsumedInstanceId` to the incorporated observation.

An unchanged state does not restart the active period.

## 7. Preserve semantics

When `InstanceId` changes under `StateContinuityMode.Preserve`, retain the complete evaluator context:

```text
Signals          retained
State            retained
ActiveState      retained
ActiveStartedAt  retained
```

Apply the first new-instance observation normally to that retained context.

The instance boundary itself does not synthesize a state transition. A transition exists only if evaluation after applying the new-instance observation changes the working state.

### 7.1 Preserve cross-instance activity completion

If a retained activity is open and new-instance evidence changes state, completing that retained activity at the transition-causing observation's timestamp is intentional. Preserve asserts trusted continuity across the instance boundary, so the existing FC-024 completion rule remains authoritative.

### 7.2 Closing-observation envelope attribution

Any durable output produced by that transition retains the existing FC-024 envelope convention:

```text
output.Position   = closing observation Position
output.InstanceId = closing observation InstanceId
output.Sequence   = closing observation Sequence
```

An activity may therefore begin under an earlier instance and be completed by later-instance evidence; the durable completion envelope belongs to the observation that supplied the closing evidence.

## 8. Reset semantics

When `InstanceId` changes under `StateContinuityMode.Reset`, establish a fresh continuity epoch before applying the first new-instance observation:

```text
Signals          := empty
State            := Unknown
ActiveState      := null
ActiveStartedAt  := null
```

Any prior open activity is abandoned. Reset MUST NOT manufacture an end timestamp and MUST NOT emit a completed activity period merely because the acquisition instance changed.

Then apply the first new-instance observation and evaluate normally.

### 8.1 Exact Reset state/output rule

```text
baseline state = Unknown

first evaluation == Unknown
    → no transition
    → ActiveState remains null

first evaluation != Unknown
    → emit Unknown → evaluated state
    → ActiveState = evaluated state
    → ActiveStartedAt = observation timestamp
```

`ActiveState` is not a special subset of machine states. Under existing FC-024 behavior, every actual state transition establishes the newly evaluated state as `ActiveState` and the transition-causing observation timestamp as `ActiveStartedAt`.

Normal later transitions retain existing FC-024 behavior, including a later transition to `Unknown`.

Reset itself does not emit a synthetic `old-state → Unknown` transition and does not complete the prior open activity.

## 9. Multiple instance transitions within one batch

Continuity mode is applied independently at every observed instance boundary, not once per invocation or batch.

Example:

```text
position 10  instance 100
position 11  instance 100
position 12  instance 101   ← boundary
position 13  instance 101
position 14  instance 102   ← boundary
position 15  instance 102
```

Apply the policy before positions 12 and 14 independently. Each observation is evaluated against the working result of all preceding incorporated observations and any boundary action immediately preceding it.

## 10. Batching invariance and timestamp semantics

Batch boundaries have no semantic authority.

Given the same coherent initial state, policy, and ordered mapped inputs, processing them in one invocation or partitioning them across multiple invocations MUST produce the same logical state/activity result and final continuity state.

Durable-position ordering is authoritative for evaluation order.

FC-031.2D.2 does not introduce timestamp-monotonicity requirements. Activity timestamps continue to follow existing FC-024 semantics: transition/activity timestamps come from the mapped observation whose evaluation causes the transition, while durable-position ordering determines evaluation order.

## 11. `LastConsumedInstanceId` derivation

For every successful logical evaluation result:

```text
EvaluationAuthority.LastConsumedInstanceId
    = InstanceId of the mapped durable observation
      at EvaluationAuthority.EvaluatedThrough
```

It is not derived from acquisition contact, raw high-water, a generic checkpoint, a supplied-but-unincorporated batch element, or inferred legacy state.

Only an actually incorporated mapped durable observation can advance `LastConsumedInstanceId`.

## 12. Continuity-policy stability

One logical evaluation publication is calculated under exactly one resolved `CurrentStateContinuityPolicy`.

Its `CurrentStatePolicyReference` is stable for the whole logical calculation, including every instance boundary encountered while calculating that publication.

The resulting `EvaluationAuthority.AppliedContinuityPolicy` MUST equal that policy reference.

A retry of the same logical publication MUST retain the same policy reference. A changed policy reference at the same `EvaluatedThrough` is not exact replay under the frozen FC-031.2D.1 publication algebra.

Policy-resolution composition remains outside FC-031.2D.2.

## 13. No-input / no-advance semantics

When no newly incorporated mapped input advances evaluation:

```text
no instance-transition policy is applied
no evaluator state changes
no state-change output is derived
no activity-period output is derived
no new logical EvaluationAuthority is created
no authority revision churn is permitted
```

This includes an empty invocation and an invocation whose supplied durable positions are all already incorporated.

FC-031.2D.1 lost-ack recovery remains distinct: replay of an already-determined logical publication is recovery, not a new continuity calculation.

## 14. Derived-output summary

### Same instance

```text
retain complete working context
apply observation
evaluate
emit transition/activity output only on actual state change
```

### Different instance + Preserve

```text
retain complete working context
apply first new-instance observation
evaluate
if state changes:
    emit normal state transition
    complete retained activity at closing observation timestamp when open
```

### Different instance + Reset

```text
clear signal evidence
abandon prior open activity
State            = Unknown
ActiveState      = null
ActiveStartedAt  = null
apply first new-instance observation
evaluate
if result == Unknown:
    emit nothing
if result != Unknown:
    emit Unknown → result
    ActiveState      = result
    ActiveStartedAt  = observation timestamp
```

## 15. Coherence requirements carried into FC-031.2D.3

FC-031.2D.2 does not define atomic publication mechanics, but later FC-031.2D.3 publication must preserve these logical equalities:

```text
Projection.ProcessorId
    == EvaluationAuthority.StateProcessorId

Projection.StreamId
    == EvaluationAuthority.ObservationStreamId

Projection.Position
    == EvaluationAuthority.EvaluatedThrough

Projection.State
    == EvaluationAuthority.MachineState

EvaluationAuthority.LastConsumedInstanceId
    == InstanceId of the incorporated mapped observation at EvaluatedThrough

EvaluationAuthority.AppliedContinuityPolicy
    == reference of the continuity policy used for calculation
```

The following must all originate from one transition calculation:

```text
Projection.Signals
Projection.State
Projection.ActiveState
Projection.ActiveStartedAt
derived state-change outputs
derived activity-period outputs
EvaluationAuthority semantic fields
```

FC-031.2D.1 already requires later integration to publish projection, derived outputs, and accepted evaluation authority within one provider-owned atomic publication boundary. Mechanism and failure behavior remain FC-031.2D.3 and FC-031.2D.4 concerns.
