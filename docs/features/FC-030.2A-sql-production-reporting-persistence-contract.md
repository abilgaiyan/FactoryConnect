# FC-030.2A — SQL Production Reporting Persistence Contract

## Status

ACTIVE / ARCHITECTURE-FIRST. FC-030.1 is CLOSED / FROZEN and is consumed unchanged by this feature.

Migration 005 is now permitted to be designed, but must not be implemented until this contract freezes the SQL persistence shape and executable acceptance matrix.

## Goal

Provide SQL Server durability for the already-existing provider-neutral operational-metric projection, reporting, and machine-shift roster contracts without introducing a second reporting model or changing FC-027/FC-028 semantics.

The target is provider parity:

```text
existing provider-neutral contracts
    ↓
SQL Server persistence implementation
    ↓
existing projection runtime / reporting API / dashboard
```

FC-030.2 does not recalculate reporting values inside SQL. SQL persists and queries the durable projection model produced by the existing runtime.

## Durable projection semantics

`OperationalMetricProjectionCommit` is the authoritative mutation contract.

One commit:

```text
projection processor identity
expected checkpoint (nullable)
proposed checkpoint
exact batch manifest
0..N projections for one coherent FC-026 source revision
```

The SQL implementation must preserve the same compare-and-swap semantics as the in-memory store:

1. current checkpoint must equal `ExpectedCheckpoint` exactly;
2. an existing projection processor cannot change its FC-026 source processor or stream;
3. all projections in the commit belong to the proposed source revision;
4. projection rows and the proposed checkpoint become visible atomically;
5. failure leaves the prior committed checkpoint/projections unchanged.

A single flattened report table without checkpoint and evidence state is therefore insufficient.

## Projection identity

The durable projection identity is:

```text
OperationalMetricProjectionProcessorId
+ MachineId
+ OperationalMetricPeriodId
+ OperationalMetricDefinitionId (MetricKey + Version)
+ OperationalMetricEvaluationContextKey
```

`OperationalMetricPeriodId` is a closed union:

```text
Shift
    ShiftOccurrenceId
        SiteId
        ShiftScheduleAssignmentId
        ShiftId
        StartsAtUtc
        EndsAtUtc

ProductionDay
    ProductionDayId
        SiteId
        BusinessDate
```

Context identity is exact and nullable by component:

```text
ProductionOrderId?
OperationId?
PartId?
OperatorId?
```

SQL keys must preserve ordinal/string identity semantics and must never collapse null and empty identity. Empty identities remain invalid at the provider-neutral contract boundary.

## Projection payload

Each durable projection persists enough state to reconstruct `OperationalMetricProjection` exactly:

```text
ProcessorId
EvaluationKey
Status
Value?
Unit
ReasonCode?
ReasonOperandName?
SourceRevision
OperandEvidence[]
DependencyEvidence[]
```

`Calculated` rows require a value and no reason. Non-calculated rows require a reason and no value. SQL schema constraints may enforce mechanically safe portions of this invariant, but provider-neutral constructors remain the semantic authority.

## Source revision identity

Every projection and checkpoint refers to an FC-026 `MetricAggregationCheckpoint`:

```text
MetricAggregationProcessorId
MetricInputStreamId
Position
```

The SQL representation must preserve the exact processor/stream/position identity used by revision detection and restart processing.

## Evidence model

### Component evidence

Persist one row per component operand, including:

```text
OperandName
source aggregation processor
source machine
source period identity
ComponentKey
SourceRevision
MetricDimension
Value
Unit
InputCount
FirstInputTimestamp
LastInputTimestamp
```

### Dependency evidence

Persist one row per evaluated-metric operand, including at minimum:

```text
OperandName
exact dependency OperationalMetricDefinitionId
identity of the referenced durable projection
```

The referenced dependency must reconstruct to the exact projection processor, source revision, machine, period, context, and definition expected by the provider-neutral contract.

Do not persist dependency evidence as an unvalidated free-form JSON blob.

## Projection checkpoint and manifest

A projection processor owns one current checkpoint and is permanently bound, once created, to one FC-026 source processor/stream.

The checkpoint must durably preserve:

```text
ProjectionProcessorId
SourceAggregationProcessorId
SourceStreamId
SourceRevisionPosition
BatchManifest
```

The batch manifest is the exact set of evaluation keys committed at that source revision. It is not ordering-sensitive, but it must round-trip as the same set and participate in checkpoint equality/CAS semantics.

The schema may normalize the manifest into child rows rather than serializing it; normalized relational representation is preferred because projection identities are already relational and must be queryable.

## Reporting query requirements

SQL query behavior must remain value-equivalent to `OperationalMetricReportQuerySemantics` and `OperationalMetricReportOrdering`.

Required filters:

```text
selected (MachineId, ProjectionProcessorId) sources
shift start UTC half-open range
production-day DateOnly half-open range
exact metric definition IDs
optional context filters
optional status filters
unpartitioned-only context
```

Required deterministic ordering:

```text
period ascending or descending
then MachineId
then complete period identity
then context identity
then MetricKey
then Version
```

Continuation remains owned by the existing reporting layer. The SQL provider accepts the decoded `startAfter` evaluation key through `IOperationalMetricReportingQueryProvider.ReadWindowAsync` and performs strict `> startAfter` ordering according to the frozen comparer.

Indexes introduced by migration 005 must be justified by these concrete query shapes rather than by generic indexing guesses.

## Machine-shift occurrence roster persistence

The SQL provider must also implement `IMachineShiftOccurrenceRosterStore` because the in-memory provider exposes it as part of the complete persistence capability set and downstream production-context/reporting composition relies on durable ownership state.

Roster identity:

```text
MachineId
ProductionDayId (SiteId + BusinessDate)
```

Roster payload:

```text
ProductionLineId
Revision > 0
0..N ShiftOccurrenceId ownership rows
```

Commit uses exact revision compare-and-swap semantics:

```text
ExpectedRevision null    → roster must not already exist
ExpectedRevision value   → current revision must match exactly
ProposedRoster.Revision  → stored atomically with its exact occurrence set
```

A successful update replaces the occurrence set for that roster identity atomically.

## Schema design principles to freeze before SQL is written

1. Prefer normalized relational identities over opaque serialized keys.
2. Use binary/ordinal string comparison where identity equality depends on `StringComparer.Ordinal`.
3. Preserve UTC offset requirements explicitly for UTC timestamps.
4. Preserve `DateOnly` business dates without timezone conversion.
5. Use the repository's existing canonical decimal codec/precision rules for durable metric numeric values rather than inventing a second decimal convention.
6. Make checkpoint/projection/evidence commits transactional and CAS-safe under concurrent processors.
7. Reporting reads never mutate or repair projection state.
8. Provider SQL must reconstruct the same public records so provider conformance fixtures can compare values directly.
9. No SQL-side metric formula evaluation, OEE calculation, status inference, or context inference.
10. No host-specific reporting schema semantics.

## Hard exclusions

FC-030.2A and migration 005 design must not:

- change migrations 001–004;
- change `LegacyPost004SchemaDescriptor`;
- change migration ledger semantics;
- change migration applock semantics;
- change C transaction/rollback semantics;
- change D classification precedence or diagnostics;
- change E startup failure semantics;
- add a second reporting API contract;
- calculate operational metrics in SQL;
- persist only dashboard-specific denormalized values;
- couple reporting identity to UI display order/configuration;
- introduce provider-specific behavior visible through the existing abstractions.

## Immediate next step

Inventory the exact existing identifier lengths, SQL type conventions, aggregation checkpoint/revision encoding, and in-memory conformance fixtures. Then produce the physical migration-005 decision table for 2A review. Until that decision table is frozen, migration 005 remains design-only.
