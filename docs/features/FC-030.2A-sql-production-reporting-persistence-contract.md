# 3. SQL representation conventions

Physical storage conventions:

```text
MachineId                         uniqueidentifier
provider/domain strings          nvarchar(256) COLLATE Latin1_General_100_BIN2 unless narrower below
Unit                             nvarchar(128) COLLATE Latin1_General_100_BIN2
canonical decimal text           nvarchar(64)  COLLATE Latin1_General_100_BIN2
StringOrderKeyV2                 varbinary(769)
UInt64 position/revision         decimal(20,0), CHECK 1..18446744073709551615
UTC timestamp                    datetimeoffset(7), mandatory offset +00:00
production business date         date
row surrogate                    bigint IDENTITY(1,1)
hash                             binary(32), SHA-256
canonical binary identity        varbinary(max)
codec version                    smallint
```

Raw `nvarchar` values remain reconstruction/diagnostic storage. `Latin1_General_100_BIN2` is **not** provider-neutral equality/order authority.

Whenever SQL equality/order has semantic effect before reconstruction, it MUST compare the mapped `StringOrderKeyV2` companion column from `FC-030.2A-string-comparison-ownership-map.md`.

`StringOrderKeyV2` candidate encoding is exactly:

```text
for each validated .NET UTF-16 code unit u:
  0x01
  UInt16BE(u)
then:
  0x00

max bytes = 256 * 3 + 1 = 769
```

No normalization, trimming, case folding, BOM stripping, NUL stripping, escaping, or scalar rewriting occurs.

Classification of text + V2 duplicated state:

```text
Writer construction invariant + reader revalidation
```

The writer constructs both from the same exact string. The reader re-encodes the reconstructed string and requires exact byte equality with the stored key. SQL owns only the outer column shape and relational comparison over the binary key.

Projection/evidence decimal values remain `CanonicalDecimalTextV1`; SQL performs no canonical decimal arithmetic or formatting.

