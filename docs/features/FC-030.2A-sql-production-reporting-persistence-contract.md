Projection/evidence decimal values remain canonical decimal text. SQL performs no metric arithmetic. The SQL implementation reuses the repository decimal codec/convention already used by aggregation persistence.

## 3.1 Guid ordering

`OperationalMetricReportOrdering` compares `MachineId.Value` using the .NET `Guid` comparer. SQL MUST NOT assume native `uniqueidentifier ORDER BY` is provider-neutral ordering authority.

Each projection therefore stores:

```text
MachineOrderKey binary(16) NOT NULL
```

`MachineOrderKey` is produced by an internal versioned SQL-provider codec whose byte order is defined to compare lexicographically exactly as `.NET Guid.CompareTo` for the corresponding `MachineId`. It is not identity; `MachineId` remains identity. 2D conformance must exhaustively cover differing Guid fields/bytes and prove SQL order equals `OperationalMetricReportOrdering`.

# 4. Projection logical identity and null encoding

## 4.1 Surrogate versus logical identity

`dbo.OperationalMetricProjection` uses:

```text
OperationalMetricProjectionRowId bigint IDENTITY PK
```

Child tables use this surrogate FK.

Logical uniqueness is separately represented by:

```text
ProjectionProcessorRowId
+ EvaluationKeyHash binary(32)
```

with canonical `EvaluationKeyBinary varbinary(max)` retained beside the hash.

The provider owns an internal versioned `OperationalMetricEvaluationKeySqlCodec` that encodes the complete logical key with explicit type/field/null tags. SHA-256 is computed over those exact canonical bytes. Empty-string sentinels are forbidden.

A hash match MUST compare `EvaluationKeyBinary` before treating the row as the same logical key. A same-hash/different-binary condition is a deterministic collision failure and must never overwrite state.

Physical unique authority:

```text
UQ_OperationalMetricProjection_LogicalHash
  UNIQUE (OperationalMetricProjectionProcessorRowId, EvaluationKeyHash)
```

This hash+canonical-byte pattern avoids exceeding SQL Server B-tree key-width limits while preserving exact logical identity.

## 4.2 Nullable context

Each nullable context identity is represented as a presence/value pair:

```text
ProductionOrderPresent bit NOT NULL
ProductionOrderId      nvarchar(256) BIN2 NULL
OperationPresent       bit NOT NULL
OperationId            nvarchar(256) BIN2 NULL
PartPresent            bit NOT NULL
PartId                 nvarchar(256) BIN2 NULL
OperatorPresent        bit NOT NULL
OperatorId             nvarchar(256) BIN2 NULL
```

Each pair has the exact check:

```text
(Present = 0 AND Value IS NULL)
OR
(Present = 1 AND Value IS NOT NULL)
```

A present value must also satisfy `LEN(Value) > 0`. Null and empty are never collapsed. Presence bits are part of canonical evaluation-key bytes and reporting order.

## 7.1 Current-state versus history semantics

Projection persistence stores **one current row per logical projection key**, matching the in-memory provider.

For a newer source revision:

- a committed key already present is replaced in-place as the current projection, including its evidence and source revision;
- a newly committed key is inserted;
- an older projection key absent from the new batch manifest is **not deleted**;
- no historical projection-version table is created by migration 005.

The checkpoint manifest describes the exact keys in the latest committed batch, not every retained projection row.

This is required for replay equality with the current in-memory behavior.

## 9.1 Evidence ordering

`EvidenceOrdinal` is zero-based **within `EvidenceKind`**. Reads reconstruct component evidence ordered by ordinal and dependency evidence ordered by ordinal. `OperandName` uniqueness is across both kinds, matching the domain constructor.

## 9.2 Dependency evidence is an immutable recursive snapshot

`OperationalMetricProjectionFactory` recursively creates dependency projections and `OperationalMetricProjectionEquivalence` recursively compares them. Therefore a dependency evidence row MUST NOT FK to the mutable current dependency projection as its value authority.

Instead, `DependencySnapshotBinary` is a versioned canonical binary encoding of the complete recursive `OperationalMetricProjection` dependency snapshot, including nested component/dependency evidence. `DependencySnapshotHash` is SHA-256 over those exact bytes. The structured `DependencyMetricKey/Version` header must match the decoded snapshot definition; the writer validates before persistence and the reader validates hash, codec version, complete decode, and header agreement before reconstruction.

This is not free-form JSON and not an opaque unvalidated payload. The codec is deterministic/versioned and covered by round-trip/corruption tests.

Deletion policy:

- replacing a root projection explicitly deletes/replaces that root's evidence rows inside the projection commit transaction;
- deleting/replacing dependency evidence never deletes or updates any live dependency projection;
- changing a live dependency projection never mutates already-committed parent evidence snapshots;
- no cascade from dependency snapshot to another projection row exists.

# 10. Reporting ordering: executable SQL definition

SQL ordering must equal `OperationalMetricReportOrdering`, not merely appear similar.

Define context compare atom for each optional field as:

```text
(Present ASC, Value BIN2 ASC when Present=1)
```

Thus null (`Present=0`) sorts before any value, exactly matching the provider-neutral optional comparer. No sentinel participates.

## 10.1 Shift order

Ascending query:

```text
ShiftStartsAtUtc ASC,
MachineOrderKey ASC,
PeriodSiteId ASC,
ShiftScheduleAssignmentId ASC,
ShiftId ASC,
ShiftEndsAtUtc ASC,
ProductionOrderPresent ASC, ProductionOrderId ASC,
OperationPresent ASC, OperationId ASC,
PartPresent ASC, PartId ASC,
OperatorPresent ASC, OperatorId ASC,
MetricKey ASC,

```

Descending query:

```text
ShiftStartsAtUtc DESC,
ALL REMAINING FIELDS ABOVE ASC
```

Only the primary period scalar reverses.

## 10.2 Production-day order


```text

```

## 10.3 Scalar comparison authority

```text
DateOnly          -> SQL date
DateTimeOffset    -> datetimeoffset(7) with mandatory +00:00, so instant comparison is deterministic
Guid              -> MachineOrderKey, never native uniqueidentifier ordering
string            -> nvarchar BIN2 / StringComparer.Ordinal equivalence
presence bit      -> 0 then 1
revision/numeric  -> decimal(20,0); not part of reporting order
```

Included-column order never participates in result order, identity, or continuation.

## 10.4 Exact startAfter predicate

Let `P` be the primary period scalar and `T` be the complete ascending tail tuple listed above.

Ascending is exactly:

```text
(P > @cursorP)
OR (P = @cursorP AND T >lex @cursorT)
```

Descending is exactly:

```text
(P < @cursorP)
OR (P = @cursorP AND T >lex @cursorT)
```

`T >lex` is expanded in SQL as the normal strict OR-chain:

```text
t1 > c1
OR (t1=c1 AND t2 > c2)
OR (t1=c1 AND t2=c2 AND t3 > c3)
...
```

For each nullable context member the tuple contains `Present` followed by `Value`; value equality/comparison is evaluated only for `Present=1`. Both absent values are equal at that atom.

The predicate is strict; the cursor row itself is never repeated.

2D conformance must prove ascending/descending SQL windows equal the provider-neutral comparer for:

- null versus present context in every component;
- case/code-unit-distinct BIN2 identities;
- identical period starts with different complete shift identities;
- identical production dates across machines/sites;
- Guid values whose SQL native uniqueidentifier order differs from .NET Guid order;
- same key except MetricKey/Version;
- page boundaries at every tail component.

# 11. Reporting indexes and SQL key-width policy

The full provider-neutral tail contains several `nvarchar(256)` identities and cannot safely be frozen as one SQL B-tree key without violating SQL Server index-key width constraints.

Therefore correctness is owned by explicit WHERE/seek + ORDER BY, not by physical index order.

Migration 005 creates narrow access indexes:

```text
IX_OperationalMetricProjection_ShiftWindow
  ON (OperationalMetricProjectionProcessorRowId, ShiftStartsAtUtc, MachineOrderKey, OperationalMetricProjectionRowId)
  WHERE PeriodKind = 1

IX_OperationalMetricProjection_ProductionDayWindow
  ON (OperationalMetricProjectionProcessorRowId, ProductionBusinessDate, MachineOrderKey, OperationalMetricProjectionRowId)
  WHERE PeriodKind = 2
```

Useful scalar payload may be INCLUDE columns, but INCLUDE order has no semantic meaning.

These indexes narrow selected source/range reads. SQL may sort the narrowed candidate set to satisfy the exact mixed-direction tail order. No optimization may weaken ordering or continuation semantics.

A future performance feature may add a bounded order-key materialization only with separate architecture/conformance proof; it is not part of migration 005.

## 12.3 Roster CAS

One `SERIALIZABLE` transaction uses `UPDLOCK,HOLDLOCK` on the unique roster identity.

- absent row + expected null: key-range lock then insert;
- present row + expected null: conflict;
- present row + expected revision: exact equality required;
- absent row + expected revision: conflict;
- successful update replaces the complete occurrence set and revision atomically;
- failure preserves prior roster/occurrences.
