# FC-030.1E — Startup Integration and Operational Failure Handling

## Status

**CLOSED / FROZEN.** E.1 through E.6 are complete. FC-030.1A through D remain the frozen migration, structural, and runtime-verification authorities consumed by this startup layer.

FC-030.1E introduces no migration SQL and no reporting-persistence schema. It only sequences the selected persistence provider's startup readiness before host activation.

## Central invariant

For a host configured with SQL Server, no HTTP listener, background worker, acquisition loop, processor, reporting workload, or other application workload may become operational until:

```text
C migration/adoption engine succeeds
    -> D runtime verifier succeeds
        -> D returns Compatible
            -> host activation is permitted
```

## Provider-aware startup boundary

Hosts depend only on:

```csharp
IPersistenceStartupGate
    EnsureReadyAsync(CancellationToken)
```

Provider selection remains owned by the existing persistence-finalization boundary.

For non-SQL providers the startup gate is a cancellation-aware no-op. No SQL connection, migration engine, verifier, or SQL lock-timeout configuration is required.

For SQL Server, the shared implementation is `SqlServerPersistenceStartupGate`.

## Frozen SQL startup sequence

```text
1. observe cancellation
2. invoke FC-030.1C migration/adoption engine
3. if C throws, fail with MigrationOperationalFailure
4. invoke FC-030.1D read-only verifier
5. if D throws, fail with VerificationOperationalFailure
6. if D returns non-Compatible, fail with DatabaseIncompatible
7. if D returns Compatible, return successfully
8. host may activate
```

C and D retain separate connection/transaction ownership. E does not duplicate their SQL commands, catalog checks, structural comparison, ledger parsing, diagnostic generation, or applock conversion rules.

## Migration authority

Both production hosts may perform SQL startup migration:

```text
FactoryConnect.Api
FactoryConnect.Edge
```

They are safe concurrent authorities because both invoke the same C engine and therefore serialize through the same Exclusive transaction-owned `FactoryConnect.SqlMigration` application lock.

The first host may migrate/adopt and commit. A later host re-reads the committed state and performs no duplicate migration when already current.

## Host activation points

API:

```text
builder.Build()
-> pre-activation cancellation registration
-> IPersistenceStartupGate.EnsureReadyAsync
-> dispose pre-activation cancellation registration
-> app.RunAsync()
```

Edge:

```text
builder.Build()
-> pre-activation cancellation registration
-> IPersistenceStartupGate.EnsureReadyAsync
-> dispose pre-activation cancellation registration
-> host.RunAsync()
```

The gate is not an ordinary hosted service; failed readiness prevents the API listener and Edge workers from starting.

## Frozen failure vocabulary

Exactly three startup failure kinds exist:

```text
MigrationOperationalFailure
VerificationOperationalFailure
DatabaseIncompatible
```

Rules:

- C operational failure -> preserve the exact C exception as `InnerException`; D is not invoked.
- D operational failure -> preserve the exact D/provider exception as `InnerException`.
- D non-compatible result -> preserve that exact immutable `SqlRuntimeCompatibilityResult`; `InnerException` is null.
- E does not flatten C/D taxonomies or invent competing diagnostics.

## Cancellation rule

The frozen cancellation rule is unconditional on token inspection:

> **Any `OperationCanceledException` emitted by C or D propagates unchanged and is never wrapped by E.**

Real `Microsoft.Data.SqlClient` cancellation while blocked in `sp_getapplock` may surface as `SqlException`; that remains a provider operational failure and is translated by stage. E does not normalize provider exceptions into `OperationCanceledException`.

Cancellation before activation always prevents workloads from starting.

## SQL startup configuration

The actual configuration key is:

```text
PersistenceProviders:SqlServer:Startup:LockTimeout
```

The default is 30 seconds unless configured otherwise.

The same configured value is passed to C Exclusive-lock acquisition and D Shared-lock acquisition. Conversion and validation remain owned by `SqlMigrationLockTimeout`.

SQL startup configuration is captured through one lazy immutable provider-registration snapshot shared by the startup gate and SQL persistence services so runtime reload cannot split the database or timeout used by those artifacts.

## Logging boundary

Allowed structured evidence includes host identity, persistence provider, startup stage, failure kind, compatibility classification, D diagnostic code/stage/artifact/expected/actual/detail.

Connection strings, passwords, tokens, raw configuration dumps, and unfiltered provider data must not be logged by E-authored message templates.

## Hard boundary

FC-030.1E must not:

- introduce migration 005;
- introduce operational-metric or production-reporting SQL persistence;
- change migrations 001–004;
- change C transaction, lock, adoption, or exception semantics;
- change D classification, diagnostics, or non-mutation semantics;
- add host-specific migration SQL;
- permit degraded SQL startup after incompatibility;
- expose API endpoints before readiness succeeds;
- start Edge workers before readiness succeeds; or
- alter non-SQL persistence semantics.

With E.6 complete, this startup boundary is frozen for FC-030.1 and may be consumed by the next reporting-persistence feature.
