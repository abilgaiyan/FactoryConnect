# FC-030.1E — Startup Integration and Operational Failure Handling

## Status

Architecture contract proposed for review. FC-030.1A through FC-030.1D are treated as closed/frozen authorities for this slice. FC-030.1E may compose those authorities but must not change their migration, locking, compatibility-classification, diagnostic, or structural-comparison semantics.

No migration 005, operational-metric SQL persistence, or production-reporting schema work is permitted until FC-030.1E and the whole FC-030.1 closure matrix are complete.

## Goal

Connect the frozen SQL migration engine and runtime compatibility verifier to the actual FactoryConnect hosts so application workloads activate only after SQL persistence reaches and proves an exact binary-supported state.

The startup boundary is:

```text
construct host/service provider
        ↓
resolve selected persistence provider
        ↓
non-SQL provider
        └─ no SQL startup gate; existing behavior continues

SQL Server provider
        ↓
run FC-030.1C migration/adoption engine
under Exclusive FactoryConnect.SqlMigration lock
        ↓
run FC-030.1D read-only runtime verifier
under Shared FactoryConnect.SqlMigration lock
        ↓
Compatible
        ├─ yes → activate host workloads
        └─ no  → deterministic startup failure; host never activates
```

## Central invariant

For a host configured with the SQL Server persistence provider, no HTTP listener, background worker, acquisition loop, projection processor, reporting workload, or other application workload may become operational until the existing migration engine has completed successfully and a subsequent read-only compatibility verification returns `Compatible`.

Startup integration is orchestration only. It does not introduce a second migration implementation, a second compatibility classifier, a second diagnostic vocabulary, or host-specific schema semantics.

## Frozen authority reuse

FC-030.1E must use the existing authorities exactly:

```text
FC-030.1C
    SqlServerMigrationEngine
    Exclusive transaction-owned FactoryConnect.SqlMigration applock
    Serializable migration transaction
    legacy adoption rules
    migration execution rules
    migration operational failure taxonomy

FC-030.1D
    SqlServerRuntimeSchemaCompatibilityVerifier
    Shared transaction-owned FactoryConnect.SqlMigration applock
    read-only verification transaction
    SqlRuntimeCompatibilityClassification
    SqlRuntimeCompatibilityDiagnostic[]
```

E must not duplicate their SQL commands, catalog checks, structural comparison, ledger parsing, diagnostic generation, or lock-timeout conversion.

## Decision 1 — migration authority

Both production hosts are authorized to perform startup migration when and only when the selected persistence provider is SQL Server:

```text
FactoryConnect.Api     SQL Server selected → migration authority
FactoryConnect.Edge    SQL Server selected → migration authority
```

This is safe because both hosts must call the same FC-030.1C engine and therefore contend on the same Exclusive transaction-owned `FactoryConnect.SqlMigration` application lock.

If API and Edge start concurrently against the same database:

```text
API  ─┐
      ├─ Exclusive FactoryConnect.SqlMigration serialization
Edge ─┘

first host
    → migrates/adopts as required
    → commits

second host
    → acquires lock afterward
    → re-reads committed state
    → performs no duplicate migration when already current
```

Host identity must not participate in migration history or schema semantics.

## Decision 2 — migration policy

SQL Server migration/adoption is automatic during host startup for FC-030.1.

There is no separate administrative command requirement in this slice.

Automatic startup migration is permitted only through the already-frozen C engine. Hosts must not execute migration SQL directly, create the ledger directly, or perform ad-hoc repair.

A future explicit administrative migration mode may be added as a separate feature, but E does not require or define it.

## Decision 3 — post-migration verification is mandatory

A successful migration-engine call is necessary but not sufficient for workload activation.

Every SQL host must immediately perform FC-030.1D runtime compatibility verification after the C engine succeeds:

```text
Migration engine success
        ↓
Runtime verifier
        ↓
Compatible only
        ↓
activate host
```

This preserves the separation of concerns:

- C is the mutation/deployment authority;
- D is the read-only runtime decision authority;
- E only sequences them.

No host may infer compatibility merely because migration execution returned successfully.

## Decision 4 — non-SQL behavior

Hosts using a non-SQL persistence provider are unaffected by the FC-030.1 SQL startup gate.

For non-SQL providers:

- no SQL connection is opened for E;
- no migration engine is resolved or invoked;
- no SQL runtime verifier is resolved or invoked;
- no SQL lock timeout is required; and
- existing host activation behavior remains unchanged.

Provider selection remains the existing persistence-finalization authority. Host code must not duplicate provider-name normalization rules.

## Decision 5 — activation point

### API

The API startup gate runs after the service provider/application is constructed but before `Run`/`RunAsync` starts the web server.

Conceptually:

```text
builder.Build()
    ↓
SQL startup gate
    ↓ success
app.RunAsync()
```

Endpoint mapping may already exist in the constructed application object, but no listener is allowed to become operational before the gate succeeds.

Therefore `/health`, OpenAPI, reporting endpoints, and SPA/other HTTP surfaces are not externally reachable during a failed SQL startup gate.

### Edge

The Edge startup gate runs after host construction but before `RunAsync` starts hosted services.

Conceptually:

```text
builder.Build()
    ↓
SQL startup gate
    ↓ success
host.RunAsync()
```

No `BackgroundService`, MTConnect acquisition loop, observation processor, metric-input worker, metric aggregation processor, or operational-metric projection worker may start before the gate succeeds.

The gate must not be implemented merely as another ordinary hosted service whose ordering could allow unrelated hosted services to start first.

## Startup orchestration contract

E should introduce one provider-aware startup orchestration boundary callable by both hosts.

Conceptual shape:

```text
IPersistenceStartupGate
    EnsureReadyAsync(CancellationToken)
```

or an equivalent concrete/internal application boundary.

The contract must be provider-aware but provider-neutral at the host call site:

```text
host
    → startup gate
        → selected provider is non-SQL → completed
        → selected provider is SQL     → SQL startup sequence
```

API and Edge must not each implement their own SQL migration/verification sequence.

## SQL startup sequence

The frozen sequence is:

```text
1. observe cancellation
2. open deployment/runtime SQL connection as required by existing C/D boundaries
3. invoke C migration engine with configured startup lock timeout
4. if C throws → operational startup failure
5. invoke D runtime compatibility verifier with configured startup lock timeout
6. if D throws → operational startup failure
7. if D returns non-Compatible → compatibility startup failure
8. if D returns Compatible → startup gate succeeds
```

The implementation may reuse one connection only if doing so does not alter C or D ownership/transaction/cleanup contracts. Otherwise separate connections are preferred over changing frozen mechanism semantics for startup convenience.

## Startup failure vocabulary

E adds startup-layer failure vocabulary without replacing C/D failures.

The startup boundary distinguishes exactly three failure categories:

```text
MigrationOperationalFailure
VerificationOperationalFailure
DatabaseIncompatible
```

Recommended internal contract:

```text
SqlPersistenceStartupFailureKind
    MigrationOperationalFailure
    VerificationOperationalFailure
    DatabaseIncompatible

SqlPersistenceStartupException
    FailureKind
    CompatibilityResult?   // present only for DatabaseIncompatible
    InnerException?        // present for operational failures
```

### Migration operational failure

If the C engine throws, E wraps/preserves that exception as the inner cause of `MigrationOperationalFailure`.

Examples include existing C lock acquisition, ledger schema, history, unledgered-schema, migration execution, or final-schema validation failures.

E must not flatten or reinterpret the C exception taxonomy.

### Verification operational failure

If D throws because of connection/provider/read/applock/cancellation-related operational behavior, E preserves the D operational exception as the cause of `VerificationOperationalFailure`, except cancellation which follows the cancellation rule below.

E must not convert provider/read/applock failures into compatibility classifications.

### Database incompatible

If D successfully returns a non-`Compatible` `SqlRuntimeCompatibilityResult`, E throws `DatabaseIncompatible` carrying that exact immutable result.

The result's classification and ordered diagnostics are the sole compatibility evidence. E must not generate competing schema/history diagnostics.

## Cancellation policy

Host shutdown/startup cancellation propagates through the startup gate.

`OperationCanceledException` caused by the supplied startup cancellation token is not wrapped as a migration or verification startup failure.

Cancellation before host activation means:

```text
startup cancelled
→ gate does not succeed
→ host workloads do not start
```

C and D retain responsibility for their own transactional rollback/disposal behavior.

## Lock-timeout policy

Startup exposes one SQL migration/compatibility lock-timeout configuration value and passes it through the existing frozen timeout conversion/validation authority.

The same configured timeout is used for:

```text
C Exclusive migration lock
D Shared verification lock
```

unless later architecture review identifies a concrete operational requirement for two independently configured values.

E must not reimplement millisecond rounding, SQL `Int32` range validation, zero-wait semantics, or applock return-code parsing.

Invalid timeout configuration must fail before workloads activate.

## Logging and diagnostics policy

Startup logging is deterministic and secret-safe.

Allowed structured fields include:

```text
HostName / service identity
PersistenceProvider
StartupStage = Migration | Verification
FailureKind
CompatibilityClassification
DiagnosticCode
DecisionStage
Artifact
Expected
Actual
Detail
```

The D diagnostic values may be logged because they describe FactoryConnect migration/schema authority and observed FactoryConnect-owned structure.

Logs must not include:

- connection strings;
- passwords;
- access tokens;
- SQL authentication secrets;
- raw configuration dumps;
- exception `Data` collections without explicit filtering; or
- provider messages when doing so could expose connection details.

Operational exceptions may be attached to structured logging through the normal logger exception channel, but E-authored message templates must not interpolate connection strings or secret configuration values.

Compatible startup may emit one concise informational event. Non-compatible results emit deterministic classification plus the ordered D diagnostics.

## Configuration boundary

E may add SQL startup options only for orchestration concerns, for example:

```text
Persistence:SqlServer:Startup:LockTimeout
```

The final key should follow existing SQL Server option conventions after repository inventory.

E must not add configuration that changes:

- catalog contents;
- legacy adoption policy;
- migration checksum rules;
- compatibility classification semantics;
- Current/Legacy descriptor authority; or
- whether a non-compatible SQL database may be ignored.

There is no `IgnoreCompatibilityFailure` or `ContinueOnMigrationFailure` escape hatch in FC-030.1E.

## Failure precedence

Startup executes stages sequentially, so precedence is naturally deterministic:

```text
C migration failure
    → MigrationOperationalFailure
    → D is not invoked

C success + D operational failure
    → VerificationOperationalFailure

C success + D non-compatible result
    → DatabaseIncompatible

C success + D Compatible
    → success
```

A cleanup/logging failure must not replace the primary startup failure.

## Host lifecycle guarantees

For SQL Server hosts, E must prove:

```text
before gate success:
    API listener not operational
    Edge hosted workers not started

after gate success:
    normal host lifecycle proceeds unchanged

on gate failure/cancellation:
    process startup fails/terminates
    no application workload becomes operational
```

E does not define a degraded SQL mode.

## Construction slices

### FC-030.1E.1 — Host startup contract and failure vocabulary

Freeze and implement:

- provider-aware startup gate abstraction;
- SQL startup failure kinds;
- startup exception contract;
- cancellation semantics;
- lock-timeout option/validation boundary; and
- deterministic secret-safe logging contract.

No API/Edge startup wiring yet.

### FC-030.1E.2 — SQL Server provider registration/composition

Implement:

- SQL startup-gate implementation;
- registration only when/through the selected SQL provider composition boundary;
- reuse of C migration engine;
- reuse of D runtime verifier;
- non-SQL no-op behavior; and
- exact provider-selection ownership.

No host-specific duplicated SQL logic.

### FC-030.1E.3 — API startup integration

Wire the shared startup gate:

```text
Build
→ EnsureReadyAsync
→ RunAsync
```

Prove failed SQL startup never exposes `/health`, OpenAPI, or reporting endpoints.

### FC-030.1E.4 — Edge startup integration

Wire the same gate:

```text
Build
→ EnsureReadyAsync
→ RunAsync
```

Prove failed SQL startup starts no hosted workers or acquisition/processing loops.

### FC-030.1E.5 — startup ordering, concurrency, and failure conformance

With real SQL Server prove at least:

- API and Edge concurrent startup serialize through C's Exclusive lock;
- first host may migrate/adopt and second re-reads committed current state;
- both subsequently verify through D;
- no duplicate migration-history rows;
- migration lock timeout fails startup before activation;
- verification lock timeout/provider failure fails startup before activation;
- C failure prevents D invocation;
- D non-compatible result preserves exact classification/diagnostics;
- cancellation propagates and prevents activation;
- non-SQL provider does not invoke SQL startup mechanisms; and
- retry after a corrected operational/database state can start normally.

## Hard boundary

FC-030.1E must not:

- introduce migration 005;
- introduce operational-metric SQL persistence;
- introduce production-reporting tables;
- change migrations 001–004;
- change C migration semantics or exception meaning;
- change D classification, diagnostic ordering, or read-only semantics;
- add host-specific migration SQL;
- permit a non-compatible SQL database to start in degraded mode;
- expose API endpoints before SQL readiness succeeds;
- start Edge workers before SQL readiness succeeds; or
- alter non-SQL persistence semantics.

## Acceptance principle

FC-030.1E is complete only when host activation itself becomes the enforcement boundary for the already-frozen SQL migration and compatibility mechanisms:

> SQL Server hosts migrate/adopt through C, verify through D, and become operational only after D returns `Compatible`; every failure before that point is deterministic, secret-safe, cancellation-aware, and prevents workloads from starting.

After E.6 closes the whole FC-030.1 matrix, FC-030.2 may begin and migration 005 may be designed against a fully enforced production startup boundary.
