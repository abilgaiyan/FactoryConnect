# FC-031.2D.1 — Evaluation Authority Store Contract

Status: **IMPLEMENTED / REVIEW REQUIRED**

Parent slice: **FC-031.2D — State / Activity Continuity Authority**

## Scope

FC-031.2D.1 freezes the portable operation algebra for `EvaluationAuthority` publication and the recovery boundary that later state/activity processor integration must obey.

This slice does not implement instance-transition behavior, modify `MachineStateActivityProcessor`, compose an authoritative current-state cut, add SQL persistence, or introduce semantic-reader, API, or dashboard behavior.

## Authority identity

Evaluation authority is independently addressed by:

```text
ObservationProcessorId stateProcessorId
+ ObservationStreamId observationStreamId
```

`StateProjectionAuthorityRevision` is provider-owned publication order for that identity. It is not derived from durable observation position.

## Logical publication

One logical evaluation publication contains:

```text
StateProcessorId
ObservationStreamId
EvaluatedThrough
MachineState
LastConsumedInstanceId
AppliedContinuityPolicy
```

These fields form `EvaluationAuthorityReplayIdentity`.

`ExpectedRevision` is deliberately excluded from replay identity. It records the provider revision observed before evaluation and participates only in compare-and-swap.

### Invariants

`EvaluatedThrough` is the greatest mapped durable input incorporated by the logical evaluation. It is not the generic FC-024 processing checkpoint and is not an independently inferred raw-observation high-water.

`LastConsumedInstanceId` is the instance of the observation at `EvaluatedThrough`. It is semantic transition state for the next evaluation and is not decorative provenance.

`AppliedContinuityPolicy` records the continuity policy applied to produce the published machine state. It is part of deterministic replay identity and therefore cannot change under exact replay.

The provider allocates `StateProjectionAuthorityRevision`. Callers do not derive or select the next revision.

## Publication algebra

### First changed publication

```text
current authority    absent
expected revision    null
logical publication  new

result
    Accepted / NewPublication
    revision = 0
```

### Changed continuation

```text
current authority    present at revision R
expected revision    R
logical publication  new and forward evaluation progress

result
    Accepted / NewPublication
    revision = R + 1
```

A changed continuation must not move `EvaluatedThrough` backward or publish a second contradictory logical evaluation at the current durable position. Those conditions are provider conformance requirements for the implementation slice.

### Exact replay / lost acknowledgement

If the currently stored authority has exactly the same replay identity as the proposal, the operation is an exact replay regardless of whether the supplied expected revision is now stale.

```text
result
    Accepted / ExactReplay
    return existing authority
    allocate no revision
```

This rule applies at revision exhaustion as well.

A superseded historical publication is not exact replay merely because it was once accepted. Once later evaluation authority has become current, replay of an older logical publication is stale/conflicting.

### Conflict

If replay identity does not match current authority and the expected revision does not identify the current authority, publication returns:

```text
EvaluationAuthorityPublicationConflict
```

No authority mutation is permitted.

### Revision exhaustion

If a changed publication would require incrementing `ulong.MaxValue`, publication returns:

```text
EvaluationAuthorityRevisionExhausted
```

No authority mutation or partial publication is permitted. Exact replay of the current logical publication remains legal.

### Empty / no-new-input invocation

No new logical evaluation means no new authority publication and therefore no revision churn.

The only no-new-input recovery action allowed is retry of an already-determined logical publication using the identical deterministic replay identity.

## Recovery boundary — authoritative strategy

FC-031.2D freezes **atomic joint publication** as the authoritative integration strategy.

The following sequence is forbidden as a completed processor integration:

```text
commit FC-024 state/activity projection + derived outputs
    ↓
independently publish FC-031 EvaluationAuthority
```

It has an unrecoverable observable cut in the current repository:

```text
projection commit succeeds
EvaluationAuthority publication is missing
replay sees projection position already consumed
replay skips the mapped inputs needed to reconstruct authority
```

The current public `MachineStateActivityProjection` is intentionally not expanded into `EvaluationAuthority`. It remains a distinct FC-024 processing projection contract.

Later FC-031.2D integration must instead provide one provider-owned atomic publication boundary whose successful commit makes all of the following visible together:

```text
FC-024 MachineStateActivityProjection
FC-024 derived state-change outputs
FC-024 derived activity-period outputs
FC-031 accepted EvaluationAuthority
```

Failure before that joint commit makes none of the new publication visible. Loss of acknowledgement after the joint commit must converge through the exact-replay algebra frozen above.

This decision does not require the public projection and authority records to become one type and explicitly forbids treating them as one semantic contract.
