# B5 — SQL ordinal-string equality/order parity

`CanonicalStringV1` is frozen and permits every well-formed Unicode string within its independent UTF-16/UTF-8 size limits. It performs:

```text
no normalization
no case folding
no trimming
no BOM stripping
no control/NUL stripping
```

Therefore provider-neutral string identity/order authority is exact `.NET StringComparer.Ordinal` semantics.

The current physical candidate uses:

```text
nvarchar(...)
COLLATE Latin1_General_100_BIN2
```

That representation is **not accepted as equivalent merely by inspection**.

Classification:

```text
SQL outer boundary + reader semantic authority
```

with an additional physical requirement:

> Whenever SQL equality/order is used before reconstruction, the SQL comparison result itself MUST be proven equivalent to `StringComparer.Ordinal` over the complete frozen CanonicalStringV1 domain exercised by the physical contract.

Reader validation cannot repair an SQL comparison that already changed membership, uniqueness, order, or continuation behavior.

---

# 1. SQL operations affected by B5

B5 applies to every SQL comparison whose result has provider-neutral semantic meaning before reader reconstruction, including:

```text
reporting ORDER BY
startAfter lexicographic seek predicates
reporting/query equality filters
projection logical structured-field comparisons used by SQL predicates
cross-kind OperandName UNIQUE enforcement
projection processor textual identity where compared
machine-shift roster identity UNIQUE enforcement
roster occurrence identity UNIQUE enforcement
roster deterministic ORDER BY
all string-bearing PK/UQ/index keys
```

A reader-side ordinal comparison remains mandatory for persisted mutual-integrity validation, but it is not a substitute for SQL parity in the operations above.

# 2. Required parity claims

For every test pair `x,y` in the permanent characterization corpus:

```text
sign(StringComparer.Ordinal.Compare(x, y))
==
sign(SQL_COMPARE_BIN2(x, y))
```

and:

```text
StringComparer.Ordinal.Equals(x, y)
==
SQL_EQUAL_BIN2(x, y)
```

The SQL side must be exercised using the exact target type/collation used by migration 005, not an approximate collation or client-side emulation.

Required target form:

```sql
nvarchar(256) COLLATE Latin1_General_100_BIN2
```

and, where applicable, the exact narrower physical width such as `nvarchar(128)`.

# 3. Mandatory characterization corpus

The real-SQL pre-freeze proof MUST include at least:

```text
basic ordinal distinctions
  "x" vs "X"
  "x" vs "y"
  composed U+00E9 vs decomposed U+0065 U+0301
  leading U+FEFF vs no U+FEFF

trailing-space identities
  "x" vs "x "
  "x " vs "x  "
  " " vs "  "
  trailing U+0020 adjacent to other scalar boundaries

NUL/control identities
  "x" vs "x\u0000"
  "x\u0000" vs "x\u0000\u0000"
  embedded U+0000
  TAB / LF / CR where field-domain validation permits the primitive value

BMP boundaries
  U+0000
  U+0001
  U+007F
  U+0080
  U+00FF
  U+0100
  U+07FF
  U+0800
  U+D7FF
  U+E000
  U+FFFD
  U+FFFF

supplementary-scalar boundaries
  U+10000
  U+10001
  U+1F600
  U+10FFFE
  U+10FFFF
  pairs spanning BMP -> supplementary boundaries
  pairs whose UTF-16 surrogate-code-unit order is material

length boundaries
  256 ASCII UTF-16 code units
  256 x U+00E9
  128 supplementary scalars = 256 UTF-16 code units
  256 x U+0800 = 768 UTF-8 bytes
  maximum accepted strings differing only at first/middle/final position

prefix relationships
  empty primitive vs non-empty where primitive testing is applicable
  "a" vs "aa"
  "a" vs "a\u0000"
  "a" vs "a "
  long prefix with differing final scalar
```

Unpaired surrogate input is rejected by CanonicalStringV1 before SQL persistence and therefore is not a valid SQL parity vector.

# 4. Permanent semantic-operation proofs

Pairwise scalar comparison is necessary but not sufficient. Real SQL must also prove end-to-end behavior for the operations that migration 005 will depend on.

## 4.1 Reporting ORDER BY

Rows whose only differences are B5-sensitive strings must sort exactly as the provider-neutral comparer for:

```text
PeriodSiteId
ShiftScheduleAssignmentId
ShiftId
ProductionOrderId
OperationId
PartId
OperatorId
MetricKey
DefinitionVersion
```

including trailing-space, NUL, BMP/supplementary-boundary, and maximum-length vectors.

## 4.2 startAfter seek

For every B5-sensitive tail component, prove page boundaries with:

```text
page size 1
page size >1
ascending
mixed descending primary scalar + ascending tail
cursor at each sensitive value
```

No duplicate and no omission are permitted.

## 4.3 Equality filters

Exact provider-neutral equality filters must distinguish every pair that `StringComparer.Ordinal` distinguishes, including:

```text
"x" vs "x "
embedded/trailing U+0000
composed vs decomposed forms
case differences
supplementary-scalar distinctions
```

## 4.4 Cross-kind OperandName uniqueness

The physical UQ on `(ProjectionRowId, OperandName)` must reject exactly the pairs considered equal by `StringComparer.Ordinal` and permit exactly the distinct pairs.

In particular, if SQL considers `"x"` and `"x "` equal while `StringComparer.Ordinal` considers them distinct, the current physical representation FAILS B5.

## 4.5 Roster identity / occurrence identity / ordering

The roster parent UQ, occurrence complete identity, and deterministic occurrence ordering must preserve the same ordinal distinctions for their string components.

B3's NONCLUSTERED key-width resolution is independent of B5: a key can fit physically and still have incorrect equality semantics.

# 5. Failure policy

If any required equality or ordering vector disagrees:

```text
B5                              FAIL
Latin1_General_100_BIN2         NOT ACCEPTED as ordinal authority
FC-030.2A physical authority    HOLD
Migration 005                   MUST REMAIN ABSENT
```

The permitted response is to design and review an exact SQL ordinal representation, for example a bounded deterministic binary comparison key whose semantics are proven equivalent to `StringComparer.Ordinal`.

The following are explicitly forbidden as implicit fallbacks:

```text
narrow CanonicalStringV1
trim values
normalize Unicode
strip U+0000
strip U+FEFF
change case semantics
accept SQL equality as "close enough"
repair ordering/filter membership after SQL pagination
```

Any replacement comparison key becomes physical-schema authority and requires key-width/index/conformance review before FC-030.2A can freeze.

---

# 6. B5 acceptance rule

B5 closes only when the supported real SQL Server target proves all of the following exactly:

```text
BIN2 equality == StringComparer.Ordinal equality
BIN2 ordering == StringComparer.Ordinal ordering
trailing-space identities preserve ordinal distinction
embedded/trailing U+0000 identities preserve ordinal distinction
BMP/supplementary-scalar boundaries preserve ordinal order
maximum-length accepted strings preserve ordinal order/equality
reporting ORDER BY parity
startAfter pagination parity
query-filter equality parity
OperandName UQ parity
roster identity/UQ parity
roster occurrence identity/order parity
```

An exact PASS authorizes retaining `Latin1_General_100_BIN2` as the migration-005 physical string comparison authority. Anything else requires redesign.
