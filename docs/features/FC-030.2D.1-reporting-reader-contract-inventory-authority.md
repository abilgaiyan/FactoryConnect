## Slice boundary

```text

IOperationalMetricReportingQueryProvider
```

This slice authorizes documentation only.

It does **not** authorize:

```text

persistence/composition registration
schema or migration changes
new indexes
provider-neutral contract changes
reporting formula changes
metric calculation or aggregation
alternate reporting truth

```

Any implementation work begins only after this authority is frozen.

## Central invariant

> **SQL readers reconstruct and validate the exact publication committed by 2C. They never repair, normalize, infer, or recalculate reporting truth.**

The SQL provider is a persistence adapter over the provider-neutral reporting model. It is not a reporting engine and is not an alternate source of metric truth.

## Authority precedence

FC-030.2D reader behavior follows this precedence:

```text
provider-neutral projection / query contracts
        ↓
provider-neutral report filtering and ordering semantics
        ↓
FC-030.2C frozen publication / checkpoint semantics
        ↓
FC-030.2A / 2B frozen physical schema and codecs
        ↓
SQL reader implementation strategy
```

SQL predicates, indexes, persisted order keys, denormalized columns, hashes, and binary envelopes are implementation/validation mechanisms. They do not replace the provider-neutral contracts as semantic authority.

## Contract inventory

### Projection query reader

`IOperationalMetricProjectionQueryReader` is the exact projection-summary/detail reconstruction boundary.

Its SQL implementation must return provider-neutral projection state reconstructed from the current committed publication for the requested projection identity. Where detail is requested, full projection evidence is part of that durable truth and must be reconstructed and validated rather than synthesized.

The existing public interface is already observable authority:

```csharp
ReadPeriodSummariesAsync(
    processorId,
    machineId,
    periodId,
    contextKey,
    cancellationToken)

ReadDetailAsync(
    processorId,
    evaluationKey,
    cancellationToken)
```

The SQL implementation must preserve the provider-neutral/in-memory behavior of those methods while applying FC-030.2C current-manifest publication authority.

### `ReadPeriodSummariesAsync` — frozen method semantics

A period-summary read is scoped to one projection processor and one exact reporting period/context identity.

A projection is eligible if and only if all of the following are true in the same checkpoint-stable current publication:

```text
manifest owns the projection row
projection processor == requested processorId
projection key MachineId == requested machineId
projection key PeriodId == requested periodId
projection key ContextKey == requested contextKey
```

Equality is provider-neutral equality. SQL collation, normalization, prefix matching, case folding, or alternate null/optional-value interpretation must not change membership.

A physically present projection row that is not in the current manifest is not eligible and is invisible to this method.

Returned summaries are ordered deterministically by:

```text
DefinitionId.MetricKey     ascending, StringComparer.Ordinal
then
DefinitionId.Version       ascending, StringComparer.Ordinal
```

No additional SQL-specific tie breaker may change the observable order. Within one valid evaluation context/period, duplicate provider-neutral definition identities are not a second ordering case to normalize; if durable state makes the provider-neutral result ambiguous or contradictory, that is corruption.

`ReadPeriodSummariesAsync` reconstructs and validates the projection state necessary to materialize each `OperationalMetricProjectionSummary`. It does **not** require full component/dependency evidence reconstruction merely to return a summary, because evidence is not part of the public summary result.

This narrower evidence boundary does not weaken corruption handling:

```text
projection-summary fields / canonical representations needed for
membership, identity, state, ordering, or summary materialization
    → MUST be validated

component/dependency evidence not read by this summary method
    → need not be traversed solely to materialize the summary
```

A current-manifest projection whose summary-authoritative state is malformed, contradictory, or canonically inconsistent is a hard query failure. It must not be skipped to return the remaining summaries.

### `ReadDetailAsync` — frozen method semantics

`ReadDetailAsync(processorId, evaluationKey, ...)` is an exact lookup in the processor's checkpoint-stable **current manifest**.

Frozen outcomes:

```text
evaluationKey absent from current manifest
    → return null

physical OperationalMetricProjection row exists
but evaluationKey is absent from current manifest
    → return null

current manifest contains evaluationKey
and projection + complete evidence reconstruct validly
    → return the exact provider-neutral OperationalMetricProjection

current manifest contains evaluationKey
but the named projection/evidence state is missing, malformed,
contradictory, or canonically inconsistent
    → hard corruption failure
```

Physical row presence alone never turns an unpublished/historical row into current reporting truth.

Conversely, a current manifest member that cannot be reconstructed is not normal absence and must not be translated to `null`.

For a manifested detail result, reconstruction includes the complete persisted component/dependency evidence snapshot and all frozen canonical validation applicable to that projection.

### Reporting query provider

`IOperationalMetricReportingQueryProvider.ReadWindowAsync(...)` is the provider-neutral filtered, ordered, seek/window boundary:

```text
OperationalMetricReportQuery
+ optional startAfter evaluation key
+ maximumCount
        ↓
IReadOnlyList<OperationalMetricProjectionSummary>
```

The existing provider-neutral authority already defines:

```text
source selection
exact machine ↔ processor binding
period range semantics
exact metric-definition filtering
context filtering
status filtering
period ascending / descending ordering
complete evaluation-key tie breaking
start-after seek semantics
```

The SQL implementation must preserve those semantics exactly. It must not introduce SQL-specific equality, collation, null ordering, period ordering, or cursor semantics.

## Current-publication authority

For each projection processor, the current reporting truth is the complete publication committed by FC-030.2C:

```text
projection checkpoint
+ exact manifest membership
+ projection rows named by that manifest
+ complete evidence for detail reconstruction
```

The manifest is the authority for the currently published projection set. A projection row is not reportable merely because it exists physically in `OperationalMetricProjection`.

Conversely, every current manifest membership must resolve to exactly one valid projection row belonging to the same processor. When a method requires detail, that projection must also reconstruct with its complete valid evidence.

The reader must not:

```text
expose a projection that is outside the current manifest
invent a missing manifest membership
ignore a manifest member because reconstruction is inconvenient
substitute an older projection row
rebuild a projection from metric inputs or definitions
infer missing evidence
```

An impossible current-publication shape is corruption, not an invitation to repair or reinterpret the publication.

## Checkpoint-stable read protocol

FC-030.2C froze the reader observation rule:

```text
ReadCommitted
read checkpoint C1
        ↓
read current manifest
        ↓
read manifest-owned data required by the public method
        ↓
read checkpoint C2
        ↓
accept only when C1 == C2
otherwise discard the entire attempt and retry
```

A checkpoint change during the read is **not durable corruption**. It means the reader crossed a valid publication commit boundary. The attempt is discarded in full and retried.

No rows from a rejected attempt may leak into a result, page, continuation boundary, cache, or reconstructed projection.

### Frozen checkpoint-stability retry policy

Repository inventory found no existing shared checkpoint-stability retry policy for `IOperationalMetricProjectionQueryReader` or `IOperationalMetricReportingQueryProvider`.

The existing MTConnect transient-acquisition retry/backoff policy is acquisition-specific and is **not** shared authority for SQL reporting reads. FC-030.2D must not silently reuse its options, delay algorithm, or failure classification.

D.1 therefore owns and freezes the SQL reporting-reader checkpoint-stability retry policy as follows:

```text
Maximum attempts: 3 total attempts, including the initial attempt.

Retry trigger:
    C1 != C2 for the processor publication read during that attempt.

Retry action:
    discard the entire unstable attempt;
    check cancellation;
    immediately restart from a fresh C1.

Backoff:
    none / zero artificial delay.

Success:
    return only an attempt for which the applicable processor
    checkpoint is stable across the complete method reconstruction.

Exhaustion:
    after the third unstable attempt, fail the read with
    InvalidOperationException.

Cancellation:
    cancellation has precedence and is propagated rather than
    converted into retry exhaustion.
```

The exhaustion exception means only that no checkpoint-stable publication could be observed within the frozen bounded read policy. It is not durable-corruption classification and must not claim that persisted state is malformed.

A SQL execution/provider failure is not retried under this checkpoint-stability policy merely because it occurred during an attempt. Any future SQL transient-fault retry policy would require its own explicit authority and must not be inferred from this rule.

### Multiple processors

Reporting source selection may contain multiple machine/processor pairs. FC-030.2C publication atomicity is per projection processor; FC-030.2D does not invent a cross-processor global checkpoint or global snapshot.

Each contributing processor must therefore be read from an individually checkpoint-stable, fully validated publication before its rows participate in the combined provider-neutral filter/order/seek result.

The frozen three-attempt budget applies to each logical checkpoint-stability reconstruction operation. An implementation may organize multi-processor reads efficiently, but it may not exceed the budget for one processor by hiding additional attempts inside batching, nor may instability of one processor authorize rows from that processor's rejected attempt to participate in the final combined result.

The SQL provider may choose an efficient physical strategy, but it must not return rows from an unstable attempt for any processor.

## Reconstruction path

The semantic path is frozen as:

```text
requested machine / processor source binding
        ↓
checkpoint C1
        ↓
current manifest membership
        ↓
projection physical row
        ↓
canonical evaluation-key reconstruction
        ↓
projection scalar/state reconstruction
        ↓
[detail only] component / dependency evidence reconstruction
        ↓
provider-neutral OperationalMetricProjection / summary
        ↓
checkpoint C2 stability check
        ↓
provider-neutral query result
        ↓
provider-neutral reporting filter + order + seek semantics where applicable
```

Construction of provider-neutral records is part of validation. SQL readers must not bypass provider-neutral invariants merely because the stored row satisfies SQL constraints.

## Required physical-to-canonical validation

A row is not considered valid merely because SQL Server returned it. Where the frozen physical contract stores a canonical representation together with denormalized/queryable representations, the reader must prove that they describe the same provider-neutral value when those representations participate in the requested public method.

At minimum later implementation must validate the applicable frozen representations below.

### Processor and source binding

The selected reporting source binds one machine to one projection processor. Reconstructed processor/source identities must agree with the immutable processor binding persisted by FC-030.2C.

A row from a different processor, machine, source aggregation processor, or source stream must not be remapped into the requested source.

### Evaluation-key authority

The persisted evaluation key must be validated from the frozen canonical representation:

```text
EvaluationKeyCodecVersion
EvaluationKeyBinary
EvaluationKeyHash
```

Required semantics:

```text
codec version is the supported frozen version
binary envelope decodes exactly
SHA-256(binary) == persisted hash
decoded evaluation key == all persisted denormalized identity columns
```

A hash match alone is insufficient. Exact canonical binary equality/decoding remains authority.

The reader must not normalize strings, regenerate a different-but-equivalent key, or accept a denormalized identity when the canonical binary disagrees.

### Canonical text and order keys

Persisted canonical text/order-key columns used for filtering, equality, ordering, or seeking must be revalidated against the reconstructed provider-neutral values and the frozen codecs, including the applicable canonical string and `StringOrderKeyV2` rules.

SQL collation/order behavior is not allowed to silently substitute for:

```text
StringComparer.Ordinal
provider-neutral optional-value ordering
provider-neutral evaluation-key ordering
```

A stored order key that does not exactly encode the reconstructed provider-neutral text is corruption even if it happens to produce the expected order for the current query.

### Projection state

The reader must reconstruct the persisted projection state without recalculation and validate the provider-neutral invariants for:

```text
processor identity
evaluation key
source revision
status
value
unit
reason code
reason operand
```

The provider-neutral `OperationalMetricProjection` / summary invariants remain authoritative for valid status/value/reason shape.

### Evidence

When the public method returns projection detail, all evidence belonging to a current manifest projection must be reconstructed as the frozen provider-neutral subtype:

```text
component evidence
or
dependency evidence
```

The SQL subtype discriminator and nullable-column shape must agree exactly with the reconstructed subtype.

Component evidence must preserve and validate its persisted operand/source identity, source revision, dimension, value, unit, input count, and timestamps.

Dependency evidence must preserve and validate its operand name, exact definition identity, frozen dependency snapshot codec/binary/hash, and recursively reconstructed dependency projection.

Evidence ordinal/order is a persistence reconstruction mechanism; it must not be used to alter provider-neutral operand identity or synthesize missing operands.

Duplicate or contradictory evidence that violates provider-neutral projection invariants is corruption.

`ReadPeriodSummariesAsync` and summary-window reads are not required to traverse evidence solely to construct a summary. That optimization is authorized only because evidence is outside the observable summary contract; it does not authorize use of corrupt summary-authoritative projection state.

## Corruption outcome

Durable corruption of current-publication state required by the requested public method is a **hard query failure**.

The reader must not return a partial successful result around corruption.

Examples include, without limiting later conformance coverage:

```text
manifest member missing/mismatching its projection row
unsupported evaluation-key codec version
malformed evaluation-key binary
EvaluationKeyHash mismatch
canonical binary vs denormalized identity mismatch
persisted text vs frozen order-key mismatch
invalid status/value/reason shape
projection/source revision mismatch
invalid evidence subtype shape during detail reconstruction
missing required evidence data during detail reconstruction
duplicate/contradictory provider-neutral evidence during detail reconstruction
invalid dependency snapshot codec/binary/hash during detail reconstruction
reconstructed dependency projection inconsistent with its evidence identity
```

D.1 freezes the **failure meaning** and, for checkpoint-stability exhaustion only, the `InvalidOperationException` surface. It does not introduce a new public exception type for durable corruption. A later implementation slice may choose an internal/provider corruption exception vocabulary consistent with existing FactoryConnect failure conventions, but it may not convert durable corruption into an empty row, skipped row, default value, repaired projection, or successful partial page.

Cancellation remains cancellation. A SQL execution failure remains a provider/storage failure unless authoritative reconstruction proves a semantic corruption condition. A checkpoint change is a retry condition, not corruption.

## Filtering authority

`OperationalMetricReportQuerySemantics.Matches(...)` is the provider-neutral membership authority for reporting-window queries.

SQL may push down filters for efficiency, but the observable result must be equivalent to applying the provider-neutral semantics to valid current-publication projection summaries.

This includes exact semantics for:

```text
(machine, processor) source membership
shift [StartsAtOrAfterUtc, StartsBeforeUtc)
production day [FromInclusive, ToExclusive)
exact metric definition IDs
context filter matching
status membership
```

`ReadPeriodSummariesAsync` has its own narrower exact membership contract frozen above and must not be reinterpreted through the broader reporting-window query shape.

A denormalized SQL column is not independently authoritative merely because it is indexed.

## Hidden-corrupt-row rule

SQL filtering must never make corruption invisible when that corruption could change result membership, ordering, or the seek boundary.

Frozen semantic rule:

> **A current-publication row whose corrupt persisted representation could cause it to be incorrectly included, excluded, ordered, or positioned relative to `startAfter` must not be silently hidden by SQL predicate/index pushdown. The read must fail as corruption unless the implementation has independently validated enough authoritative representation to prove that the row cannot affect the requested result.**

This is a semantic requirement, not a mandate for a particular physical query plan.

D.1 does **not** require every implementation to perform an unconditional whole-table scan. A later implementation may use staged reads, manifest-scoped validation, canonical range validation, redundant predicates, validated seek keys, or another proven strategy. What it may not do is treat an unchecked denormalized/indexed value as sufficient authority to omit a potentially relevant corrupt current row.

Rows that are not members of the checkpoint-stable current manifest are not reporting truth and must not appear merely because a broad physical query encounters them. Their physical existence alone does not authorize exposure. For `ReadDetailAsync`, that rule is observable as `null` when the requested key is not a current manifest member.

## Ordering authority

`OperationalMetricReportOrdering.GetEvaluationKeyComparer(...)` is the total-order authority for reporting-window queries.

The frozen ordering behavior includes:

```text
period primary ordering according to requested direction
machine identity tie breaker
complete period identity tie breakers
context identity ordering with provider-neutral optional-value semantics
metric key ordinal ordering
metric version ordinal ordering
```

SQL result ordering must be observationally identical to this comparer.

Persisted binary/order-key columns exist to make that equivalence implementable and verifiable. They do not define a competing SQL-specific order.

A page/window must be deterministic even when multiple projections share the same primary period value.

`ReadPeriodSummariesAsync` does not use this report-window total comparer; its method-specific order remains exactly `MetricKey` ordinal ascending then `DefinitionVersion` ordinal ascending.

## Seek / cursor authority

`IOperationalMetricReportingQueryProvider.ReadWindowAsync(...)` receives an optional `startAfter` evaluation key. The later SQL implementation must implement a strict seek according to the same total comparer used for result ordering:

```text
startAfter == null
    → begin at the first matching key in requested total order

startAfter != null
    → return only matching keys strictly after startAfter
       in the requested total order
```

No SQL-specific lexicographic shortcut is valid unless it is proven equivalent to the provider-neutral comparer for every frozen key component and requested direction.

Rows filtered out by the query do not become cursor landmarks merely because they appear physically between matching rows.

D.1 does not redefine the public continuation-token format owned by the reporting query/reader layer. It freezes only the provider SQL window semantics beneath that layer.

## No alternate reporting truth

The reader is forbidden from recalculating or reconstructing metric truth from sources other than the committed projection publication.

Specifically, it must not:

```text
re-run FC-027 metric formulas
re-aggregate metric inputs
reconstruct a missing projection from source facts
recalculate OEE/components
infer a reason code
fill missing evidence
normalize a persisted value into a different value
choose a newer/older source revision than the committed projection
merge multiple projections to create one result
use reporting configuration as metric truth
```

The only valid reportable value/state is the valid provider-neutral projection committed by FC-030.2C.

## Implementation acceptance matrix

Before FC-030.2D reader implementation can close, real SQL Server conformance must prove at minimum:

| Scenario | Required result |
|---|---|
| `ReadPeriodSummariesAsync` exact processor/machine/period/context matches | Returns only current-manifest matching summaries |
| `ReadPeriodSummariesAsync` deterministic definition order | `MetricKey` ordinal ascending, then `DefinitionVersion` ordinal ascending |
| `ReadPeriodSummariesAsync` valid summary with untraversed evidence | Summary succeeds without requiring detail-evidence traversal |
| `ReadPeriodSummariesAsync` corrupt summary-authoritative state | Hard corruption failure; row is not skipped |
| `ReadDetailAsync` key absent from current manifest | `null` |
| `ReadDetailAsync` physical row exists outside current manifest | `null` |
| `ReadDetailAsync` valid manifested key | Exact provider-neutral projection including complete evidence |
| `ReadDetailAsync` manifested key with missing/corrupt projection or evidence | Hard corruption failure; not `null` |
| Stable valid current publication | Exact provider-neutral reconstruction |
| Empty current manifest | Empty summary/window result for that processor without invented projections |
| Checkpoint moves between C1 and C2 | Entire attempt discarded and retried |
| First/second attempts unstable, third stable | Third complete stable attempt succeeds |
| Three consecutive unstable attempts | Read fails with `InvalidOperationException`; no unstable result leaks |
| Cancellation between checkpoint attempts | Cancellation propagated; no exhaustion exception fabricated |
| Stable retry after concurrent publication | Only one complete stable publication contributes rows |
| Multiple processors | Each contributing processor is individually checkpoint-stable; no global snapshot invented |
| Manifest member missing/mismatched projection | Hard corruption failure; no partial result |
| Evaluation-key binary/hash mismatch | Hard corruption failure |
| Canonical key vs denormalized identity mismatch | Hard corruption failure |
| Persisted text/order key mismatch | Hard corruption failure |
| Invalid projection status/value/reason state | Hard corruption failure |

| Cancellation | Cancellation propagated; no fabricated result |

The implementation matrix may add narrower proof cases, but it may not weaken these semantic outcomes.

## Freeze statement

FC-030.2D.1 freezes the reporting reader authority before SQL implementation begins.

The governing boundary is:

> **SQL readers reconstruct and validate the exact publication committed by 2C. They never repair, normalize, infer, or recalculate reporting truth.**

The narrow correction additionally freezes:

```text
ReadPeriodSummariesAsync current-manifest membership + exact method ordering
ReadPeriodSummariesAsync summary-only evidence-validation boundary
ReadDetailAsync manifest-based null / corruption behavior
checkpoint-stability retry policy: 3 total attempts, immediate retry, no backoff,
InvalidOperationException on exhaustion
```

The next FC-030.2D implementation work must remain inside this authority. Any requirement to change schema, publication choreography, provider-neutral query semantics, formula logic, or the meaning of reporting truth must stop and return to architecture review rather than being solved inside the SQL reader implementation.
