# MTConnect Sample / Incremental Acquisition

## Purpose

FC-014 introduces incremental MTConnect observation acquisition through the standard `/sample` endpoint.

The slice extends FC-013 current-state acquisition with sequence-aware observation batches. A caller supplies the sequence from which acquisition should continue, and FactoryConnect returns the observations together with the MTConnect sequence metadata required to continue acquisition.

```text
MTConnect Agent
      ↓
 /sample?from=N
      ↓
MTConnectStreams
      ↓
Header + DeviceStream
      ↓
Sequence-aware observations
      ↓
MachineObservation
      ↓
FC-011 signal mapping
      ↓
Canonical FactoryConnect signal
```

>FC-014 acquires incremental protocol data.

>It does not own continuous polling or cursor persistence.

---

## Incremental Acquisition

MTConnect /sample provides observations from the Agent's sequence buffer.

FactoryConnect supplies the starting sequence explicitly:

fromSequence = 101
        ↓
GET /sample?from=101

The acquisition client is intentionally stateless.

Caller
   │
   │ fromSequence
   ▼
MtConnectSampleClient
   │
   │ GET /sample?from=N
   ▼
MtConnectSampleResult

The client does not remember the previous sequence or automatically issue another request.

Cursor ownership and repeated acquisition belong to a later orchestration slice.

---

## Sequence Model

MTConnect sequence information is protocol acquisition metadata.

It is therefore kept out of the protocol-neutral MachineObservation abstraction.

MachineObservation
    │
    ├── MachineId
    ├── Source
    ├── Address
    ├── Type
    ├── Value
    ├── Quality
    └── Timestamp

An MTConnect sample observation wraps the raw observation with its sequence:

MtConnectSampleObservation
    │
    ├── Sequence
    │
    └── MachineObservation

This preserves the distinction between:

FactoryConnect observation semantics
             and
MTConnect acquisition semantics

Sequence values use unsigned 64-bit integers.

# Sample Result

A /sample response contains both observations and Agent sequence metadata.

FC-014 represents this as:

MtConnectSampleResult
    │
    ├── InstanceId
    ├── FirstSequence
    ├── LastSequence
    ├── NextSequence
    │
    └── Observations
          │
          ├── Sequence
          └── MachineObservation

The header values are preserved directly from the MTConnect response.

## InstanceId

InstanceId identifies the current Agent instance.

FC-014 preserves this value but does not interpret changes in it.

Agent restart detection and recovery policy belong to later acquisition orchestration.

## FirstSequence

FirstSequence identifies the earliest sequence currently represented by the Agent's sequence buffer.

FC-014 exposes the value without applying sequence-window policy.

## LastSequence

LastSequence identifies the latest sequence represented by the Agent.

It is retained as acquisition metadata.

## NextSequence

NextSequence is the continuation cursor supplied by the MTConnect Agent.

FactoryConnect does not derive this value from the observations returned for the selected device.

MTConnect Header
      ↓
 nextSequence
      ↓
MtConnectSampleResult.NextSequence

This distinction is important because an Agent may expose multiple devices and the selected DeviceStream may not contain every sequence generated by the Agent.


## Observation Ordering

MTConnect XML organizes observations by device, component, and category.

Document order therefore does not necessarily represent sequence order across all observations for the selected device.

FC-014 explicitly orders acquired observations by their MTConnect sequence.

```text
XML traversal

101
104
102
103

      ↓

Sequence ordering

101
102
103
104
```

The resulting MtConnectSampleResult.Observations collection therefore represents incremental acquisition order.

## Device Selection

As with FC-013, one MTConnect Agent may expose multiple devices.

Acquisition requires:

FactoryConnect MachineId
        +
MTConnect device key

The device key may match either:

DeviceStream.name
DeviceStream.uuid

The association between the FactoryConnect machine and MTConnect device therefore remains explicit.

If no matching DeviceStream is present, FC-014 returns an empty observation collection while preserving the response header metadata.

## Shared Observation Parsing

FC-013 introduced conversion from MTConnect stream values into raw MachineObservation records.

FC-014 reuses the same conversion rules for /sample.

The common behavior is now centralized in:

MtConnectObservationParser

The parser owns:

- DeviceStream selection
- dataItemId extraction
- timestamp parsing
- MTConnect category to SignalType conversion
- numeric value conversion
- UNAVAILABLE handling
- MachineObservation creation

The two acquisition paths therefore share the same raw observation semantics:

```text
                 MTConnectStreams
                       │
          ┌────────────┴────────────┐
          │                         │
   /current parser            /sample parser
          │                         │
          └────────────┬────────────┘
                       ↓
            MtConnectObservationParser
                       ↓
              MachineObservation

```              

This prevents /current and /sample from developing different interpretation rules for the same MTConnect values.

## Value Types

FC-014 retains the FC-013 stream-category mapping:

Samples → SignalType.Numeric
Events → SignalType.Enumeration
Condition → SignalType.Text

Numeric values are parsed using invariant culture.

An MTConnect value of UNAVAILABLE is represented as:

Value   = null
Quality = ObservationQuality.Uncertain

All other successfully parsed values use ObservationQuality.Good.

## Validation

FC-014 requires valid MTConnect sequence metadata.

The sample response must contain a Header with valid:

instanceId
firstSequence
lastSequence
nextSequence

Each acquired observation must also contain a valid sequence.

Missing or invalid required sequence values are rejected as malformed acquisition data.

HTTP failures continue to propagate through the acquisition client rather than being converted into protocol observations.

Retry and recovery policy are intentionally outside this slice.

## Acquisition Boundary

FC-014 establishes the following boundary:

Caller
   │
   │ fromSequence
   ▼
MtConnectSampleClient
   │
   ▼
MTConnect /sample
   │
   ▼
MtConnectSampleParser
   │
   ├── Header metadata
   ├── Device selection
   └── Sequence ordering
   │
   ▼
MtConnectSampleResult
   │
   ├── NextSequence
   │
   └── Sequence-aware observations

The caller decides what to do with NextSequence.

The protocol client only acquires and represents the MTConnect response.

## Relationship to Current Acquisition

FC-013 and FC-014 serve different acquisition purposes.

FC-013
/current
    ↓
Latest known machine state


FC-014
/sample?from=N
    ↓
Observations occurring through
the MTConnect sequence stream

/current is useful for obtaining a current snapshot.

/sample provides the sequence-aware data required for incremental acquisition.

Both ultimately produce the same protocol-neutral MachineObservation representation.

## Scope Boundary

FC-014 implements:

MTConnect /sample endpoint construction
acquisition from a supplied sequence
MTConnect header sequence metadata
per-observation sequence preservation
sequence-ordered observation batches
shared /current and /sample observation parsing
device selection by name or UUID
existing value and quality conversion rules
malformed sequence metadata validation
HTTP failure propagation

FC-014 does not implement:

continuous polling
cursor persistence
automatic continuation
retry or backoff
reconnect orchestration
Agent restart recovery
instanceId change policy
sequence-gap recovery policy
configurable sample batch size
canonical signal mapping
machine-state derivation
persistence
admin/setup UI

Those concerns remain outside the protocol acquisition slice.

## Result

FC-014 establishes sequence-aware MTConnect acquisition while preserving FactoryConnect's protocol-neutral observation model.

```text
MTConnect
   │
   ├── /current ──────────────┐
   │                          │
   └── /sample?from=N ────────┤
                              ↓
                    Raw observations
                              ↓
                     MachineObservation
                              ↓
                      FC-011 Mapping
                              ↓
                  Canonical FactoryConnect
                         signal model

FactoryConnect can now acquire both the latest MTConnect state and incremental MTConnect observations.
```

The next acquisition layer can build continuous operation on top of this boundary without placing polling, cursor ownership, or recovery policy inside the MTConnect protocol client.
