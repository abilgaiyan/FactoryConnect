# FC-030.1D.5 — Real-SQL Compatibility Matrix

## Status

D.1 through D.4 are closed and frozen. D.5 is the final runtime-verification conformance slice and does not introduce new compatibility semantics.

## Goal

Prove the complete FC-030.1D runtime compatibility contract against real SQL Server, including every final compatibility classification and the Shared-versus-Exclusive serialization boundary shared with FC-030.1C migration execution.

D.5 is conformance-only. A failing matrix may reveal a defect in the frozen implementation, but D.5 must not silently redefine D.1 through D.4 behavior.

## Complete final-classification matrix

The real-SQL matrix must contain one scenario for every value in `SqlRuntimeCompatibilityClassification`:

```text
Compatible
DatabaseUninitialized
LegacyAdoptionRequired
UnledgeredSchemaIncompatible
MigrationPending
DatabaseNewerThanSupported
MigrationIdentityMismatch
MigrationChecksumMismatch
MigrationHistoryInvalid
MigrationLedgerSchemaInvalid
MigrationSchemaDrift
```

The test scenario vocabulary must match the final classification vocabulary exactly by name and order. Adding, removing, or renaming a final classification therefore requires an explicit D.5 matrix update.

Each scenario must assert:

1. the exact final classification;
2. `IsCompatible` is true only for `Compatible`;
3. diagnostics are empty only for `Compatible` and non-empty for every incompatible result;
4. verification remains read-only and uses the already-frozen D.3/D.4 decision and diagnostic boundaries;
5. persistent SQL Server state is value-equivalent before and after verification; and
6. repeated verification of the unchanged state returns the same classification, `IsCompatible` value, and diagnostics in the same order.

The matrix creates real database states rather than substituting in-memory descriptors for the runtime verifier. Repository migrations 001 through 004 remain the only executable migration authority in this slice.

## Per-scenario persistent-state proof

Every final-classification scenario has a paired state-conformance proof with this exact shape:

```text
capture persistent state
-> verify #1
-> capture persistent state
-> verify #2
-> capture persistent state
-> compare both post-verification snapshots to the original
-> compare ordered diagnostics from verification #1 and #2 structurally
```

The persistent-state snapshot includes at least:

- migration-ledger object presence and object kind;
- migration-ledger object identity metadata;
- deterministic projection of the complete ledger structural metadata;
- exact ordered migration-ledger rows, including `AppliedAtUtc`;
- the complete FactoryConnect-owned structural schema as read by the frozen SQL metadata reader; and
- an unrelated sentinel table and persisted marker value, proving tolerated customer/admin objects remain unchanged.

FactoryConnect-owned schema equality is evaluated through the frozen `SqlSchemaComparator`. Ledger arrays and diagnostics use element-wise structural comparison rather than immutable-container identity.

This proof is specifically required to detect accidental runtime side effects such as:

- creating a missing ledger;
- adopting legacy history;
- applying a pending migration;
- normalizing malformed ledger rows;
- repairing invalid ledger structure;
- repairing live schema drift; or
- modifying unrelated database objects.

## Repeated diagnostic determinism

D.4 froze repeated diagnostic determinism as a value contract. D.5 therefore verifies every final-classification database state twice without changing the state between calls.

For each scenario, the two runtime results must have:

```text
same Classification
same IsCompatible
same diagnostic count
same diagnostic values
same diagnostic order
```

The comparison is structural over diagnostic elements and must not rely on `ImmutableArray` backing-array identity.

## Serialization and commit-boundary proofs

D.5 must prove both lock directions with real SQL Server sessions.

### Runtime waits behind Exclusive

A transaction holding the C migration resource in `Exclusive` mode may change migration-managed state and keep that change uncommitted. A concurrent runtime verifier must be observed waiting on an `APPLICATION` lock and must not complete while that Exclusive boundary remains active.

After the Exclusive transaction commits, the verifier proceeds and classifies the committed state. The conformance case commits a structural drift and requires the verifier to return `MigrationSchemaDrift` with evidence for that committed artifact.

This proves the verifier does not observe ledger/schema state from inside a concurrent migration transaction or from opposite sides of its commit boundary.

### Migration waits behind Shared

A transaction holding the runtime resource in `Shared` mode must block a real `SqlServerMigrationEngine.ApplyAsync` invocation. The migrator session must be observed waiting on an `APPLICATION` lock and must not complete while the Shared boundary remains active.

After the Shared transaction rolls back/releases, the migration engine proceeds normally and the resulting database must verify as `Compatible`.

This proves D.3 runtime verification and C migration execution coordinate on the same transaction-owned application-lock resource with compatible Shared/Exclusive semantics.

## Determinism

Lock contention tests must establish waiting through SQL Server lock metadata rather than relying on timing races alone. The waiting session id is captured from the actual verifier or migrator connection, and the operation is asserted incomplete while SQL Server reports that same session waiting on an application lock.

The bounded wait policy remains the frozen D.3/C policy; D.5 does not introduce another timeout conversion, command timeout, or return-code interpretation.

## Hard boundary

D.5 must not:

- change the final compatibility taxonomy;
- change D.2 history classification or precedence;
- change D.3 transaction isolation, Shared-lock resource, timeout policy, or non-mutation behavior;
- change D.4 diagnostic semantics merely to satisfy a test;
- alter migrations 001 through 004;
- introduce migration 005;
- introduce operational-metric or reporting SQL persistence schema;
- adopt or repair legacy state from the runtime verifier; or
- wire host startup policy before FC-030.1D is closed.

## Closure gate

D.5 and FC-030.1D may close only after all of the following pass on the same branch head:

```text
Release solution build
D.5 real-SQL classification matrix
D.5 matrix vocabulary guard
D.5 per-scenario persistent-state and repeatability matrix
D.1 compatibility contract regression
D.2 history classifier regression
D.3 verifier and lock regression
D.4 diagnostic regression
full Category=SqlServerIntegration suite
git diff --check
```

No final FC-030.1D closure is claimed from focused D.5 tests alone.
