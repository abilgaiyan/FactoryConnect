# FC-031.2D.4B — Pre-Commit Failure and Cancellation Atomicity Proof

Status: **BOUNDARY CLOSED / FROZEN**
Mode: **DOCUMENTATION / PROOF INVENTORY ONLY**
Implementation: **NOT AUTHORIZED**

## 1. Purpose

FC-031.2D.4B freezes the bounded proof authority for failures and cancellation that occur before the joint in-memory state/activity authority provider reaches its atomic commit point.

The governing invariant is:

```text
any failure at an authorized pre-commit proof point,
or cancellation observed by the provider's authoritative pre-lock check
    → the old P/S/A/E tuple remains authoritative
    → no state-change or activity-period output leaks
    → no authority revision is consumed
```

For a fresh lineage, the corresponding invariant is:

```text
pre-commit failure or authoritative pre-lock cancellation
    → no P/S/A/E tuple becomes visible
    → no output history becomes visible
    → no revision is allocated
```

This record inherits all frozen FC-031.2D.1 through FC-031.2D.4A authority. It does not reopen or reinterpret those decisions.

## 2. Scope

FC-031.2D.4B covers only:

- cancellation observed by the joint provider's existing pre-lock cancellation check;
- deterministic reference-provider failures on the changed `NewPublication` path before the atomic dictionary assignment;
- proof that projection, state-change history, activity-period history, and evaluation authority remain entirely unchanged after those failures;
- proof that a failed attempt does not allocate or consume an evaluation-authority revision;
- processor failure propagation only if an existing production seam already exposes the joint provider without introducing processor integration work.

The current repository does not provide such a processor seam for the joint provider, so processor propagation remains deferred.

## 4. Inherited FC-031.2D.4A publication algebra

The 4A classification order remains authoritative and unchanged:

```text
1. intrinsic proposal-local validation
2. complete-payload ExactReplay
3. dual CAS
4. current-state advancement validation
5. revision exhaustion
6. atomic NewPublication
```

FC-031.2D.4B fault injection applies only after a changed proposal has passed the inherited replay, CAS, advancement, and revision-exhaustion classification gates and has entered the `NewPublication` materialization path.

Therefore the 4B fault seam MUST NOT execute for:

```text
ExactReplay
Conflict
RevisionExhausted
```

No 4B proof may change the result precedence frozen by 4A.

## 5. Cancellation authority

The current reference provider performs one authoritative cancellation observation before acquiring its mutation lock:

```csharp
cancellationToken.ThrowIfCancellationRequested();

lock (_gate)
{
    ...
}
```

The normative cancellation contract for FC-031.2D.4B is therefore intentionally narrow.

### 5.1 Authoritative observed cancellation

```text
cancellation observed by the provider's pre-lock check
    → OperationCanceledException
    → no mutation
```

This rule applies to both fresh and established lineages.

### 5.2 After the pre-lock check succeeds

```text
after the provider's pre-lock cancellation check succeeds
    → publication is non-interruptible
    → later cancellation need not be observed
    → cancellation while waiting for _gate need not be observed
    → cancellation during publication need not be observed
    → normal publication classification and commit may complete
```

FC-031.2D.4B does **not** promise cancellation responsiveness between the successful pre-lock check and lock acquisition.

FC-031.2D.4B also does **not** authorize new cancellation checks inside joint publication staging or immediately before commit. Introducing such checks would create new semantics not established by the current provider and could weaken the intended single atomic publication boundary.

## 6. Atomic commit point

For the current reference provider, the authoritative visibility point is the single dictionary assignment:

```csharp
_entries[key] = next;
```

All 4B deterministic failure proof points occur before this assignment.

The provider must never expose a state in which only a subset of the joint tuple is visible.

The joint tuple is conceptually:

```text
P = MachineStateActivityProjection
S = state-change publication/history
A = activity-period publication/history
E = EvaluationAuthority
```

The commit authority is therefore:

```text
before _entries[key] = next
    → old tuple only

after _entries[key] = next
    → complete new tuple only
```

There is no authorized intermediate visible state.

## 7. Deterministic reference-provider fault checkpoints

FC-031.2D.4B defines five deterministic proof points for the in-memory reference provider.

These are **reference-provider proof points only**. They are not portable storage-provider API requirements and MUST NOT be added to `IMachineStateActivityAuthorityStore` or any other portable abstraction.

The checkpoints are:

```text
F1  before new-publication materialization

F2  after EvaluationAuthority construction

F3  after publication-output copies
    - LastStateChanges
    - LastActivityPeriods

F4  after cumulative-history construction
    - StateChangeHistory
    - ActivityPeriodHistory

F5  immediately before
    _entries[key] = next
```

The checkpoints describe actual provider work. They do not imply that the target projection itself is staged by the provider; the projection already exists in the supplied publication.

A future implementation may choose an internal mechanism suitable for deterministic tests, but that mechanism must remain provider-specific and non-portable.

## 8. Fault-seam activation rule

The deterministic fault seam may activate only for a proposal classified as a valid changed forward publication.

Conceptually:

```text
proposal
    ↓
intrinsic validation
    ↓
ExactReplay?
    yes → return ExactReplay
    no
    ↓
dual CAS valid?
    no → return Conflict
    yes
    ↓
advancement valid?
    no → return Conflict
    yes
    ↓
revision exhausted?
    yes → return RevisionExhausted
    no
    ↓
NewPublication materialization
    ↓
F1 ... F5 may execute
    ↓
_entries[key] = next
```

The seam MUST NOT execute while determining replay, conflict, or exhaustion classifications.

## 9. Existing-lineage failure oracle

For an established lineage, each injected F1–F5 failure must leave the complete authoritative state exactly unchanged.

The proof oracle must establish equality of at least:

```text
Projection
    ProcessorId
    StreamId
    Position
    Signals
    State
    ActiveState
    ActiveStartedAt

EvaluationAuthority
    StateProcessorId
    ObservationStreamId
    EvaluatedThrough
    MachineState
    LastConsumedInstanceId
    AppliedContinuityPolicy
    ProjectionRevision

State-change cumulative history
Activity-period cumulative history
```

After the failure:

```text
ReadAsync()              == pre-failure snapshot
ReadStateChanges()       == pre-failure history
ReadActivityPeriods()    == pre-failure history
ProjectionRevision       == pre-failure revision
```

No state-change or activity-period item from the failed proposal may leak into cumulative history.

## 10. Fresh-lineage failure oracle

For a fresh lineage, each authorized pre-commit failure point must leave the lineage absent.

The proof must establish:

```text
ReadAsync()              == null
ReadStateChanges()       == empty
ReadActivityPeriods()    == empty
```

No revision may become externally observable or reserved by the failed attempt.

A later successful first publication therefore remains authoritative at revision `0`.

## 11. Revision-allocation authority

Revision allocation is part of the atomic new-publication materialization, not an independently committed side effect.

Therefore:

```text
F1–F5 failure
    → no revision is consumed
```

For established state at revision `R`:

```text
failed changed publication
    → current revision remains R

subsequent valid changed publication
    → next committed revision remains R + 1
```

For fresh state:

```text
failed first publication
    → no authority exists

subsequent valid first publication
    → committed revision is 0
```

No hidden revision counter or sequence may advance independently of the joint dictionary assignment.

## 12. Cancellation proof matrix

At minimum, the future bounded implementation must prove:

```text
B-01  pre-cancelled fresh PublishAsync
      → OperationCanceledException
      → no P/S/A/E state
      → no histories

B-02  pre-cancelled established PublishAsync
      → OperationCanceledException
      → exact old P/S/A/E tuple
      → exact old histories
      → revision unchanged
```

These tests prove only cancellation observed by the authoritative pre-lock check.

They MUST NOT claim that cancellation which occurs after that check is required to abort publication.

## 13. Failure proof matrix

At minimum, the future bounded implementation must prove deterministic failure at each reference-provider checkpoint:

```text
B-03  F1 — before new-publication materialization
B-04  F2 — after authority construction
B-05  F3 — after publication-output copies
B-06  F4 — after cumulative-history construction
B-07  F5 — immediately before dictionary assignment
```

For each checkpoint, the established-lineage proof must show:

```text
old P unchanged
old S history unchanged
old A history unchanged
old E unchanged
revision unchanged
```

At least one fresh-lineage proof must establish that a pre-commit failure leaves the complete lineage absent and that the subsequent first successful publication still receives revision `0`.

The implementation may cover fresh-lineage failure at every checkpoint if useful, but 4B does not require multiplying the matrix where the single-assignment invariant is already deterministically proven.

## 14. Processor failure propagation

The current production `MachineStateActivityProcessor` consumes `IMachineStateActivityProjectionStore`, not `IMachineStateActivityAuthorityStore`.

Therefore the 4A joint provider is not presently reachable from the processor without performing processor/joint-authority integration work.

FC-031.2D.4B MUST NOT add such integration merely to prove failure propagation.

Accordingly:

```text
processor failure propagation
    → DEFERRED
```

If a future already-authorized production seam exposes the joint provider without changing continuity semantics, propagation may be proven in the appropriate later slice.

## 15. Portable-provider boundary

F1–F5 are deterministic proof instrumentation for the in-memory reference provider only.

They do not impose any requirement that other storage providers expose equivalent named checkpoints, hooks, callbacks, enums, or APIs.

Portable conformance remains semantic:

```text
if a provider reports/throws a failure before its joint commit becomes authoritative
    → no partial P/S/A/E state may become visible
```

How another provider establishes or tests that property is provider-specific.

No fault-injection surface belongs in the portable joint-store contract.

## 16. Non-goals

FC-031.2D.4B does not prove or authorize:

- ambiguous/lost acknowledgement after a successful commit;
- automatic or processor-level ExactReplay retry orchestration;
- replay reconstruction after restart;
- concurrent or competing publication behavior;
- Preserve/Reset transition execution;
- `LastConsumedInstanceId` integration into processor transitions;
- continuity-policy application in the processor;
- DI registration or composition ownership;
- SQL persistence;
- Core semantic reader behavior;
- HTTP API behavior;
- dashboard behavior.
