# FC-031.2D.3 — Atomic State / Activity Authority Integration

Status: CLOSED / FROZEN

Mode: Documentation-only authority inventory

Implementation authority: NOT AUTHORIZED

## 1. Scope

FC-031.2D.3 freezes the integration contract for publishing state/activity projection state, derived outputs, and `EvaluationAuthority` as one authoritative provider-owned state transition.

It freezes:

- coherent provider-owned starting reads;
- sole mutation ownership for each state/activity authority lineage;
- permitted secondary read-only authority surfaces;
- deterministic continuity-calculation input/output boundaries;
- dual projection-position / authority-revision CAS expectations;
- canonical complete-payload replay equality;
- exact-replay-first publication precedence;
- strictly forward changed publication;
- all-or-nothing projection/output/authority visibility;
- conflict and revision-exhaustion semantics;
- processor success/failure mapping;
- the current mapped-runtime cursor boundary; and
- the FC-031.2D.5 composition-proof obligation.

It does not authorize:

- `MachineStateActivityProcessor` implementation changes;
- in-memory provider changes;
- dependency-injection registration changes;
- failure-injection, concurrency, or competing-publication proof;
- SQL persistence;
- semantic-reader implementation;
- API or dashboard work; or
- any FC-031.2E+ work.

```text
2D.3  atomic integration semantics                 CLOSED / FROZEN
2D.4  failure/replay/competing-publication proof   NOT AUTHORIZED
2D.5  in-memory composition/conformance             NOT AUTHORIZED
```

## 2. Governing mutation-ownership rule

For one state/activity lineage:

```text
(StateProcessorId, ObservationStreamId)
```

the governing rule is:

```text
one lineage
one underlying authority state
one joint mutation owner
multiple read-only projections permitted
no independently composed authority writer
```

After joint integration exists, the joint state/activity authority provider is the sole mutation owner for the `EvaluationAuthority` used by that lineage.

The same mutation owner publishes:

```text
MachineStateActivityProjection
DurableMachineStateChangedEvent[]
DurableMachineActivityPeriod[]
EvaluationAuthority
```

as one logical persistence boundary.

This is a provider/composition invariant, not merely a restriction on `MachineStateActivityProcessor`.

Two independently usable writers MUST NOT be composed over the same underlying state/activity authority lineage.

## 3. Standalone authority surfaces

The portable `IEvaluationAuthorityStore` publication algebra remains valid, but for a lineage whose authority is jointly owned:

```text
standalone consumers
    MAY read EvaluationAuthority

standalone EvaluationAuthority publication
    MUST NOT be independently composed over the same lineage
```

An independent standalone authority writer over joint-owned state could otherwise create:

```text
EvaluationAuthority new
MachineStateActivityProjection old
```

which is prohibited by the atomicity contract.

The exact interface shape remains an implementation choice. A valid decomposition may separate read and mutation roles, for example:

```text
IEvaluationAuthorityReader
    ReadAsync(...)

IEvaluationAuthorityStore
    portable publication algebra
    usable only where authority is independently owned

IStateActivityEvaluationStore
    coherent read
    joint publication
    sole composed writer for state/activity lineage
```

The type names are illustrative. The frozen rule is ownership.

Permitted:

```text
one underlying authority state
one mutation owner
multiple read-only surfaces
```

Prohibited:

```text
one underlying authority state
multiple independently usable mutation surfaces
```

## 4. Provider-owned coherent starting read

The continuity calculator MUST NOT establish its starting state from independently timed projection and authority reads.

The authoritative starting read returns one coherent provider-owned observation of:

```text
MachineStateActivityProjection?
EvaluationAuthority?
```

### 4.1 Fresh

```text
Projection absent
EvaluationAuthority absent
```

is valid.

### 4.2 Established continuation

```text
Projection present
EvaluationAuthority present
```

is valid only when:

```text
Projection.ProcessorId
    == EvaluationAuthority.StateProcessorId

Projection.StreamId
    == EvaluationAuthority.ObservationStreamId

Projection.Position
    == EvaluationAuthority.EvaluatedThrough

Projection.State
    == EvaluationAuthority.MachineState
```

The projection supplies:

```text
Signals
State
ActiveState
ActiveStartedAt
```

The authority supplies:

```text
LastConsumedInstanceId
AppliedContinuityPolicy
ProjectionRevision
```

### 4.3 Incoherent start

A mismatched or one-sided pair remains invalid under FC-031.2D.2.

The joint read path MUST NOT hide, repair, or implicitly adopt such a state.

Concrete failure representation remains an implementation decision.

## 5. Runtime cursor read versus calculator authority read

The current `MappedObservationProcessingRuntime` reads `MachineStateActivityProjection.Position` and uses it as the mapped-observation reader `startAfter` cursor.

That read selects candidate input. It is not the authoritative FC-031 calculator snapshot.

The frozen sequence permits:

```text
runtime reads projection cursor
    ↓
runtime reads candidate mapped observations
    ↓
processor performs coherent provider-owned
Projection + EvaluationAuthority read
    ↓
processor ignores already-incorporated positions
    ↓
continuity calculation uses the coherent pair
```

A publication between the runtime cursor read and the processor coherent read may cause redundant candidate delivery, but MUST NOT cause duplicate evaluation or authority advancement.

## 6. Deterministic calculator boundary

FC-031.2D.2 owns continuity semantics. FC-031.2D.3 freezes the persistence boundary around that calculation.

Conceptually the calculator consumes:

```text
StateActivityContinuityInput
    CoherentCurrentState
        Projection?
        EvaluationAuthority?

    ContinuityPolicy
        one resolved CurrentStateContinuityPolicy

    Observations
        ordered DurableMappedMachineObservation[]
```

The calculator performs no persistence and allocates no authority revision.

Its outcome is:

```text
NoAdvance
```

or one deterministic joint publication proposal.

## 7. Joint publication proposal

An advancing calculation produces one proposal containing:

```text
ExpectedProjectionPosition
ExpectedAuthorityRevision

TargetProjection
StateChanges[]
ActivityPeriods[]

Authority semantic target
    StateProcessorId
    ObservationStreamId
    EvaluatedThrough
    MachineState
    LastConsumedInstanceId
    AppliedContinuityPolicy
```

The calculator MUST NOT allocate `StateProjectionAuthorityRevision`; revision allocation remains provider-owned.

The proposal must satisfy:

```text
TargetProjection.ProcessorId
    == Authority.StateProcessorId

TargetProjection.StreamId
    == Authority.ObservationStreamId

TargetProjection.Position
    == Authority.EvaluatedThrough

TargetProjection.State
    == Authority.MachineState
```

All derived outputs must belong to the target projection advancement under existing FC-024 output-identity semantics.

## 8. Intrinsic proposal validation

Before replay classification, CAS classification, revision-exhaustion classification, revision allocation, or mutation, the provider MUST reject intrinsically invalid joint proposals.

Intrinsic validation covers proposal-local coherence among:

```text
TargetProjection
StateChanges[]
ActivityPeriods[]
Authority semantic target
```

An intrinsically invalid proposal:

```text
MUST be rejected before replay classification
MUST be rejected before CAS classification
MUST be rejected before revision-exhaustion classification
MUST allocate no revision
MUST mutate nothing
```

The concrete validation mechanism and public invalid-proposal representation remain implementation decisions.

## 9. Dual CAS expectation

Changed publication is authorized only against both progression tokens observed by the coherent starting read.

### Fresh publication

```text
ExpectedProjectionPosition = null
ExpectedAuthorityRevision  = null
```

### Established continuation

If the coherent read observed:

```text
Projection.Position                    = P
EvaluationAuthority.ProjectionRevision = R
```

then the proposal carries:

```text
ExpectedProjectionPosition = P
ExpectedAuthorityRevision  = R
```

For a proposal that is not exact replay, both expected values must identify the current provider state.

If either is stale or contradictory:

```text
→ Conflict
→ no revision allocation
→ no projection mutation
→ no state-change mutation
→ no activity-period mutation
→ no EvaluationAuthority mutation
```

`Projection.Position` remains the FC-024 projection-side progression token. `StateProjectionAuthorityRevision` remains the FC-031 authority-side publication token.

No additional projection revision is introduced by 2D.3.

## 10. Complete joint replay identity

`EvaluationAuthorityReplayIdentity` is necessary but insufficient for replay classification of a joint state/activity publication because it does not contain projection signal/activity context or derived outputs.

Exact replay therefore compares the complete logical joint payload:

```text
TargetProjection
    ProcessorId
    StreamId
    Position
    Signals
    State
    ActiveState
    ActiveStartedAt

StateChanges[]
ActivityPeriods[]

EvaluationAuthorityReplayIdentity
    StateProcessorId
    ObservationStreamId
    EvaluatedThrough
    MachineState
    LastConsumedInstanceId
    AppliedContinuityPolicy
```

Excluded from replay identity:

```text
ExpectedProjectionPosition
ExpectedAuthorityRevision
provider-assigned StateProjectionAuthorityRevision
```

Expected CAS state and provider-assigned revision are not part of the deterministic logical publication payload.

## 11. Canonical structural replay equality

Complete joint replay equality means canonical structural equality, not collection-reference equality.

For `Projection.Signals`, `StateChanges`, and `ActivityPeriods`:

```text
same count
same deterministic order
same element values
```

Exact replay also requires complete publication-owned output equality:

```text
no missing output
no additional output
no changed output
```

A proposal is NOT exact replay merely because `EvaluationAuthorityReplayIdentity` matches while any of these differ:

```text
Projection.Signals
Projection.ActiveState
Projection.ActiveStartedAt
StateChanges
ActivityPeriods
```

Such a proposal is contradictory, not replay.

The implementation may choose any internal canonicalization/comparison mechanism that preserves this semantic definition.

## 12. Frozen publication classification order

The exact classification order is:

```text
1. Validate intrinsic joint-payload coherence.

   If invalid:
       → reject
       → no replay/CAS classification
       → no revision allocation
       → no mutation

2. Compare complete canonical joint replay identity.

   If exact match:
       → Accepted / ExactReplay
       → return existing EvaluationAuthority
       → no CAS rejection
       → no revision allocation
       → no mutation

3. Compare ExpectedProjectionPosition
   AND ExpectedAuthorityRevision.

   If either does not identify current provider state:
       → Conflict
       → no mutation

4. Validate strictly forward changed publication.

   If changed proposal is non-forward or contradictory:
       → Conflict
       → no mutation

5. Determine whether another StateProjectionAuthorityRevision
   can be allocated.

   If revision space is exhausted:
       → RevisionExhausted
       → no mutation

6. Otherwise atomically publish:

       MachineStateActivityProjection
       DurableMachineStateChangedEvent[]
       DurableMachineActivityPeriod[]
       EvaluationAuthority

       allocate exactly one new authority revision
       → Accepted / NewPublication
```

The critical recovery precedence is:

```text
ExactReplay precedes CAS rejection.
ExactReplay precedes revision exhaustion.
```

## 13. Strictly forward changed publication

A changed publication is valid only when evaluation advances beyond the currently authoritative position.

A non-replay proposal with:

```text
EvaluatedThrough < current EvaluatedThrough
```

is a conflict.

A non-replay proposal that changes semantic publication state at the same `EvaluatedThrough` is also a conflict.

This applies the frozen 2D.1 forward-publication algebra to the complete joint payload.

## 14. Lost-acknowledgement replay

The required recovery case is:

```text
joint publication commits successfully
    ↓
caller does not observe acknowledgement
    ↓
same deterministic joint calculation is retried
with stale expected tokens
    ↓
provider finds complete canonical joint payload already current
    ↓
Accepted / ExactReplay
    ↓
existing EvaluationAuthority and revision returned
    ↓
no duplicate outputs
no revision churn
no mutation
```

This is why exact replay precedes CAS and revision-exhaustion checks.

## 15. Atomic visibility

A successful new publication makes all four publication components visible together:

```text
MachineStateActivityProjection
DurableMachineStateChangedEvent[]
DurableMachineActivityPeriod[]
EvaluationAuthority
```

No observer may see an accepted intermediate state such as:

```text
Projection new
EvaluationAuthority old
```

or:

```text
EvaluationAuthority new
Projection old
```

or:

```text
Projection and EvaluationAuthority new
required derived outputs absent
```

The sole-mutation-owner rule is part of this guarantee. Atomicity is not satisfied merely because one method is internally atomic if another independently usable writer can mutate the same underlying authority state.

## 16. Publication result semantics

### Accepted / NewPublication

The provider atomically publishes the complete joint state and allocates exactly one new `StateProjectionAuthorityRevision`.

The accepted result returns the authoritative `EvaluationAuthority` containing that revision.

### Accepted / ExactReplay

The complete canonical logical publication is already current.

The provider returns the existing `EvaluationAuthority` and revision.

No mutation or revision allocation occurs.

### Conflict

A proposal is not exact replay and either its dual CAS expectation is stale/contradictory or it violates strictly forward publication.

Conflict means:

```text
no projection mutation
no state-change mutation
no activity-period mutation
no EvaluationAuthority mutation
no revision allocation
```

### RevisionExhausted

A valid changed strictly-forward publication requires another authority revision but none can be allocated.

Revision exhaustion means:

```text
no projection mutation
no state-change mutation
no activity-period mutation
no EvaluationAuthority mutation
```

Exact replay remains legal at revision exhaustion because it allocates no revision.

## 17. No-input / no-advance semantics

If no newly incorporated mapped durable input advances evaluation:

```text
no continuity boundary is applied
no evaluator state changes
no state-change output is produced
no activity-period output is produced
no joint publication occurs
no authority revision is allocated
```

Lost-acknowledgement retry is distinct: it retries an already-determined logical publication and converges through `Accepted / ExactReplay`.

## 18. Processor integration sequence

The later integration MUST preserve:

```text
candidate mapped observations
    ↓
coherent provider-owned read:
    Projection + EvaluationAuthority
    ↓
validate frozen 2D.2 starting-state coherence
    ↓
ignore already-incorporated positions
    ↓
if no advance:
    return successfully
    no publication
    ↓
use one stable continuity policy
    ↓
run deterministic 2D.2 calculation
    ↓
construct deterministic joint proposal
    ↓
provider validates intrinsic proposal coherence
    ↓
provider classifies replay / CAS / forward progress / exhaustion
    ↓
Accepted / NewPublication
or Accepted / ExactReplay
    → ProcessAsync reports success

Conflict
or RevisionExhausted
    → ProcessAsync MUST NOT report success
```

There is no independent post-projection `EvaluationAuthority` write in this sequence.

## 19. Processor result mapping

The current state/activity processor returns `ValueTask`, not a domain publication result.

Therefore:

```text
Accepted / NewPublication
    → processor success

Accepted / ExactReplay
    → processor success

Conflict
    → processor failure

RevisionExhausted
    → processor failure
```

Concrete exception/result translation remains an implementation and 2D.4 proof concern.

## 20. Correct mapped-runtime cursor boundary

The raw `ObservationProcessingRuntime` owns a generic processing checkpoint and commits it after `IObservationProcessor.ProcessAsync(...)` succeeds.

The current `MappedObservationProcessingRuntime` does not own an `IObservationProcessingCheckpointStore`.

It uses:

```text
MachineStateActivityProjection.Position
```

as the mapped reader `startAfter` cursor.

Therefore the state/activity ordering is:

```text
joint projection/output/EvaluationAuthority publication
    ↓
processor reports success
    ↓
runtime cycle returns
    ↓
next mapped runtime cycle uses the jointly published
Projection.Position as durable mapped-input progress
```

FC-031.2D.3 introduces no new generic checkpoint.

The general rule is:

```text
the authoritative state/activity publication MUST complete
before the processor reports successful processing;

where a surrounding FC-024 runtime owns a separate generic checkpoint,
processor success necessarily precedes that checkpoint;

for the current MappedObservationProcessingRuntime,
Projection.Position itself is the durable processing cursor.
```

## 21. FC-031.2D.5 composition-proof obligation

FC-031.2D.3 freezes sole mutation ownership. FC-031.2D.5 must later prove that real in-memory provider and DI composition obey it.

For every jointly owned lineage, later proof must establish:

```text
one underlying EvaluationAuthority state exists
one joint mutation owner is composed
secondary read-only authority surfaces may resolve
no independently composed EvaluationAuthority writer can mutate that state
```

Sharing a backing object or lock between two independently usable writers does not satisfy this invariant. The prohibition concerns mutation authority, not merely storage-instance duplication.
