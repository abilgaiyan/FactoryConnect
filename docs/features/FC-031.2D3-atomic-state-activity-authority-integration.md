# FC-031.2D.3 — Atomic State / Activity Authority Integration

Status: DOCUMENTATION RECORD / REVIEW REQUIRED

Mode: Documentation-only authority inventory

Implementation authority: NOT AUTHORIZED

## 1. Scope

This record freezes the integration contract that later FC-031.2D.3 implementation must satisfy when state/activity projection, derived outputs, and `EvaluationAuthority` become one authoritative publication boundary.

It defines:

- provider-owned coherent projection/authority reads;
- sole mutation ownership for state/activity evaluation authority;
- permitted secondary read-only authority surfaces;
- deterministic continuity-calculation input/output separation;
- dual compare-and-swap expectations;
- canonical complete-payload replay equality;
- exact-replay-first classification precedence;
- strictly forward changed publication;
- all-or-nothing projection/output/authority visibility;
- conflict and revision-exhaustion semantics;
- processor success/failure mapping;
- the current mapped-runtime durable cursor boundary; and
- the composition-proof obligation deferred to FC-031.2D.5.

This record does not authorize:

- `MachineStateActivityProcessor` implementation changes;
- in-memory provider implementation changes;
- dependency-injection registration changes;
- failure-injection, concurrency, or competing-publication proof;
- SQL persistence;
- semantic-reader implementation;
- API work;
- dashboard work; or
- any FC-031.2E+ work.

The implementation separation remains:

```text
2D.3  atomic projection / derived-output / EvaluationAuthority integration
2D.4  failure, lost-acknowledgement, replay, and competing-publication proof
2D.5  in-memory composition and whole-slice conformance
```

## 2. Governing ownership principle

For one state/activity authority lineage identified by:

```text
(StateProcessorId, ObservationStreamId)
```

the governing rule is:

```text
one lineage
one underlying authority state
one joint mutation owner
multiple read-only projections permitted
no independently composed authority writer
```

After joint integration exists, the provider that owns the state/activity lineage is the sole mutation owner for the `EvaluationAuthority` used by that lineage.

The joint mutation owner also owns publication of the corresponding:

```text
MachineStateActivityProjection
DurableMachineStateChangedEvent[]
DurableMachineActivityPeriod[]
EvaluationAuthority
```

as one logical persistence boundary.

This requirement is stronger than constraining one processor call sequence. The provider composition itself MUST NOT expose two independently usable mutation surfaces over the same underlying evaluation-authority state.

## 3. Standalone authority publication and read-only surfaces

`IEvaluationAuthorityStore` currently expresses the portable publication algebra through both `ReadAsync(...)` and `PublishAsync(...)`.

That portable contract remains valid, but once a state/activity lineage is jointly owned, an independently composed standalone `PublishAsync(...)` over that same underlying authority state would violate atomicity by allowing:

```text
EvaluationAuthority new
MachineStateActivityProjection old
```

or the inverse through an independent projection writer.

Therefore, for a jointly owned lineage:

```text
standalone consumers
    MAY read EvaluationAuthority

standalone EvaluationAuthority publication
    MUST NOT be independently composed over the same lineage
```

The exact interface decomposition remains an implementation choice. A future implementation may, for example, separate read and write roles:

```text
IEvaluationAuthorityReader
    ReadAsync(...)

IEvaluationAuthorityStore
    portable authority publication algebra
    usable where authority is independently owned

IStateActivityEvaluationStore
    coherent read
    joint publication
    sole composed writer for state/activity lineage
```

These names are illustrative only. The frozen invariant is ownership, not a required type hierarchy.

Permitted:

```text
one underlying authority state
one mutation owner
multiple read-only surfaces
```

Prohibited:

```text
one underlying authority state
multiple independently usable mutation surfaces
```

## 4. Provider-owned coherent starting read

The continuity calculator must not independently read projection and authority as unrelated snapshots.

The authoritative starting read for one lineage must return a coherent pair representing one provider-owned state observation:

```text
MachineStateActivityProjection?
EvaluationAuthority?
```

The read may classify the state using any implementation-specific result shape, but it must preserve the frozen FC-031.2D.2 starting-state semantics.

### 4.1 Fresh state

```text
Projection absent
EvaluationAuthority absent
```

This is a valid fresh starting state.

### 4.2 Established state

```text
Projection present
EvaluationAuthority present
```

This is valid only when:

```text
Projection.ProcessorId
    == EvaluationAuthority.StateProcessorId

Projection.StreamId
    == EvaluationAuthority.ObservationStreamId

Projection.Position
    == EvaluationAuthority.EvaluatedThrough

Projection.State
    == EvaluationAuthority.MachineState
```

The projection supplies the persisted evaluator context:

```text
Signals
State
ActiveState
ActiveStartedAt
```

The authority supplies the previously authoritative:

```text
LastConsumedInstanceId
AppliedContinuityPolicy
ProjectionRevision
```

### 4.3 Incoherent state

Any mismatched or one-sided pair remains invalid under FC-031.2D.2.

The joint provider/read path must not hide, repair, or implicitly adopt an incoherent starting pair.

Concrete failure representation remains an implementation choice.

## 5. Runtime candidate read versus authoritative calculator read

The current `MappedObservationProcessingRuntime` reads `MachineStateActivityProjection` to obtain `Projection.Position` and uses that position as the mapped-observation `startAfter` cursor.

That runtime cursor read is a candidate-input selection mechanism. It is not the authoritative FC-031 continuity snapshot.

The later integration sequence must therefore allow:

```text
runtime reads projection cursor
    ↓
runtime reads candidate mapped observations
    ↓
processor obtains provider-owned coherent
Projection + EvaluationAuthority starting state
    ↓
processor ignores/skips already-incorporated mapped positions
    ↓
continuity calculation uses only the coherent pair
```

A publication that occurs between the runtime cursor read and the processor coherent read may cause redundant candidate input delivery, but MUST NOT cause duplicate evaluation or authority advancement.

## 6. Deterministic continuity-calculation boundary

FC-031.2D.2 defines the continuity semantics. FC-031.2D.3 freezes the integration boundary around that calculation.

Conceptually, the calculation consumes:

```text
StateActivityContinuityInput
    CoherentCurrentState
        Projection?
        EvaluationAuthority?

    ContinuityPolicy
        one resolved CurrentStateContinuityPolicy

    Observations
        ordered DurableMappedMachineObservation[]
```

The calculation itself performs no persistence and allocates no authority revision.

Its logical outcome is either:

```text
NoAdvance
```

or a deterministic joint publication proposal.

`NoAdvance` means no newly incorporated mapped durable observation advances evaluation.

## 7. Joint publication proposal shape

An advancing calculation produces one deterministic logical proposal containing both expected CAS state and target publication state.

Conceptually:

```text
StateActivityEvaluationPublication

ExpectedProjectionPosition
ExpectedAuthorityRevision

TargetProjection
StateChanges[]
ActivityPeriods[]

Authority semantic target
    StateProcessorId
    ObservationStreamId
    EvaluatedThrough
    MachineState
    LastConsumedInstanceId
    AppliedContinuityPolicy
```

The calculator MUST NOT allocate `StateProjectionAuthorityRevision`. Revision allocation remains provider-owned.

The proposal must satisfy the frozen coherence equalities:

```text
TargetProjection.ProcessorId
    == Authority.StateProcessorId

TargetProjection.StreamId
    == Authority.ObservationStreamId

TargetProjection.Position
    == Authority.EvaluatedThrough

TargetProjection.State
    == Authority.MachineState
```

All derived outputs must belong to the target projection advancement under the existing FC-024 output-identity semantics.

## 8. Intrinsic proposal validation

Before replay classification, compare-and-swap classification, revision allocation, or mutation, the provider MUST reject intrinsically invalid joint proposals.

Intrinsic validation includes all proposal-local invariants required to establish that the proposed payload is internally coherent before comparing it with current provider state.

At minimum, the proposal must not contradict the frozen identity/coherence rules between:

```text
TargetProjection
StateChanges[]
ActivityPeriods[]
Authority semantic target
```

An intrinsically invalid proposal:

```text
MUST be rejected before replay classification
MUST be rejected before CAS classification
MUST be rejected before revision-exhaustion classification
MUST allocate no revision
MUST mutate nothing
```

The concrete validation mechanism and public failure representation remain implementation decisions.

## 9. Dual CAS expectation

A changed joint publication is authorized only against the exact projection progress and evaluation-authority revision observed by the coherent starting read.

### 9.1 Fresh publication

```text
ExpectedProjectionPosition = null
ExpectedAuthorityRevision  = null
```

### 9.2 Established continuation

If the coherent read observed:

```text
Projection.Position            = P
EvaluationAuthority.ProjectionRevision = R
```

then the proposal carries:

```text
ExpectedProjectionPosition = P
ExpectedAuthorityRevision  = R
```

These expected tokens represent one coherent starting state and participate together in compare-and-swap.

For a non-replay proposal, the provider may accept a changed publication only when both expectations identify the current provider state.

If either expectation is stale or contradictory:

```text
→ Conflict
→ no revision allocation
→ no projection mutation
→ no derived-output mutation
→ no EvaluationAuthority mutation
```

The existing FC-024 projection position remains the projection-side progression token; FC-031 adds `StateProjectionAuthorityRevision` as the authority-side semantic publication token.

No additional projection revision is introduced by this record.

## 10. Complete joint replay identity

The frozen `EvaluationAuthorityReplayIdentity` is necessary but not sufficient for replay classification of the joint publication because the joint publication also contains projection evaluator context and derived outputs.

Joint exact replay therefore compares the complete logical joint publication payload.

The replay identity includes:

```text
TargetProjection
    ProcessorId
    StreamId
    Position
    Signals
    State
    ActiveState
    ActiveStartedAt

StateChanges[]
ActivityPeriods[]

EvaluationAuthorityReplayIdentity
    StateProcessorId
    ObservationStreamId
    EvaluatedThrough
    MachineState
    LastConsumedInstanceId
    AppliedContinuityPolicy
```

The replay identity excludes:

```text
ExpectedProjectionPosition
ExpectedAuthorityRevision
provider-assigned StateProjectionAuthorityRevision
```

These excluded members describe concurrency expectation or provider-assigned publication metadata, not the deterministic logical payload.

## 11. Canonical structural equality

Complete joint replay equality is canonical structural equality. It is not ordinary `IReadOnlyList` object-reference equality.

### 11.1 Projection signals

`Projection.Signals` must use deterministic ordered element equality:

```text
same count
same deterministic order
same element values
```

### 11.2 State changes

`StateChanges` must use deterministic ordered element equality:

```text
same count
same deterministic order
same element values
```

### 11.3 Activity periods

`ActivityPeriods` must use deterministic ordered element equality:

```text
same count
same deterministic order
same element values
```

### 11.4 Completeness

Exact replay requires the complete publication-owned output set to match.

There may be:

```text
no missing publication output
no additional publication output
no changed publication output
```

A proposal is not exact replay merely because its `EvaluationAuthorityReplayIdentity` matches while any of the following differ:

```text
Projection.Signals
Projection.ActiveState
Projection.ActiveStartedAt
StateChanges
ActivityPeriods
```

Such a proposal is contradictory, not replay.

The implementation may choose any internal canonicalization/comparison mechanism that preserves these semantics.

## 12. Publication classification precedence

The frozen publication order is:

```text
1. Validate intrinsic joint-payload coherence.

   If invalid:
       → reject
       → no replay/CAS classification
       → no revision allocation
       → no mutation

2. Compare complete canonical joint replay identity.

   If exact match:
       → Accepted / ExactReplay
       → return existing EvaluationAuthority
       → no CAS rejection
       → no revision allocation
       → no mutation

3. Compare expected projection position
   AND expected authority revision.

   If either does not identify current provider state:
       → Conflict
       → no mutation

4. Validate strictly forward changed publication.

   If changed proposal is non-forward or contradictory:
       → Conflict
       → no mutation

5. Determine whether the changed publication can allocate
   another StateProjectionAuthorityRevision.

   If revision space is exhausted:
       → RevisionExhausted
       → no mutation

6. Otherwise atomically publish the complete joint state:

       MachineStateActivityProjection
       DurableMachineStateChangedEvent[]
       DurableMachineActivityPeriod[]
       EvaluationAuthority

       allocate exactly one new authority revision
       → Accepted / NewPublication
```

The critical recovery precedence is:

```text
ExactReplay precedes CAS rejection.
ExactReplay precedes revision exhaustion.
```

## 13. Strictly forward changed publication

A changed logical publication is valid only when evaluation advances beyond the currently authoritative evaluated position.

A proposal that is not an exact replay and attempts to publish:

```text
EvaluatedThrough < current EvaluatedThrough
```

is a conflict.

A proposal that is not an exact replay and attempts to change semantic publication state at the same `EvaluatedThrough` is also a conflict.

This preserves the FC-031.2D.1 authority-publication algebra while applying it to the complete joint payload.

## 14. Lost-acknowledgement exact replay

The required recovery case is:

```text
joint publication commits successfully
    ↓
caller does not observe acknowledgement
    ↓
same deterministic joint calculation is retried
with stale expected projection/authority tokens
    ↓
provider finds complete canonical joint payload already current
    ↓
Accepted / ExactReplay
    ↓
existing EvaluationAuthority and revision returned
    ↓
no duplicate outputs
no revision churn
no mutation
```

This is why replay classification precedes CAS and revision-exhaustion classification.

A stale expectation alone does not prevent exact replay when the complete logical publication is already present.

## 15. Atomic visibility

A successful new publication must make the following visible as one provider-owned atomic state transition:

```text
MachineStateActivityProjection
DurableMachineStateChangedEvent[]
DurableMachineActivityPeriod[]
EvaluationAuthority
```

No observer may see an accepted publication in an intermediate state such as:

```text
Projection new
EvaluationAuthority old
```

or:

```text
EvaluationAuthority new
Projection old
```

or:

```text
Projection and EvaluationAuthority new
required derived outputs absent
```

or any other partial publication of the joint payload.

The sole-mutation-owner rule is part of this guarantee: atomicity is not satisfied merely by making one method internally atomic while another independently composed writer can mutate the same underlying authority state.

## 16. Result semantics

The joint provider publication exposes the following semantic outcomes.

### 16.1 Accepted / NewPublication

The provider atomically publishes the complete joint state and allocates exactly one new `StateProjectionAuthorityRevision`.

The accepted result returns the authoritative `EvaluationAuthority` containing that provider-assigned revision.

### 16.2 Accepted / ExactReplay

The complete canonical logical publication is already current.

The provider returns the existing authoritative `EvaluationAuthority` and revision.

No mutation and no revision allocation occur.

### 16.3 Conflict

The proposal is not exact replay and either:

- one or both CAS expectations are stale/contradictory; or
- the changed proposal violates strictly forward publication semantics.

Conflict means:

```text
no projection mutation
no state-change mutation
no activity-period mutation
no EvaluationAuthority mutation
no revision allocation
```

### 16.4 RevisionExhausted

A valid changed strictly-forward publication requires another provider-owned authority revision but no revision can be allocated.

Revision exhaustion means:

```text
no projection mutation
no state-change mutation
no activity-period mutation
no EvaluationAuthority mutation
```

Exact replay remains legal when revision space is exhausted because exact replay allocates no new revision.

## 17. No-input / no-advance behavior

If the processor's authoritative coherent read and supplied candidate observations produce no newly incorporated mapped durable input:

```text
no continuity boundary is applied
no evaluator state changes
no derived output is produced
no joint publication occurs
no authority revision is allocated
```

A lost-acknowledgement retry is distinct from no-advance calculation: it retries a previously determined logical publication and converges through `Accepted / ExactReplay`.

## 18. Processor integration sequence

The later processor integration must preserve this order:

```text
candidate mapped durable observations
    ↓
provider-owned coherent read:
    Projection + EvaluationAuthority
    ↓
validate FC-031.2D.2 starting-state coherence
    ↓
ignore already-incorporated durable positions
    ↓
if no advance:
    return successfully
    no publication
    ↓
use one stable resolved continuity policy
    ↓
run deterministic FC-031.2D.2 calculation
    ↓
construct deterministic joint publication proposal
    ↓
provider validates intrinsic proposal coherence
    ↓
provider classifies replay / CAS / forward progress / exhaustion
    ↓
Accepted / NewPublication
or Accepted / ExactReplay
    → ProcessAsync completes successfully

Conflict
or RevisionExhausted
    → ProcessAsync does not complete successfully
```

There is no independent post-projection `EvaluationAuthority` write in this sequence.

## 19. Processor result mapping

The current mapped state/activity processor surface returns `ValueTask` rather than a domain publication result.

Therefore the integration semantics are:

```text
Accepted / NewPublication
    → processor reports success

Accepted / ExactReplay
    → processor reports success

Conflict
    → processor MUST NOT report success

RevisionExhausted
    → processor MUST NOT report success
```

FC-031.2D.3 freezes only this success/failure meaning.

Concrete exception/result translation and failure proof remain implementation and FC-031.2D.4 concerns.

## 20. Correct mapped-runtime cursor boundary

The current raw `ObservationProcessingRuntime` owns a generic processing checkpoint and commits that checkpoint after `IObservationProcessor.ProcessAsync(...)` succeeds.

The current `MappedObservationProcessingRuntime` is different. It does not own an `IObservationProcessingCheckpointStore`.

Instead, it uses:

```text
MachineStateActivityProjection.Position
```

as the mapped-observation reader `startAfter` cursor.

Therefore the state/activity integration boundary is:

```text
joint projection/output/EvaluationAuthority publication
    ↓
processor reports successful completion
    ↓
runtime cycle returns
    ↓
next mapped runtime cycle reads the jointly published
Projection.Position as durable mapped-input progress
```

No new generic checkpoint is introduced by FC-031.2D.3.

The general ordering invariant remains:

```text
the authoritative state/activity publication MUST complete
before the processor reports successful processing;

where a surrounding FC-024 runtime owns a separate generic checkpoint,
processor success necessarily precedes that checkpoint;

for the current MappedObservationProcessingRuntime specifically,
Projection.Position is the durable processing cursor and there is
no separate generic checkpoint commit.
```

## 21. Composition obligation deferred to FC-031.2D.5

FC-031.2D.3 freezes the sole-mutation-owner invariant.

FC-031.2D.5 must later prove that actual in-memory provider and dependency-injection composition obey it.

The later composition proof must establish that, for every jointly owned `(StateProcessorId, ObservationStreamId)` lineage:

```text
one underlying EvaluationAuthority state exists
one joint mutation owner is composed
secondary read-only authority surfaces may resolve
no independently composed EvaluationAuthority writer can mutate that state
```

FC-031.2D.5 must not weaken the ownership rule by exposing a second writer merely because the two writers share one backing object or lock.

The prohibition is about independently usable mutation authority, not only about storage-instance duplication.
