# 1. Corrected governing publication order

The canonical lock-acquisition order for one projection processor publication is frozen as:

```text
ProjectionProcessor key slot
    ↓
ProjectionCheckpoint key slot
    ↓
OperationalMetricProjection identity rows
    ↓
OperationalMetricProjectionManifest rows
    ↓
OperationalMetricProjectionEvidence rows
```

This order is authoritative anywhere C.1 discusses writer locking, replacement preparation, concurrent writers, or failure injection.

The earlier text that placed evidence before manifest in the atomic writer sequence is superseded.

Important distinction:

> **The frozen order above is lock-acquisition / state-resolution order. Once all required locks are held, individual DML statements may be issued in the dependency-safe order required by migration-005 foreign keys, provided no later lock acquisition reverses the frozen order.**

For example, an obsolete projection row cannot be physically deleted while manifest/evidence rows still reference it. Therefore after its projection identity row, manifest membership, and evidence rows have all been locked in the frozen acquisition order, deletion may execute as:

```text
delete obsolete manifest membership
    ↓
delete obsolete evidence
    ↓
delete obsolete projection row
```

This dependency-safe DML sequence does not redefine the lock order because the dependent rows were already resolved/locked in the authoritative order.

# 2. Corrected Section 8 replacement semantics

Projection replacement remains complete-snapshot replacement, not field patching.

For every advancing commit, the writer prepares durable state in this order:

```text
1. Resolve/lock every affected projection identity row or missing hash slot.
2. Resolve/lock current manifest membership for the processor.
3. Resolve/lock evidence rows for the affected projection rows.
4. Only after those locks are held, perform dependency-safe DML.
```

Required outcome:

```text
absent exact key
    → insert complete projection
    → publish manifest membership
    → insert complete evidence snapshot

existing exact key retained
    → replace complete projection durable state
    → preserve/replace exact manifest membership
    → replace complete evidence snapshot

old manifest key absent from new manifest
    → unpublish manifest membership
    → remove evidence
    → remove obsolete current projection row when physically deleted
```

Evidence remains a complete snapshot. It MUST NOT be patched field-by-field.

A successful commit still atomically publishes:

```text
projection state
+ exact manifest
+ complete evidence
+ checkpoint advancement
```

and an unsuccessful commit leaves the previous complete publication unchanged.

# 3. Frozen writer isolation protocol

FC-030.2C writer transactions SHALL use SQL Server **`Serializable` isolation**.

The writer protocol is frozen as:

```text
open connection
    ↓
begin SqlTransaction(IsolationLevel.Serializable)
    ↓
lock processor key slot
    ↓
lock checkpoint key slot
    ↓
lock projection identity/hash slots
    ↓
lock manifest rows
    ↓
lock evidence rows
    ↓
perform dependency-safe DML
    ↓
advance checkpoint
    ↓
COMMIT
```

The transaction remains `Serializable` for the complete publication attempt, including initial creation, replay validation when performed inside the write path, and ambiguous-outcome reconciliation reads performed before deciding whether mutation is allowed.

No implementation slice may downgrade the publication writer to ordinary `ReadCommitted` and compensate ad hoc without returning to architecture review.

# 4. Exact processor-key locking protocol

Processor lookup/creation uses the frozen `ProcessorKeyBinary` authority and its unique index:

```text
UQ_OperationalMetricProjectionProcessor_ProcessorKeyBinary
```

Inside the `Serializable` writer transaction, the processor key slot MUST be resolved with an update/range-locking read equivalent to:

```sql
SELECT ...
FROM dbo.OperationalMetricProjectionProcessor WITH (UPDLOCK, HOLDLOCK)
WHERE ProcessorKeyBinary = @ProcessorKeyBinary;
```

The query MUST be sargable against the frozen unique processor-key authority.

For an existing row, the row/key is held for update until transaction completion.

For a missing processor, `Serializable` + `UPDLOCK, HOLDLOCK` MUST hold the missing-key range on the unique processor-key index until commit/rollback. That missing-key range is the authority that serializes concurrent initial creation for the same processor key.

After resolution or insertion, the writer MUST revalidate the immutable aggregation-processor and metric-input-stream binding.

A plain checkpoint read outside a commit remains observational and MUST NOT create a processor row.

---

# 5. Exact checkpoint locking protocol

After processor resolution, the checkpoint slot is resolved under the same `Serializable` transaction using `UPDLOCK, HOLDLOCK` on the checkpoint primary-key authority.

Conceptually:

```sql
SELECT ...
FROM dbo.OperationalMetricProjectionCheckpoint WITH (UPDLOCK, HOLDLOCK)
WHERE OperationalMetricProjectionProcessorRowId = @ProcessorRowId;
```

This freezes both cases:

```text
checkpoint exists
    → update lock held through commit/rollback

checkpoint missing
    → missing-key range held through commit/rollback
```

The checkpoint slot is the same-processor compare-and-swap serialization point after processor identity is established.

Two writers with the same expected checkpoint MUST NOT both publish divergent successor states.

---

# 6. Projection / manifest / evidence locking details

After processor and checkpoint locks are held:

### Projection identity rows

Projection identities are resolved by the frozen unique authority:

```text
(OperationalMetricProjectionProcessorRowId, EvaluationKeyHash)
```

using `UPDLOCK, HOLDLOCK` semantics under the existing `Serializable` transaction.

Each hash owner MUST then pass exact codec-version and `EvaluationKeyBinary` equality validation.

When multiple evaluation-key slots are resolved, the writer MUST resolve them in deterministic ascending `EvaluationKeyHash` byte order. This ordering is frozen to reduce same-processor deadlock opportunities.

### Manifest rows

After all required projection identity/hash slots are locked, current manifest membership for the processor is resolved/locked.

When multiple manifest rows are touched, process them in deterministic ascending `OperationalMetricProjectionRowId` order.

### Evidence rows

Evidence is resolved/locked only after projection and manifest locks are held.

When multiple projection evidence sets are touched, process projection IDs in deterministic ascending `OperationalMetricProjectionRowId` order; within one projection, process `(EvidenceKind, EvidenceOrdinal)` in ascending order.

No code path may acquire a manifest/evidence lock and subsequently acquire an earlier projection-identity lock for the same publication attempt.

# 7. Corrected atomic writer sequence

The authoritative write-path sequence is now:

```text
BEGIN TRANSACTION — Serializable

1.  Resolve/lock canonical processor key slot with UPDLOCK, HOLDLOCK.
2.  Create processor if absent and initial commit permits creation.
3.  Revalidate immutable aggregation-processor + input-stream binding.
4.  Resolve/lock checkpoint slot with UPDLOCK, HOLDLOCK.
5.  Classify expected/current/proposed source revision.
6.  Resolve/lock all incoming/current affected projection hash slots
    in ascending EvaluationKeyHash order.
7.  Verify codec version + exact EvaluationKeyBinary for every hash owner.
8.  Resolve/lock current manifest rows in ascending projection-row order.
9.  Resolve/lock affected evidence rows in ascending projection-row,
    evidence-kind, evidence-ordinal order.
10. Perform dependency-safe projection/manifest/evidence DML while retaining
    all previously acquired locks.
11. Revalidate the exact replacement manifest/state required by the commit.
12. Advance the checkpoint last as the logical publication marker.
13. COMMIT.
```

Checkpoint advancement is not a separate commit boundary.

Any implementation optimization that changes this acquisition protocol requires architecture review before merge.

# 8. Reader isolation and old-or-new complete-set visibility

FC-030.2C does **not** require enabling SQL Server snapshot database options.

Complete-set reconstruction used for checkpoint restoration, replay validation, ambiguous-write reconciliation, and provider conformance SHALL use **`ReadCommitted` committed-state reads plus checkpoint-stability validation**:

```text
1. Read checkpoint C1.
2. Read exact manifest for C1.
3. Read/reconstruct every manifest projection and its evidence.
4. Read checkpoint C2 again.
5. Accept the reconstructed set only when C1 == C2.
6. If C1 != C2, discard the reconstruction and retry from the new checkpoint.
```

Because publication writers commit projection rows, manifest, evidence, and checkpoint atomically, `ReadCommitted` never exposes uncommitted publication state. Because source checkpoint positions advance monotonically, any writer commit that occurs during a multi-statement reconstruction changes the durable checkpoint and is detected by the final checkpoint read.

Therefore an accepted reconstruction corresponds to one stable committed publication. A reader may return the old complete set or the new complete set, but MUST NOT return an intermediate mixture.

For unknown processors, two stable absent checkpoint reads with no intervening durable processor/checkpoint publication yield absence.

If a reader implementation instead elects to use `Serializable` for the entire reconstruction, that is semantically compatible but is not required. It MUST still preserve the same publication interpretation and must not introduce a database-wide lock.

Reporting-query readers implemented later in FC-030.2D must satisfy the same externally visible old-or-new publication guarantee. If their query shape cannot prove that guarantee using one committed statement or checkpoint-stability validation, they must return to architecture review rather than weaken C.1.

# 9. Source revision behavior under the frozen protocol

Revision classification remains:

```text
no durable checkpoint
+ ExpectedCheckpoint = null
    → initial commit candidate

current = expected
+ proposed > current
    → advancing commit candidate

current > expected
    → stale expected checkpoint
    → no mutation

proposed < current
    → source revision regression
    → no mutation

proposed = current
    → replay validation only
```

Equal-revision replay succeeds only when checkpoint, exact manifest, projections, and evidence are provider-neutral equivalent to the proposed state.

A replay mismatch MUST NOT rewrite durable history.

---

# 10. Ambiguous-write reconciliation

Ambiguous commit behavior remains frozen, now explicitly under committed-state reconstruction semantics.

On retry:

```text
durable checkpoint == proposed
+ exact durable manifest == proposed manifest
+ every published projection/evidence is provider-neutral equivalent
    → prior publication succeeded
    → return idempotent success

 durable checkpoint == expected
    → prior attempt did not publish
    → retry may perform the publication

 durable checkpoint is neither expected nor proposed
    → stale/concurrent writer conflict

 same proposed revision but different durable state
    → replay mismatch / persisted corruption
```

A client-side failure after SQL Server has committed MUST NOT be converted blindly into a stale-write failure.

# 11. Failure representation clarification

The names used in the original C.1 document are **semantic classifications, not new public exception types**:

```text
CheckpointConflict
ImmutableProcessorBindingConflict
PersistedIdentityCollision
PersistedProjectionCorruption / ReplayMismatch
Cancellation
ProviderFailure
```

C.2 MUST NOT introduce a new public provider-neutral exception hierarchy merely because these labels appear in documentation.

Representation is frozen as follows:

| Semantic classification | Required representation |
|---|---|
| Checkpoint conflict / stale writer | `InvalidOperationException`, consistent with existing projection-store precedent. |
| Immutable processor binding conflict | `InvalidOperationException`. |
| Persisted evaluation-key hash collision | `InvalidOperationException`. |
| Replay mismatch / persisted projection corruption detected by store reconstruction | `InvalidOperationException`. |
| Cancellation before confirmed commit | `OperationCanceledException` / derived cancellation exception through normal .NET cancellation semantics. |
| Unexpected SQL provider failure | Preserve the originating `SqlException`; do not translate it into a semantic conflict based only on an error number. |

When a SQL uniqueness/concurrency error may represent either an expected race or a true identity collision, the store MUST reread authoritative durable state first. If that reread proves one of the semantic conflicts above, throw the corresponding `InvalidOperationException`; otherwise preserve the SQL provider failure.

Internal/private helper exception types are permitted only if they do not become a new provider-neutral/public contract and are translated to the frozen surface before leaving the SQL store boundary.

# 12. Corrected rollback and failure-injection ordering

Failure injection MUST follow the frozen lock-acquisition/state-resolution order.

Required rollback points are:

```text
after processor key-slot resolution / optional creation
after checkpoint-slot resolution
after projection-identity resolution or projection mutation
after manifest resolution or mutation
after evidence resolution or mutation
immediately before checkpoint advancement
immediately after checkpoint UPDATE but before COMMIT
```

For every injected pre-commit failure:

```text
processor creation/binding effects
checkpoint
projection rows
manifest membership
evidence
```

MUST roll back to the previous complete committed publication.

The acceptance proof must not use an evidence-before-manifest failure order as an alternate authority.
