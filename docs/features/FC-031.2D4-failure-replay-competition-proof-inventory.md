# FC-031.2D.4 — Failure, Replay, and Competition Proof Inventory

Status: DOCUMENTATION RECORD / REVIEW REQUIRED

## 1. Scope and authority

This record defines the proof obligations for FC-031.2D.4 above the frozen FC-031.2D.1–2D.3 contracts.

It authorizes no production implementation, provider/test implementation, failure-injection hook, concurrency harness, retry-policy implementation, DI composition, FC-031.2D.5 work, or FC-031.2E+ work.

No frozen 2D.1–2D.3 decision is reopened by this inventory.

## 2. Complete observable oracle

Every joint-publication proof reasons about the complete authoritative tuple:

```text
P = MachineStateActivityProjection
S = DurableMachineStateChangedEvent[]
A = DurableMachineActivityPeriod[]
E = EvaluationAuthority

Joint observable state = (P, S, A, E)
```

A proof is incomplete if it checks only `E`, only `P`, or only authority revision while another publication-owned component can differ.

At quiescent observation cuts, a failed or competing operation must expose either the complete prior tuple or the complete accepted tuple. Mixed tuples are forbidden.

## 3. Recovery-layer vocabulary

Three concepts are distinct.

### 3.1 ExactReplay

`ExactReplay` is a provider classification of a submitted complete joint proposal whose canonical logical payload already equals the current complete joint payload.

It is not a generic processor-recovery result.

### 3.2 NoAdvance

`NoAdvance` is a fresh calculation outcome after a coherent `P + E` read when no supplied mapped durable input advances beyond the already incorporated position.

`NoAdvance` creates no joint proposal and makes no publication call.

### 3.3 LostAcknowledgement

`LostAcknowledgement` means the joint provider may already have committed the complete publication although the caller did not observe successful acknowledgement.

The recovery mechanism depends on whether the already-calculated proposal is still retained.

## 4. Provider lost-acknowledgement recovery

If the caller retains the exact deterministic proposal after a committed publication whose acknowledgement was lost:

```text
joint publication commits P/S/A/E
    ↓
acknowledgement is lost
    ↓
same complete proposal is submitted directly
    ↓
provider compares current complete payload
    ↓
Accepted / ExactReplay
```

Required outcome:

```text
same P
same S
same A
same E
same StateProjectionAuthorityRevision
no duplicate state-change output
no duplicate activity-period output
no mutation
```

Exact replay MUST precede dual-CAS rejection and revision-exhaustion rejection as frozen by 2D.3.

Repeated direct submission of the same complete proposal must remain `ExactReplay` with stable `(P,S,A,E)` and stable revision.

## 5. Fresh processor/runtime recovery after committed publication

If the ambiguous publication failure unwinds and a later invocation or process restart begins, the previous in-memory proposal is not assumed to exist.

The required recovery path is:

```text
joint publication already committed
    ↓
later runtime cycle supplies candidate input
    ↓
processor performs authoritative coherent P + E read
    ↓
committed advancement is already visible
    ↓
already-incorporated candidate positions are skipped
    ↓
if no genuinely new input remains:
    NoAdvance
    ↓
no proposal
no PublishAsync call
```

A fresh invocation MUST NOT reconstruct the previous proposal merely to obtain `ExactReplay`.

It MUST NOT:

```text
infer a prior proposal from current P/E plus incoming observations
re-create prior state/activity outputs solely to force ExactReplay
reapply continuity boundaries for already-incorporated observations
require durable proposal reconstruction that 2D.1–2D.3 never authorized
```

If the supplied candidate batch contains an already-incorporated prefix followed by genuinely new positions, the processor skips the incorporated prefix and evaluates only the new suffix from the coherent current state.

## 6. Optional processor-local retry

An implementation MAY retain an already-calculated proposal inside one invocation and retry an ambiguous provider failure directly. Such a direct retained-proposal retry would converge through provider `ExactReplay` if the first attempt committed.

FC-031.2D.4 does not require this strategy and does not authorize a retry policy. Correctness is already provided by provider exact-replay capability plus fresh coherent reread / `NoAdvance` convergence.

## 7. Intrinsic-invalid proposal rejection

Intrinsic joint-payload validation has first classification precedence.

Proof must cover proposal-local contradictions including at least the semantic classes represented by:

```text
projection processor != authority processor
projection stream != authority stream
projection position != authority EvaluatedThrough
projection state != authority MachineState

derived output belongs to wrong processor
derived output belongs to wrong stream
derived output lies outside the proposed projection advancement

other complete-payload contradictions required by the frozen joint contract
```

An intrinsically invalid proposal MUST be rejected before:

```text
replay classification
CAS classification
revision-exhaustion classification
revision allocation
mutation
```

Observable result:

```text
P unchanged
S unchanged
A unchanged
E unchanged
revision unchanged
```

The exact invalid-proposal representation and validation implementation remain implementation decisions.

## 8. Pre-commit failure cuts

The proof matrix is semantic rather than tied to implementation line numbers.

At minimum, future proof must establish no mutation for failures occurring before the atomic commit point in these classes:

```text
F1  coherent starting read does not complete
F2  deterministic continuity calculation does not complete
F3  calculation completes but publication has not begun
F4  intrinsic proposal validation fails/throws before mutation
F5  projection publication state is being prepared/staged
F6  state-change outputs are being prepared/staged
F7  activity-period outputs are being prepared/staged
F8  EvaluationAuthority is being prepared/staged
F9  failure immediately before the indivisible commit point
```

For every pre-commit failure cut:

```text
P = old
S = old
A = old
E = old
revision = old
processor does not report success
```

No particular failure-injection mechanism is frozen by this record.

## 9. Cancellation ordering

Required cancellation proofs include:

```text
C1  token canceled before processor work
C2  cancellation observed during calculation before publication
C3  token already canceled when joint publication begins
```

For cancellation before the atomic commit point:

```text
operation propagates cancellation
P/S/A/E unchanged
revision unchanged
```

Once an indivisible atomic commit has occurred, a later caller-side cancellation or lost acknowledgement cannot retroactively remove the committed tuple. Recovery then follows Section 4 or Section 5 depending on whether the retained proposal still exists.

## 10. Successful publication baseline

### Fresh publication

From absent joint state, a valid fresh proposal with fresh expected tokens publishes the complete tuple atomically and allocates authority revision `0`.

### Forward continuation

From coherent current state at projection position `P0` and authority revision `R`, a valid changed strictly-forward proposal using the matching dual expectation publishes the complete new tuple atomically and allocates exactly `R + 1`.

No independent projection revision is introduced. Projection position remains the FC-024 projection-side progression token.

## 11. Complete-payload exact replay

Provider exact replay compares the complete canonical logical proposal frozen by 2D.3:

```text
TargetProjection
    ProcessorId
    StreamId
    Position
    Signals
    State
    ActiveState
    ActiveStartedAt

StateChanges[]
ActivityPeriods[]

EvaluationAuthorityReplayIdentity
    StateProcessorId
    ObservationStreamId
    EvaluatedThrough
    MachineState
    LastConsumedInstanceId
    AppliedContinuityPolicy
```

Excluded from replay identity:

```text
ExpectedProjectionPosition
ExpectedAuthorityRevision
provider-assigned StateProjectionAuthorityRevision
```

Collection equality is canonical structural equality:

```text
same count
same deterministic order
same element values
no missing element
no additional element
```

The proof matrix must demonstrate that matching `EvaluationAuthorityReplayIdentity` alone is insufficient.

Negative replay cases include at least:

```text
changed Projection.Signals
changed Projection.ActiveState
changed Projection.ActiveStartedAt
changed state-change output
missing state-change output
additional state-change output
changed activity-period output
missing activity-period output
additional activity-period output
changed deterministic collection ordering
```

Such proposals are not `ExactReplay`.

## 12. Dual-CAS conflict matrix

From coherent starting state:

```text
Projection.Position                    = P0
EvaluationAuthority.ProjectionRevision = R
```

a non-replay changed proposal is authorized only if both expected values identify current state.

The proof matrix must independently cover:

```text
stale ExpectedProjectionPosition only  → Conflict
stale ExpectedAuthorityRevision only   → Conflict
both expected tokens stale             → Conflict
```

Every conflict means:

```text
P unchanged
S unchanged
A unchanged
E unchanged
no revision allocation
```

## 13. Backward and same-position contradictions

With otherwise matching CAS expectations:

```text
proposed EvaluatedThrough < current EvaluatedThrough
    → Conflict
```

A non-replay changed proposal at the same `EvaluatedThrough` is also `Conflict`.

Same-position negative cases must cover semantic changes including:

```text
MachineState
LastConsumedInstanceId
AppliedContinuityPolicy
Projection.Signals
Projection.ActiveState
Projection.ActiveStartedAt
StateChanges[]
ActivityPeriods[]
```

No same-position contradictory proposal may mutate `(P,S,A,E)` or allocate a revision.

## 14. Competing publishers

### 14.1 Different proposals from one coherent pair

Two publishers observe the same coherent starting pair `(P0,R)` and submit different valid strictly-forward proposals carrying that same dual expectation.

Required outcome:

```text
exactly one Accepted / NewPublication
exactly one Conflict
winner authority revision = R + 1
```

Final `(P,S,A,E)` must belong entirely to the winning proposal. No loser-owned output or mixed tuple may be visible.

### 14.2 Identical proposals from one coherent pair

Two publishers submit the same complete logical proposal from the same coherent starting pair.

Required outcome:

```text
one Accepted / NewPublication
one Accepted / ExactReplay
one revision increment total
one logical output set
same authoritative E returned for the logical publication
```

This proves replay-before-CAS behavior under competition.

No concrete concurrency harness is authorized by this record.

## 15. Revision exhaustion

When current `StateProjectionAuthorityRevision == ulong.MaxValue`, a valid changed strictly-forward proposal that requires another revision must return `RevisionExhausted` and mutate nothing:

```text
P unchanged
S unchanged
A unchanged
E unchanged
no wraparound
```

A direct complete-payload exact replay remains legal at `ulong.MaxValue` because it allocates no revision:

```text
Accepted / ExactReplay
same P/S/A/E
same revision = ulong.MaxValue
no duplicate outputs
no mutation
```

## 16. Quiescent atomic-visibility proof

The required minimum proof observes provider state at deterministic quiescent cuts around success, failure, replay, and competition.

Forbidden observable states include:

```text
P new / E old
E new / P old
P and E new / required S or A absent
new outputs / old P
winner E / loser P or outputs
partial loser output mixed with winner tuple
```

At each required observation cut, the visible state is exactly the complete old tuple or the complete accepted new tuple.

A continuous stress observer is not required by this inventory. It may be supplementary if later implementation details justify it.

The sole-mutation-owner composition proof remains FC-031.2D.5.

## 17. Processor and runtime result propagation

The frozen processor result mapping remains:

```text
Accepted / NewPublication → ProcessAsync success
Accepted / ExactReplay    → ProcessAsync success
Conflict                  → ProcessAsync failure
RevisionExhausted         → ProcessAsync failure
```

Future proof must show that `Conflict` and `RevisionExhausted` are not swallowed by `MachineStateActivityProcessor` or `MappedObservationProcessingRuntime`.

The current mapped runtime has no separate generic processing checkpoint. `MachineStateActivityProjection.Position` is the mapped durable-input cursor.

Therefore failed changed publication cannot report processor success or advance a separate mapped-processing checkpoint.

Concrete exception/result translation remains an implementation decision.

## 18. Preserve recovery at both layers

A Preserve scenario must include multiple acquisition-instance boundaries in one logical publication and enough signal changes to exercise derived output behavior.

### Provider layer

After successful joint publication, direct submission of the retained identical complete proposal must return `ExactReplay` with:

```text
same final projection signals/state/activity
same LastConsumedInstanceId
same AppliedContinuityPolicy
same state-change outputs
same activity-period outputs
same authority revision
```

### Fresh processor/runtime layer

After the committed publication, a fresh invocation must coherently reread current `P/E`, skip all already-incorporated observations, and converge through `NoAdvance` when nothing new remains.

It must not reapply Preserve boundaries or recreate prior outputs.

If a new suffix exists, only that suffix is evaluated from the already-committed Preserve result.

## 19. Reset recovery at both layers

A Reset scenario must include multiple acquisition-instance boundaries and prove the frozen reset semantics.

### Provider layer

Direct retained-proposal replay after committed publication returns `ExactReplay` with the same complete tuple and revision.

### Fresh processor/runtime layer

A fresh invocation rereads the committed `P/E`, skips incorporated observations, and reaches `NoAdvance` when nothing new remains.

It MUST NOT:

```text
reapply the Reset boundary
resurrect discarded prior-instance signal context
manufacture an old-state → Unknown transition
complete an abandoned prior activity
recreate or duplicate Unknown → evaluated-state output
```

If a new suffix exists, evaluation begins from the already-authoritative post-Reset state.

## 20. Stale runtime cursor and overlapping input

The mapped runtime may have selected candidate observations using a projection cursor that is stale relative to a publication that committed before processing resumes.

The processor's coherent `P + E` read governs calculation.

If all supplied candidate positions are already incorporated:

```text
skip all
→ NoAdvance
→ no proposal
→ no PublishAsync
→ no revision churn
```

If only a prefix is incorporated:

```text
skip incorporated prefix
apply no continuity boundary to skipped observations
evaluate only genuinely new suffix
```

This proves that runtime candidate selection is not the final evaluation-authority decision.

## 21. NoAdvance versus ExactReplay

The proof suite must keep these paths observably distinct:

```text
Direct retained proposal retry
    → provider ExactReplay

Fresh calculation with no new input
    → NoAdvance
    → no provider publication call
```

Position skipping alone does not prove provider exact-replay semantics, and provider exact replay is not required to reconstruct a proposal after restart.

## 22. Processor/stream lineage isolation

Joint authority is isolated by exact `(StateProcessorId, ObservationStreamId)` lineage.

Required proof classes:

```text
same processor / different streams
different processors / same stream
different processors / different streams
```

Publication, replay, conflict, failure, competition, or revision exhaustion in one lineage must not alter another lineage's:

```text
P
S
A
E
revision
```
