# FC-030.1E.2 — SQL Provider Composition and Concrete Startup Gate

## Status

Implemented on the feature branch; blocking shared-configuration-snapshot review finding resolved; awaiting local verification before closure/freeze.

FC-030.1E.1 is closed/frozen. API and Edge host lifecycle wiring remain outside this slice and belong to E.3/E.4.

## Goal

Bind the provider-neutral `IPersistenceStartupGate` through the already-selected persistence provider and implement the SQL Server sequence:

```text
selected SQL Server provider
    → C migration/adoption engine
    → D runtime compatibility verifier
    → Compatible only
    → startup gate succeeds
```

Non-SQL providers retain existing behavior through a cancellation-aware no-op startup gate.

## Provider-selection authority

`AddFactoryConnectPersistence` remains the single authority that selects the configured persistence provider.

Provider registration now exposes a startup-gate factory in addition to the existing persistence-services factory. Persistence finalization binds `IPersistenceStartupGate` from the selected registration only.

Consequences:

```text
SQL Server registered + InMemory selected
    → SQL startup gate is not constructed
    → SQL connection string is not required by the startup gate
    → no SQL migration or verification can run

SQL Server selected
    → SQL registration constructs SqlServerPersistenceStartupGate
```

Existing provider registrations remain source-compatible because `IPersistenceProviderRegistration.CreateStartupGate` has a default cancellation-aware no-op implementation and the existing `PersistenceProviderRegistration` constructors use that same no-op behavior.

## Immutable SQL configuration snapshot

The selected SQL registration owns one lazily-created immutable configuration snapshot shared by both of its factories:

```text
SQL provider registration
    → Lazy<SqlServerPersistenceConfigurationSnapshot>
       ├─ ConnectionString
       └─ SqlPersistenceStartupOptions

startup-gate factory ─┐
                      ├─ same Lazy.Value
services factory ─────┘
```

The snapshot is created on the first selected-provider factory resolution, not during provider registration. This preserves the existing invariant that merely registering an unselected SQL provider does not require valid SQL configuration.

Once created, configuration reloads cannot cause the startup gate and persistence stores to bind different databases or different startup lock-timeout values. Therefore the database migrated and verified by the gate is the same configured database captured for the persistence workloads.

`LazyThreadSafetyMode.ExecutionAndPublication` ensures concurrent first resolutions publish one snapshot instance rather than independently binding configuration.

## SQL startup configuration

The SQL Server startup orchestration configuration lives under the existing provider section:

```text
PersistenceProviders:SqlServer:ConnectionString
PersistenceProviders:SqlServer:Startup:LockTimeout
```

`Startup:LockTimeout` defaults to 30 seconds when omitted.

The configured `TimeSpan` is passed through `SqlPersistenceStartupOptions`, which delegates validation to the frozen `SqlMigrationLockTimeout` authority. E.2 does not reimplement timeout rounding/range rules.

The same configured timeout is used by:

```text
C Exclusive FactoryConnect.SqlMigration lock
D Shared FactoryConnect.SqlMigration lock
```

## Concrete SQL gate

`SqlServerPersistenceStartupGate` owns orchestration only.

Its sequence is:

```text
observe cancellation
    ↓
open migration-stage SqlConnection
    ↓
SqlServerMigrationEngine.CreateDefault().ApplyAsync(...)
    ↓
open separate verification-stage SqlConnection
    ↓
SqlServerRuntimeSchemaCompatibilityVerifier.CreateDefault().VerifyAsync(...)
    ↓
Compatible → return
non-Compatible → DatabaseIncompatible carrying exact D result
```

Separate connections preserve the frozen C/D transaction, lock, and cleanup ownership boundaries.

Connection-open failures are classified by the stage whose connection is being opened:

```text
migration connection/open failure
    → MigrationOperationalFailure

verification connection/open failure
    → VerificationOperationalFailure
```

## Failure and cancellation precedence

```text
C stage throws OperationCanceledException
    → propagate exact OCE
    → D not invoked

C stage throws other exception
    → MigrationOperationalFailure
    → exact cause preserved
    → D not invoked

C succeeds; D stage throws OperationCanceledException
    → propagate exact OCE

C succeeds; D stage throws other exception
    → VerificationOperationalFailure
    → exact cause preserved

D returns non-Compatible
    → DatabaseIncompatible
    → exact SqlRuntimeCompatibilityResult preserved

D returns Compatible
    → startup gate succeeds
```

E.2 uses the frozen `SqlPersistenceStartupCancellationPolicy` before generic exception translation.

## Composition tests

`SqlPersistenceStartupGateCompositionTests` proves without requiring a real SQL instance:

1. the selected provider owns the resolved startup-gate factory;
2. registering SQL Server does not construct/use SQL startup behavior when InMemory is selected;
3. default provider startup behavior remains cancellation-aware and no-op;
4. SQL orchestration is migration then verification;
5. one configured timeout is passed unchanged to both stages;
6. migration operational failure preserves its exact cause and prevents D invocation;
7. migration cancellation propagates unchanged;
8. verification operational failure preserves its exact cause;
9. verification cancellation propagates unchanged;
10. non-compatible D results are preserved exactly;
11. SQL startup timeout binds from the existing SQL provider configuration section; and
12. after the startup gate captures the first lazy SQL configuration snapshot, changing the underlying connection-string and timeout configuration cannot cause the later persistence-services resolution to rebind configuration.

The shared-snapshot proof deliberately changes the underlying configuration to values that would fail fresh binding after resolving the gate, then resolves `PersistenceProviderServices` successfully and confirms the gate retains the initial timeout. This makes an independent second bind observable as a test failure without exposing store connection strings as public API.

Real SQL startup serialization, migration/verification execution, and cross-host concurrency remain E.5 concerns.
