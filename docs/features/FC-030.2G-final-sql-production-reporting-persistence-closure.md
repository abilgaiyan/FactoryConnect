## 4. FC-030.2C — projection / checkpoint / evidence SQL persistence

FC-030.2C freezes the SQL publication protocol for operational-metric projection state.

The governing publication order is:

```text
processor serialization
→ checkpoint serialization
→ projection acquisition / preparation
→ manifest acquisition
→ evidence acquisition
→ complete lock boundary established
→ projection / manifest / evidence DML
→ exact published-state revalidation
→ publication body returns successfully
→ checkpoint advances last
→ COMMIT
```

The checkpoint remains the final publication marker.

### Advancing publication

Real-SQL tests prove complete replacement semantics for:

```text
empty → populated
retained-row replacement
manifest growth
manifest shrinkage
nonempty → empty
component evidence → dependency evidence replacement
```

The committed projection, manifest, evidence, and checkpoint state is always the exact proposed published set.

### Equal-revision replay

`ReconcileProposed` remains validation-only.

```text
same revision + exact same publication
→ validation succeeds
→ zero projection/manifest/evidence/checkpoint DML

same revision + divergent publication
→ validation fails
→ durable publication remains unchanged
```

### Failure / rollback

Mutation-stage failure injection proved rollback after every frozen publication phase.

No partial projection, manifest, evidence, or checkpoint state survives a failed publication transaction.

### Writer and reader concurrency

Same-processor writers serialize and divergent successors cannot both publish.

Distinct processors retain independent logical correctness authority; no database-wide publication mutex or shared cross-processor correctness state is introduced.

Reader checkpoint stability remains:

```text
read C1
→ read manifest / projections / evidence
→ read C2
→ accept only when C1 == C2
→ otherwise retry
```

Readers therefore accept only an old complete publication or a new complete publication, never a mixed intermediate publication.

FC-030.2C status: **CLOSED / FROZEN**.

## 5. FC-030.2D — SQL reporting readers

The critical absence/corruption semantics are:

```text

→ absence

known processor + no checkpoint + empty state
→ absence

known processor + no checkpoint + persisted rows
→ corruption
```

Checkpoint stability is per processor.

Multi-processor reads do not invent a global checkpoint.

The SQL readers prove:

```text
period summary reconstruction
detail reconstruction
evidence reconstruction
checkpoint/source-revision coherence
reporting-window filtering
deterministic total ordering
strict startAfter
maximumCount
hidden-corruption rejection

```

The public reader does not add a generic retry layer around provider failures.

Checkpoint-instability retry remains owned by the SQL stable-read implementation.

Caller cancellation propagates and is not converted into a retryable provider failure.

The SQL reader composition is registered only when the corresponding reporting/query capabilities are requested.
