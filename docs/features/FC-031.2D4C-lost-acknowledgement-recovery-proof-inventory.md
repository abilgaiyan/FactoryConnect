## 1. Purpose

FC-031.2D.4C records the recovery contract for a joint state/activity authority publication whose authoritative provider commit succeeds but whose successful acknowledgement is not observed by the caller.

The recovery model contains two distinct mechanisms and they must not be conflated:

```text
provider retained-proposal recovery
    versus
fresh processor/runtime recovery
```

The provider-level retained-proposal proof is independently executable within 4C.

Fresh-invocation recovery semantics are recorded here, but their end-to-end execution proof is deferred because the current processor/runtime path is not yet integrated with the joint FC-031 authority provider.

## 3. Recovery layers are separate mechanisms

### 3.1 Provider retained-proposal recovery

This mechanism starts with a deterministic publication proposal that the caller still retains.

```text
retained proposal
    ↓
initial PublishAsync
    ↓
provider commits P/S/A/E
    ↓
success acknowledgement is lost or suppressed
    ↓
same retained proposal is resubmitted directly to provider
    ↓
Accepted / ExactReplay
```

`ExactReplay` is a provider classification of a submitted complete proposal that structurally and semantically matches the current authoritative publication.

The replay check remains before dual-CAS conflict classification and before revision-exhaustion classification.

A retained exact replay must not:

- allocate a new projection revision;
- append state-change history;
- append activity-period history;
- alter the authoritative projection;
- alter the authoritative evaluation authority.

### 3.2 Fresh processor/runtime recovery

This mechanism does not require the caller to retain or reconstruct the previous complete publication proposal.

A fresh invocation begins from a coherent reread of current authority and determines whether supplied mapped observations contain anything not already incorporated.

```text
fresh invocation
    ↓
coherent current P+E reread
    ↓
compare candidate durable positions to incorporated position
```

The resulting semantics are:

```text
fully overlapping input
    → NoAdvance

partially overlapping input
    → skip incorporated prefix
    → evaluate only forward suffix
```

`NoAdvance` is not an `ExactReplay` classification. It is the fresh-evaluation outcome when no supplied mapped observation advances beyond the currently incorporated position.

Fresh recovery must not be required to reconstruct the previous publication solely to obtain `ExactReplay`.

## 4. Post-commit lost-acknowledgement semantic cut

The 4C contract freezes only the semantic cut required for deterministic proof:

```text
joint provider commit has become authoritative
    ↓
caller has not observed successful acknowledgement
```

Equivalently:

```text
provider committed P/S/A/E
caller observed failure or ambiguity
```

The contract does not freeze a concrete test mechanism.

A natural proof mechanism is an external test wrapper:

```text
test wrapper
    → call inner PublishAsync
    → inner returns NewPublication
    → suppress that result and throw
```

This shape keeps acknowledgement behavior outside provider mutation logic and proves the required semantic cut without introducing a post-commit provider fault point.

A provider-local proof seam remains theoretically possible, but 4C does not require or authorize one merely by recording this contract.

The following remain explicitly non-normative implementation choices:

- external wrapper versus provider-local seam;
- exception type used by a proof harness;
- retry scheduling;
- retry ownership;
- automatic retry policy.

## 5. Provider-level proof boundary

The independently executable 4C provider proof is required to establish:

```text
retained proposal
committed publication
lost acknowledgement
direct resubmission
ExactReplay
stable P/S/A/E and revision
no history duplication
```

For every accepted replay:

```text
P unchanged
S history unchanged
A history unchanged
E unchanged
revision unchanged
```

Expected projection position and expected authority revision remain excluded from complete replay identity. A stale expected token therefore does not defeat an otherwise exact replay.

Changed payload with the same expected tokens is not replay.

## 6. Minimum provider proof matrix

The 4C provider proof matrix is:

### C-01 — Fresh publication acknowledgement lost

```text
fresh NewPublication succeeds internally
acknowledgement is lost
same retained proposal is resubmitted
    → Accepted / ExactReplay
```

Required proof:

- authoritative P unchanged on replay;
- authoritative E unchanged on replay;
- revision remains the fresh publication revision;
- S history is not duplicated;
- A history is not duplicated.

### C-02 — Forward publication acknowledgement lost

```text
established lineage
changed forward NewPublication succeeds internally
acknowledgement is lost
same retained proposal is resubmitted
    → Accepted / ExactReplay
```

Required proof:

- P/S/A/E remain exactly the committed forward publication;
- replay does not allocate the next revision;
- histories are not appended again.

### C-03 — Repeated retained-proposal replay

After C-01 or C-02 has converged through one `ExactReplay`, repeated direct resubmission of the same retained proposal must remain:

```text
Accepted / ExactReplay
```

with stable:

- projection;
- evaluation authority;
- projection revision;
- state-change history;
- activity-period history.

### C-04 — Exact replay at revision `ulong.MaxValue`

If the current committed publication already carries projection revision `ulong.MaxValue`, resubmission of its exact retained proposal must still classify as:

```text
Accepted / ExactReplay
```

because exact replay precedes revision-exhaustion classification.

No revision allocation occurs.

### C-05 — Same expected tokens, changed payload

A proposal that reuses the same expected projection position and expected authority revision but changes any member of the complete replay payload is not an exact replay.

Where that proposal does not form a valid changed-forward publication, it must classify as conflict according to the inherited 4A algebra.

The proof must demonstrate that matching expected tokens do not weaken complete-payload replay identity.

### C-06 — Lineage isolation during lost-ack recovery

Lost-acknowledgement recovery for one `(StateProcessorId, ObservationStreamId)` lineage must not alter any other lineage.

The proof must establish isolation across at least the provider-owned lineage key boundary while replaying the retained proposal.

## 7. Fresh-invocation authority semantics

The joint authority API already defines a coherent P+E snapshot in which:

```text
Projection.ProcessorId == EvaluationAuthority.StateProcessorId
Projection.StreamId == EvaluationAuthority.ObservationStreamId
Projection.Position == EvaluationAuthority.EvaluatedThrough
Projection.State == EvaluationAuthority.MachineState
```

The incorporated durable position for fresh recovery is therefore represented coherently by:

```text
Projection.Position
    ==
EvaluationAuthority.EvaluatedThrough
```

### 7.1 Fully overlapping input

If every supplied mapped observation satisfies:

```text
candidate.Position <= incorporated position
```

then fresh recovery semantics are:

```text
NoAdvance
```

and no new authority publication, output history, or revision churn is permitted merely because the invocation is fresh.

### 7.2 Partially overlapping input

If the supplied mapped observations contain an already-incorporated prefix followed by new positions:

```text
covered prefix
    → skip

forward suffix
    → evaluate normally
```

Only the forward suffix contributes new evaluation work and any resulting changed-forward joint publication.

Batch partitioning must not change which durable positions are considered incorporated versus forward.

Therefore the repository currently contains the required primitives separately:



Provider-level retained-proposal proof is therefore necessary but is not sufficient evidence for the fresh-invocation recovery layer.
