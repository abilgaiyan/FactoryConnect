# FC-030.1D — Runtime Schema Compatibility Verification

## Status

Architecture contract active. D.1 and D.2 remain open until the compatibility taxonomy and history-classifier corrections pass their local verification gates. D.3 must not start before that closure.

## Runtime compatibility invariant

A runtime compatibility decision is computed from migration history and live FactoryConnect-owned schema observed while holding a shared transaction-owned `FactoryConnect.SqlMigration` application lock. Runtime verification never adopts, migrates, repairs, or otherwise mutates persistent SQL Server state.

## D.1 compatibility taxonomy

The runtime compatibility vocabulary includes:

- `Compatible`
- `DatabaseUninitialized`
- `LegacyAdoptionRequired`
- `UnledgeredSchemaIncompatible`
- `MigrationPending`
- `DatabaseNewerThanSupported`
- `MigrationIdentityMismatch`
- `MigrationChecksumMismatch`
- `MigrationHistoryInvalid`
- `MigrationLedgerSchemaInvalid`
- `MigrationSchemaDrift`

`MigrationHistoryInvalid` is reserved for malformed ledger row semantics such as a non-canonical checksum representation or non-zero `AppliedAtUtc` offset. A syntactically canonical checksum that differs from repository authority is `MigrationChecksumMismatch` instead.

The frozen terminal mapping is:

```text
ExactPrefixPending         -> MigrationPending
DatabaseNewerThanSupported -> DatabaseNewerThanSupported
IdentityMismatch           -> MigrationIdentityMismatch
ChecksumMismatch           -> MigrationChecksumMismatch
RowSemanticsInvalid        -> MigrationHistoryInvalid
```

The history-to-runtime mapping API is nullable:

```text
MapTerminal(ExactCurrent)  -> null
MapTerminal(terminal state)-> non-null final compatibility classification
```

`ExactCurrent` is deliberately non-terminal. It proves only that ledger history exactly matches the repository catalog. It must continue to `CurrentSchemaComparison` before a final runtime compatibility classification can be produced:

```text
ExactCurrent
    -> compare live FactoryConnect-owned schema to CurrentSchemaDescriptor
        -> exact   -> Compatible
        -> unequal -> MigrationSchemaDrift
```

No history-only mapping API may return or expose `Compatible` for `ExactCurrent`, including through an auxiliary or default output value.

## D.2 future-history identity invariants

A history suffix beyond the supported repository catalog may be classified as `DatabaseNewerThanSupported` only when:

1. the complete supported prefix matches repository migration ids, names, and checksums exactly;
2. every row has canonical checksum syntax and UTC offset zero;
3. future migration ids are strictly increasing;
4. future migration names are unique across both supported and future rows;
5. future migration names use the frozen ASCII letter/digit/hyphen/underscore migration-name grammar; and
6. future migration names are non-empty.

Any violation of identity rules is `IdentityMismatch`. Row-semantic invalidity has precedence over the history/catalog relationship.

## D.3 raw-history reader decision

D.3 will use a read-only raw migration-history projection for runtime verification.

The existing `SqlServerMigrationHistoryStore.ReadAsync` remains the validating deployment/migration reader used by FC-030.1C. Runtime compatibility verification will not reuse that eager-validation boundary because doing so would convert malformed row semantics into exceptions before the D classifier can produce a deterministic compatibility result.

The D.3 flow is therefore frozen as:

```text
open runtime connection
-> begin Serializable verification transaction
-> acquire Shared transaction-owned FactoryConnect.SqlMigration applock
-> resolve exact ledger identity and physical shape
-> read raw ledger rows without semantic validation
-> classify row semantics and history/catalog relationship through D.2
-> MapTerminal(history classification)
   -> non-null: return that terminal runtime classification
   -> null: history is ExactCurrent; continue to Current schema comparison
-> compare live schema to CurrentSchemaDescriptor
-> exact schema -> Compatible
-> unequal schema -> MigrationSchemaDrift
-> rollback/dispose verification transaction
```

The verification transaction uses `IsolationLevel.Serializable`.

The Shared application lock must reuse the C locking contract rather than define a second policy:

- resource: `FactoryConnect.SqlMigration`;
- owner: `Transaction`;
- database principal: `public`;
- mode: `Shared`;
- timeout conversion: the existing `SqlMigrationLockTimeout.ToMilliseconds` contract;
- timeout must be finite and non-negative;
- positive fractional milliseconds are rounded upward;
- values beyond the SQL Server `Int32` millisecond limit are rejected;
- zero means zero-wait;
- lock command timeout remains `0` so `sp_getapplock` owns bounded waiting;
- scalar return values are parsed with the same strict SQL-int requirement as C;
- any negative `sp_getapplock` return code is an operational `SqlMigrationLockAcquisitionException`, not a compatibility result;
- cleanup is best-effort and must not replace the primary operational failure.

The raw projection may deserialize SQL values into `SqlMigrationHistoryRow`, but it must not reject checksum casing/content or `AppliedAtUtc` offset before classification. Provider/read failures remain operational exceptions, not compatibility classifications.

## Hard boundary

D.3 must not:

- create or alter the migration ledger;
- execute migrations;
- adopt legacy history;
- repair schema or history;
- introduce migration 005;
- introduce reporting persistence schema; or
- wire runtime host startup policy before the verifier contract is complete.
