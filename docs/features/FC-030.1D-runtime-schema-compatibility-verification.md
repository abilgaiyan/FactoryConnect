# FC-030.1D — Runtime Schema Compatibility Verification

## Status

D.1, D.2, and D.3 are closed and frozen. D.4 is active. D.5 has not started.

## Runtime compatibility invariant

A runtime compatibility decision is computed from migration history and live FactoryConnect-owned schema observed while holding a shared transaction-owned `FactoryConnect.SqlMigration` application lock. Runtime verification never adopts, migrates, repairs, or otherwise mutates persistent SQL Server state.

## D.1 compatibility taxonomy

The runtime compatibility vocabulary includes:

- `Compatible`
- `DatabaseUninitialized`
- `LegacyAdoptionRequired`
- `UnledgeredSchemaIncompatible`
- `MigrationPending`
- `DatabaseNewerThanSupported`
- `MigrationIdentityMismatch`
- `MigrationChecksumMismatch`
- `MigrationHistoryInvalid`
- `MigrationLedgerSchemaInvalid`
- `MigrationSchemaDrift`

`MigrationHistoryInvalid` is reserved for malformed ledger row semantics such as a non-canonical checksum representation or non-zero `AppliedAtUtc` offset. A syntactically canonical checksum that differs from repository authority is `MigrationChecksumMismatch` instead.

The frozen terminal mapping is:

```text
ExactPrefixPending         -> MigrationPending
DatabaseNewerThanSupported -> DatabaseNewerThanSupported
IdentityMismatch           -> MigrationIdentityMismatch
ChecksumMismatch           -> MigrationChecksumMismatch
RowSemanticsInvalid        -> MigrationHistoryInvalid
```

The history-to-runtime mapping API is nullable:

```text
MapTerminal(ExactCurrent)  -> null
MapTerminal(terminal state)-> non-null final compatibility classification
```

`ExactCurrent` is deliberately non-terminal. It proves only that ledger history exactly matches the repository catalog. It must continue to `CurrentSchemaComparison` before a final runtime compatibility classification can be produced:

```text
ExactCurrent
    -> compare live FactoryConnect-owned schema to CurrentSchemaDescriptor
        -> exact   -> Compatible
        -> unequal -> MigrationSchemaDrift
```

No history-only mapping API may return or expose `Compatible` for `ExactCurrent`, including through an auxiliary or default output value.

## D.2 future-history identity invariants

A history suffix beyond the supported repository catalog may be classified as `DatabaseNewerThanSupported` only when:

1. the complete supported prefix matches repository migration ids, names, and checksums exactly;
2. every row has canonical checksum syntax and UTC offset zero;
3. future migration ids are strictly increasing;
4. future migration names are unique across both supported and future rows;
5. future migration names use the frozen ASCII letter/digit/hyphen/underscore migration-name grammar; and
6. future migration names are non-empty.

Any violation of identity rules is `IdentityMismatch`. Row-semantic invalidity has precedence over the history/catalog relationship.

## D.3 raw-history reader and serialized verification

Runtime verification uses a read-only raw migration-history projection. The existing `SqlServerMigrationHistoryStore.ReadAsync` remains the validating deployment/migration reader used by FC-030.1C.

The frozen D.3 flow is:

```text
open runtime connection
-> begin Serializable verification transaction
-> acquire Shared transaction-owned FactoryConnect.SqlMigration applock
-> resolve exact ledger identity and physical shape
-> read raw ledger rows without semantic validation
-> classify row semantics and history/catalog relationship through D.2
-> MapTerminal(history classification)
   -> non-null: return that terminal runtime classification
   -> null: history is ExactCurrent; continue to Current schema comparison
-> compare live schema to CurrentSchemaDescriptor
-> exact schema -> Compatible
-> unequal schema -> MigrationSchemaDrift
-> rollback/dispose verification transaction
```

The verification transaction uses `IsolationLevel.Serializable`.

The Shared application lock reuses the C locking contract:

- resource: `FactoryConnect.SqlMigration`;
- owner: `Transaction`;
- database principal: `public`;
- mode: `Shared`;
- timeout conversion: `SqlMigrationLockTimeout.ToMilliseconds`;
- timeout finite and non-negative;
- positive fractional milliseconds rounded upward;
- values beyond the SQL Server `Int32` millisecond limit rejected;
- zero means zero-wait;
- lock command timeout remains `0` so `sp_getapplock` owns bounded waiting;
- scalar return values use C's strict SQL-int requirement;
- any negative `sp_getapplock` return code is an operational `SqlMigrationLockAcquisitionException`, not a compatibility result; and
- cleanup is best-effort and must not replace the primary operational failure.

The raw projection may deserialize SQL values into `SqlMigrationHistoryRow`, but it must not reject checksum casing/content or `AppliedAtUtc` offset before classification. Provider/read failures remain operational exceptions, not compatibility classifications.

## D.4 runtime diagnostics and deterministic differences

D.4 enriches the already-frozen D.3 result with immutable diagnostic evidence. Diagnostics explain a classification; they never compute, replace, promote, or downgrade it.

The result contract is frozen as:

```text
SqlRuntimeCompatibilityResult
    Classification
    Diagnostics[]
```

Each diagnostic carries a stable diagnostic code, the frozen decision stage that produced the evidence, a deterministic artifact identity, optional expected/actual values, and a stable detail message. Diagnostic values are derived only from repository authority and the database state already read under the D.3 Shared lock.

The following invariants apply:

1. `Compatible` has an empty diagnostic collection.
2. Every non-compatible result has at least one diagnostic.
3. Operational connection, provider, read, cancellation, and applock failures remain exceptions and never become diagnostics.
4. Diagnostic ordering is deterministic and independent of SQL metadata row order or input collection order.
5. Repeated verification of the same database state returns value-equal diagnostics in the same order.
6. Diagnostics never include timestamps generated by verification, session ids, provider exception text, or other volatile values.
7. History diagnostics describe the already-selected D.2 classification; they do not perform an alternate compatibility decision.
8. When more than one row-semantic defect exists, the first ledger row in canonical `MigrationId` read order is reported; within that row, checksum syntax precedes UTC-offset evidence.
9. `MigrationPending` identifies the first repository migration not present in the exact applied prefix.
10. `DatabaseNewerThanSupported` identifies the first unsupported valid history row.
11. `MigrationIdentityMismatch`, `MigrationChecksumMismatch`, and `MigrationHistoryInvalid` identify the first evidence that establishes the frozen classification precedence.
12. `MigrationLedgerSchemaInvalid` exposes deterministic ledger-contract evidence. Incompatible object kind and exact physical-ledger validation remain distinct diagnostic codes while sharing the final classification.
13. `UnledgeredSchemaIncompatible` uses the frozen `LegacyPost004SchemaDescriptor` comparator differences as evidence.
14. `MigrationSchemaDrift` projects every `SqlSchemaComparator` difference against `CurrentSchemaDescriptor`, preserving the comparator's existing stable order.
15. Schema-difference diagnostics preserve `SqlSchemaDifferenceKind`, table identity, artifact name, and detail; D.4 does not create a second structural comparator.
16. `DatabaseUninitialized` and `LegacyAdoptionRequired` expose stable state diagnostics but perform no mutation.

The diagnostic code vocabulary is diagnostic-only and must not add or reinterpret final compatibility classifications. A code may refine why a final classification was reached, for example distinguishing invalid checksum syntax from a non-zero `AppliedAtUtc` offset while the final classification remains `MigrationHistoryInvalid`.

## Hard boundary

D.4 must not:

- change D.1 final compatibility classifications;
- change D.2 history classification semantics or precedence;
- change D.3 locking, transaction isolation, or non-mutation behavior;
- create or alter the migration ledger;
- execute migrations;
- adopt legacy history;
- repair schema or history;
- introduce migration 005;
- introduce reporting persistence schema; or
- wire runtime host startup policy before the verifier contract is complete.
