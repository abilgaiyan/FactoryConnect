# 1. Frozen concurrency authority

The original FC-030.2C.1 persistence contract freezes the following concurrency semantics:

```text
Commits for the same processor are serialized around processor/checkpoint CAS authority.
Distinct processors remain logically independent.
```

It further requires:

> Distinct processors MUST remain logically independent; correctness MUST NOT require a database-wide projection publication lock.

The replacement closure preserves this authority while freezing SQL Server `Serializable` isolation and the lock-acquisition order:

```text
ProjectionProcessor key slot
    ↓
ProjectionCheckpoint key slot
    ↓
OperationalMetricProjection identity rows
    ↓
OperationalMetricProjectionManifest rows
    ↓
OperationalMetricProjectionEvidence rows
```

Projection identities are owned by the frozen unique authority:

```text
UQ_OperationalMetricProjection_LogicalHash
(
    OperationalMetricProjectionProcessorRowId,
    EvaluationKeyHash
)
```

and are resolved under the existing `Serializable` publication transaction with `UPDLOCK, HOLDLOCK` semantics.

No architecture amendment was authorized during this investigation.

---

# 2. Investigated projection-prefix acquisition

The investigated complete-current-set acquisition uses the frozen logical-hash index and the processor prefix:

```sql
SELECT ...
FROM dbo.OperationalMetricProjection WITH
(
    UPDLOCK,
    HOLDLOCK,
    INDEX(UQ_OperationalMetricProjection_LogicalHash)
)
WHERE OperationalMetricProjectionProcessorRowId = @ProcessorRowId
ORDER BY EvaluationKeyHash;
```

The production C.3 preparation path performs the same processor-prefix acquisition before any projection DML.

The purpose of the scan is to obtain all current projection identities for one processor while preventing phantoms for missing evaluation-key hashes under `Serializable` isolation.

No `READUNCOMMITTED`, application lock, database-wide lock, schema change, snapshot-option dependency, or isolation downgrade was introduced.

---

# 3. Execution-plan evidence

Real-SQL diagnostics confirmed that SQL Server uses the frozen unique logical-hash index for the processor-prefix query.

Observed plan requirements passed:

```text
Index Seek
index = UQ_OperationalMetricProjection_LogicalHash
seek predicate includes OperationalMetricProjectionProcessorRowId
```

Therefore the investigated failure is not explained by an accidental table scan or by ignoring the frozen index authority.

---

# 4. Lock-footprint evidence

`sys.dm_tran_locks` was captured while the acquisition transaction remained open.

For a populated processor prefix, SQL Server granted key-range locks on:

```text
UQ_OperationalMetricProjection_LogicalHash
```

with request mode:

```text
KEY | RangeS-U | GRANT
```

The diagnostic also observed only intent-level broader locks for the projection object/index path:

```text
OBJECT | IX | GRANT
PAGE   | IU | GRANT
```

No granted page/object `S`, `U`, `X`, or `SIX` lock was observed in the fixture.

This rules out lock escalation as the explanation for the distinct-processor failure in the investigated query shape.

An empty processor prefix also acquired granted key-range phantom protection, proving that SQL Server protects the missing prefix/range rather than treating the empty result as unlocked.

---

# 5. Same-processor protection evidence

The production-path and diagnostic real-SQL tests established all of the following:

```text
existing evaluation-key identity
    → excluded from a concurrent same-processor acquisition until rollback

missing identity in an empty processor prefix
    → excluded until rollback

missing evaluation-key hash inside a nonempty processor prefix
    → excluded until rollback

same-processor writer serialization
    → preserved by processor/checkpoint + projection range locking
```

These results demonstrate that the investigated prefix acquisition provides the required same-processor identity and phantom protection.

The same tests also confirmed that the held locks are released after both rollback and commit.

---

# 6. Distinct-processor failure

The production-path concurrency proof attempted to hold complete projection preparation for one processor while independently completing production preparation for another processor.

That test failed: the second processor could not complete preparation while the first processor's projection-prefix acquisition remained held.

The dedicated DMV diagnostic reproduced the same behavior with adjacent nonempty processor prefixes.

Observed owner transaction for processor A:

```text
LOCK_SNAPSHOT=processor-A
DATABASE | S        | GRANT
KEY      | RangeS-U | GRANT | UQ_OperationalMetricProjection_LogicalHash
KEY      | RangeS-U | GRANT | UQ_OperationalMetricProjection_LogicalHash
KEY      | RangeS-U | GRANT | UQ_OperationalMetricProjection_LogicalHash
OBJECT   | IX       | GRANT
PAGE     | IU       | GRANT | UQ_OperationalMetricProjection_LogicalHash
```

Observed contender transaction for processor B before failure:

```text
LOCK_SNAPSHOT=processor-B
DATABASE | S  | GRANT
OBJECT   | IX | GRANT
PAGE     | IU | GRANT | UQ_OperationalMetricProjection_LogicalHash
```

The contender then reported:

```text
DISTINCT_PROCESSOR_RESULT=BLOCKED_1222
```

SQL Server error 1222 is the lock-request timeout used deliberately by the diagnostic contender.

The contender successfully obtained database/object/page intent locks but did not receive the required key-range lock while processor A retained its granted `RangeS-U` key-range locks.

Classification:

```text
cause class
    = key-range contention on the frozen logical-hash index

not caused by
    = page/object lock escalation
    = accidental table scan
    = missing frozen-index hint
```

The evidence proves that this complete processor-prefix `Serializable` acquisition primitive is not processor-local in the required concurrency sense.

---

# 7. Empty-table and populated-index behavior

The investigation covered both:

```text
processor prefix with zero projection rows
processor prefix with multiple projection hashes
```

For populated prefixes, the fixture included multiple hashes so the acquisition covered existing rows and internal missing-hash ranges.

For empty prefixes, the acquisition still produced phantom-protecting key-range behavior.

The distinct-processor diagnostic used adjacent populated processor prefixes in the same frozen composite index and reproduced the lock timeout.

No unrealistic fixture size was required to produce the failure, and no lock escalation was observed.

# 8. Architectural classification

The investigated primitive satisfies:

```text
complete current projection-set discovery          PROVEN
Serializable projection identity protection        PROVEN
existing identity exclusion                        PROVEN
missing internal hash exclusion                    PROVEN
empty-prefix phantom protection                    PROVEN
frozen-index seek                                  PROVEN
same-processor serialization                       PROVEN
commit/rollback lock release                       PROVEN
no lock escalation in investigated fixtures        PROVEN
```

It fails:

```text
distinct-processor independent acquisition         FAILED
```

This failure conflicts with the frozen C.1 concurrency semantics that distinct processors remain logically independent.

The narrower technical conclusion is authoritative:

> A complete `Serializable` processor-prefix acquisition over `UQ_OperationalMetricProjection_LogicalHash` using the investigated `UPDLOCK, HOLDLOCK` prefix scan cannot provide processor-local concurrency in the observed real-SQL execution.

This document does **not** claim that migration 005 is incapable of supporting every conceivable compliant locking protocol. It records only that no reliable compliant implementation has yet been established and that the currently investigated complete-prefix primitive is disqualified by real-SQL evidence.
