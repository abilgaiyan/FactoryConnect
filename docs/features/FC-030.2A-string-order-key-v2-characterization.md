# 1. Candidate encoding

`StringOrderKeyV2` is derived from the exact validated .NET UTF-16 code-unit sequence.

For every UTF-16 code unit `u`, emit:

```text
0x01
UInt16BE(u)
```

After the final code unit emit:

```text
0x00
```

No normalization, trimming, case folding, escaping, BOM removal, NUL removal, or scalar rewriting occurs.

Maximum frozen `CanonicalStringV1` length is 256 UTF-16 code units, therefore:

```text
maximum StringOrderKeyV2 bytes
= 256 * 3 + 1
= 769
```

Candidate SQL representation:

```sql
varbinary(769)
```

The terminator is intentionally lexicographically below the per-code-unit marker. This preserves prefix ordering while preventing SQL trailing-zero binary comparison behavior from collapsing terminal U+0000 code units into end-of-string.

# 6. Physical-design consequence

Any SQL operation that has provider-neutral string equality/order semantics before reader reconstruction must use `StringOrderKeyV2`, not raw `nvarchar` comparison authority.

The human/domain string column remains persisted for reconstruction and diagnostics. The order/equality key is a duplicated physical projection and therefore requires:

```text
writer construction invariant + reader revalidation
```

The writer derives both from the same exact .NET string. The reader reconstructs/re-encodes and requires exact key equality before using the row. A mismatched string/key pair is persisted-data corruption.

Candidate SQL comparison columns must be `varbinary(769)` and must never be generated by trimming/normalizing the text value.

`nvarchar` collation remains storage metadata only where a companion order key owns semantic comparison.
