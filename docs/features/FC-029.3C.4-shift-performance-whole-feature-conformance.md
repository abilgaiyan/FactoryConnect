## Required semantic distinctions

Closure retains all of these as different states:

1. zero configured sources → valid empty configured factory and no reporting request;
2. configured machine + covered production day + zero occurrences → configured machine with zero shifts;
3. authoritative occurrence + `SourceRevision = null` + `Metrics = []` → occurrence survives with five explicit missing slots;
4. non-null report lineage + absent requested evaluation → occurrence and exact revision survive at the model boundary while that evaluation is explicitly missing;
5. absent roster coverage → typed roster-coverage-required failure;
6. malformed authoritative reporting result → controlled presentation-contract failure.

None may be collapsed into another state.

## Dependency boundary

The production dependency direction remains:

```text
route-owned production day + configured runtime sources
                    ↓
production-day shift reporting lifecycle
                    ↓
complete authoritative reporting result
                    ↓
Shift Performance authority validation / mapper
                    ↓
classified page state
                    ↓
model-only rendering
```

Dependency/import allowlists are executable architecture evidence. Source-text searches for words such as `Date`, arithmetic operators, metric names, or test-name prose are not accepted as architectural proof.

The presentation layer must not import generated reporting contracts, the reporting client, runtime configuration, continuation-token handling, or query lifecycle implementation. Composition must not introduce a second reporting state machine or reporting-result cache.

## Persistence-provider coverage

The machine-shift roster capability is provider-neutral, but SQL Server roster persistence is deliberately not implemented in this feature branch. `SqlServerPersistenceServiceCollectionExtensions` registers `PersistenceProviderCapabilities.Core` and does not advertise `MachineShiftOccurrenceRoster`.

Therefore FC-029.3C.4 does **not** claim SQL-backed roster persistence conformance. The transitional rule remains explicit: roster startup materialization is enabled only when the selected persistence provider advertises the roster capability; providers without it retain the pre-roster production-processing lifecycle and do not advertise roster coverage.

This is a documented deferred provider capability, not a silent test omission.
