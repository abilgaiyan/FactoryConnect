# FC-030.2C.3 / FC-030.2C.4 — Joint Publication Conformance Closure

Status: **CLOSED / FROZEN — JOINT REAL-SQL PUBLICATION AUTHORITY**

This document closes FC-030.2C.3 and FC-030.2C.4 together.

It does not reopen or modify FC-030.2A, FC-030.2B, Migration 005, Migration 006, the frozen C.1 concurrency amendment, or the frozen C.2 checkpoint choreography.

## Closure boundary

The jointly closed implementation preserves the frozen execution order:

```text
processor serialization
→ checkpoint serialization
→ projection acquisition / preparation
→ manifest acquisition
→ evidence acquisition
→ complete lock boundary established
→ projection / manifest / evidence DML
→ exact published-state revalidation
→ C.4 body returns successfully
→ C.2 advances checkpoint last
→ COMMIT
```

No projection, manifest, evidence, or checkpoint DML is authorized before the full projection → manifest → evidence acquisition boundary is complete.

FC-030.2C.3 remains a lock / prepare / validate layer and performs no publication DML.

FC-030.2C.4 owns publication mutation and exact-state validation after the complete lock boundary.

C.2 remains the sole checkpoint advancement authority and advances only after the publication body succeeds.

## Advancing publication proof

Real-SQL tests prove the advancing replacement contract for:

- empty → populated publication,
- retained-row replacement,
- manifest growth,
- manifest shrinkage,
- nonempty → empty publication,
- component-evidence replacement by dependency evidence.

The durable publication is always the exact proposed set of projection rows, manifest memberships, and complete evidence snapshots for the committed checkpoint revision.

## Equal-revision reconciliation

`ReconcileProposed` is frozen as validation-only behavior.

When `proposed == durable`:

- the complete C.3 / C.4 acquisition path may run,
- durable projection / manifest / evidence state is validated against the proposed commit,
- projection DML is forbidden,
- manifest DML is forbidden,
- evidence DML is forbidden,
- checkpoint DML is forbidden.

A matching replay succeeds without changing durable state.

A divergent same-revision proposal fails validation with `InvalidOperationException` and leaves the already-published state unchanged.

## Exact revalidation before checkpoint advancement

The `ExactStateRevalidated` injection point is observed inside the writer transaction.

At that point the durable checkpoint is still the previous checkpoint position.

Therefore the proven ordering is:

```text
publication mutation
→ exact projection / manifest / evidence revalidation
→ publication body returns
→ checkpoint advancement
→ commit
```

The checkpoint is not advanced before exact-state revalidation completes successfully.

## Same-processor writer serialization

Real-SQL conformance proves that two same-processor writers cannot publish concurrently.

For divergent successors based on the same prior checkpoint:

```text
writer 1 enters advancing publication
→ writer 2 cannot enter the transaction body while writer 1 owns the processor/checkpoint serialization boundary
→ writer 1 commits revision N+1
→ writer 2 wakes
→ writer 2 classifies proposed == durable
→ writer 2 enters ReconcileProposed
→ divergent exact-state validation fails
→ writer 2 performs no publication/checkpoint DML
→ writer 1 publication remains authoritative
```

Thus divergent same-processor successors cannot both publish.

## Distinct-processor concurrency

The frozen C.1 concurrency amendment remains authoritative:

> Distinct processors have independent logical state and correctness authority. Implementations must not use a database-wide publication mutex or shared cross-processor correctness state. Incidental, bounded SQL Server key-range blocking between adjacent processor prefixes is permitted. It must not cause partial publication, state corruption, or checkpoint interference.

The existing C.3 physical lock proof demonstrates allowed bounded cross-prefix key-range waiting and completion after owner rollback.

The joint publication proof also demonstrates distinct processors converging to independent durable publication and checkpoint state.

No application lock, global publication mutex, sentinel row, new range-locality index, isolation downgrade, or shared cross-processor correctness state is introduced.

## Reader atomicity

The frozen ReadCommitted checkpoint-stability algorithm is proven:

```text
read C1
→ read manifest / projections / evidence
→ read C2
→ accept only when C1 == C2
→ otherwise retry
```

A reader started while a writer has mutated publication state inside an uncommitted transaction first observes the old checkpoint.

After writer commit, a mixed attempt is rejected when the checkpoint changes, and the retry converges to the complete new publication.

The accepted reader result is therefore only:

- the old complete publication, or
- the new complete publication.

An intermediate / mixed publication is not accepted.

## Retry and replay convergence

Real-SQL proof covers:

```text
advancing publication

→ retry of the same advance

→ equal-revision replay
→ ReconcileProposed validation only
→ durable state unchanged
```

This preserves the worker retry / replay semantic boundary expected by the provider-neutral projection contract.
