Status: draft procedure only; not authorized for execution.

Authority: [IMP-1C specification](P1.6-IMP-1C-GG003-historical-inventory-specification.md).
No SQL connection, query, backup/restore, credential change, test, replay or production operation was performed to prepare this document.

## Review and execution scope

The operator will perform a bounded read-only inventory against one pre-existing, identified disposable restore using direct SELECT queries and offline payload validation. Creating/restoring the target and provisioning credentials are prerequisites outside this procedure.
Procedure acceptance/merge is not execution authorization. A later authorization must identify target, backup, selected periods/cuts, permitted reads/artifacts, output location and operator.
Do not connect to Gajra production. Do not start Edge/API/Dashboard, test harnesses with database-create/drop behavior, migration runners, boot/reconciliation scripts, workers or provider Publish/Commit APIs.
ApplicationIntent=ReadOnly and a readonly transaction label are not permission enforcement.

## Stage P0 — Permission and target preflight only

The first approved connection performs metadata SELECTs only. Capture server/database identity, login/user, database state/read-only flag, roles and effective permissions.
Example metadata reads for the separately reviewed query packet (shown for review, not executed here):

```sql
SELECT @@SERVERNAME AS SqlServer, DB_NAME() AS DatabaseName,
       ORIGINAL_LOGIN() AS OriginalLogin, SUSER_SNAME() AS LoginName,
       USER_NAME() AS DatabaseUser, SYSDATETIMEOFFSET() AS CapturedAt;
SELECT name, state_desc, is_read_only, source_database_id
FROM sys.databases WHERE database_id = DB_ID();
SELECT IS_SRVROLEMEMBER('sysadmin') AS IsSysadmin,
       IS_ROLEMEMBER('db_owner') AS IsDbOwner;
SELECT permission_name
FROM sys.fn_my_permissions(NULL, 'SERVER') ORDER BY permission_name;
SELECT permission_name
FROM sys.fn_my_permissions(NULL, 'DATABASE') ORDER BY permission_name;
```

Preflight acceptance requires target equality with the approved record, ONLINE and is_read_only=1, non-owner/non-sysadmin identity, and a reviewed effective permission inventory showing only required connect/read/metadata rights for the target.
Check object-level effective permissions on every allowlisted table/view using the permission function with OBJECT scope. Review nested roles, grants/denies and any impersonation/module execution route with the target administrator's attested grant inventory; database-level permission rows alone are not sufficient.
Reject write/DDL/control/ownership/impersonation capabilities and executable modules that could mutate databases or invoke privileged code. Server/database metadata visibility limitations or NULL role results leave proof incomplete and stop preflight.
Never probe permission enforcement using INSERT/UPDATE/DDL followed by ROLLBACK. No change of database state, grants, credentials or isolation options is permitted.
The READ_ONLY target supplies independent persistent-data protection; restricted credentials and SELECT-only query review protect the access path. Do not claim that this prevents all SQL engine bookkeeping/tempdb activity or all possible server-side effects.
No inventory source-data reads follow until permission/identity evidence is reviewed and accepted.

## Stage P1 — Schema discovery and query packet review

Read migration history and sys catalog metadata for required tables/columns, then freeze the exact schema-aware SELECT packet. Missing optional structures become evidence limitations; no migration to add them.
Allowlist only the required observation/acquisition, joint activity, production-context output, metric fact/aggregation and coverage tables plus required catalog views. Discover physical names from the restored schema; do not guess missing receipt tables.
Packet binds database identity, machine GUID `677b030b-1ede-4a67-82ae-6a494791357f`, processor/stream and cut parameters; it contains no SELECT INTO, DML/DDL, EXEC, stored procedure or mutating initialization.
Review exact joins/keys against the accepted repository/deployed schema. Separate SQL extraction from offline codec/identity verification; do not invoke a service startup merely to deserialize evidence.
Record packet hash and versions of offline decoders. Changes to joins/scope require review before running the changed packet.

## Stage P2 — Establish coherent view and exact cuts

The target must remain the same pre-existing immutable READ_ONLY disposable copy throughout capture. Record identity/backup/state before and after each stage; any change aborts the run.
This avoids long Serializable key-range locks for bulk inventory. If immutability cannot be independently established, stop; a different coherent transaction strategy needs separate approval.
Enumerate processor/stream/revision and stored period identities for the selected dates. Identify revision 534 only if committed under the exact requested source.
Freeze the actual committed cut list and relevant membership keys before payload extraction. A missing cut is reported, never replaced by latest.
No observations-versus-metric positions comparison; retain typed domain information.

## Stage P3 — Bounded extraction and offline verification

Execute the reviewed packet by exact machine/cut, paging on stable unique keys against the immutable copy. Record expected/returned counts and page ranges; reconcile all relevant rows. Samples alone do not prove complete membership.
Capture:
1. Exact aggregation contribution/fact joins and period identities.
2. Referenced contextualized/eligibility payloads with identity/hash/source relationships.
3. Candidate producer publication/admission bindings and dependency subsets; if not retained, leave NotEstablished.
4. Joint activity history processor/revision/ordinal and source observation identity.
5. Acquisition publication prefix/opening boundary, accepted ranges and required raw dependencies.
6. Exact coverage subject/revision payload and complete referenced dependency inventory.
7. Available historical schedule/override/exclusion artifacts, separately from SQL facts.

Use original stored bytes and the exact versioned encoding to validate hashes/identities offline. Do not normalize JSON, strings or decimal values before preserving originals. Sanitized derivatives have their own identity and cannot substitute for exact original verification.
If a dependency chain exceeds approved limits, stop that category as NotEstablished and request a bounded scope extension. Never truncate then mark complete.
Unknown state, missing running fact, advanced checkpoint, current config and Complete coverage labels do not establish authority.
No aggregation/evaluator runtime, result publication or historical replay is invoked.

## Stage P4 — External artifacts and evidence classification

Inspect only explicitly authorized artifacts. Record immutable identity/content hash, custody, effective scope and independently established link to historical derivation.
No artifact becomes historical schedule authority merely because it has POT-1, matching timestamps or a convenient filesystem date.
Separate factory approval from retained software configuration and resolved schedule windows.
For each dependency/cut use AvailableAndVerifiable, AbsentAtHistoricalCut, RetainedReferencePayloadMissing, Conflicting or NotEstablished under IMP-1C rules.
Retain missing payload/identity conflict details without fixing rows. A current empty query cannot prove historical absence.

## Stage P5 — Closeout and review

Deliver:
- Authorization/preflight evidence and immutable-target provenance.
- Exact schema/query packet hashes, cut list, counts/page reconciliation and offline validation results.
- Per-cut dependency register, unresolved spans, external artifact provenance and integrity limitations.
- Proposed historical feasibility decision with explicit supported/unsupported scopes.
- Final target identity/read-only-state capture and attestation that no mutating application path or statement ran.

READ_ONLY state plus reviewed permissions/query transcript supplies evidence of the non-mutation boundary; do not claim matching row counts alone proves no mutation.
No V2 Availability is calculated/admitted by this inventory. A diagnostic reconstruction is labeled as such and cannot satisfy reporting acceptance.
IMP-1 closure requires reviewer acceptance of actual authority/feasibility findings, not a successful packet run.
ProspectiveOnly is not selected until historical limits and prospective producer capability are both established; otherwise NotEstablished/BlockedPendingAuthorityProducers remains explicit.
Stop after report delivery. No follow-on schema changes, receipt backfill, replay, dashboard switch or deployment.

## Acceptance checklist for this procedure

- Exact approved disposable target and permission enforcement precede source reads.
- Direct query path cannot initialize mutating services.
- Immutable coherent view and full relevant membership are preserved.
- Original bytes/typed positions and external artifact provenance remain distinct.
- Bounds, missing schemas and unresolved dependencies fail honestly.
- Queries/credential details and actual target require separate execution review.
- Implementation, migrations, restored replay and production deployment remain held.
